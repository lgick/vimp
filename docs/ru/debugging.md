# Отладка (headless-прогон и браузерная половина)

Матч VIMP прячет своё состояние сразу за тремя стенами: авторитетная
половина крутится в Web Worker, сама симуляция — WASM, а между хостом и
клиентом идёт бинарный кадр по WebRTC. Типичный отказ — не исключение, а
чёрный холст, танк в стене или ключ снапшота, который молча не доезжает до
рендера. **Молчание и есть форма отказа.**

Эта страница описывает отладочный контур, превращающий молчание в текст:

- **headless-runner** (`npm run sim`), замыкающий
  `хост → бинарный кадр → ClientCore → hot-буфер → сцена в JSON` в одном
  Node-процессе, без браузера и без человека;
- **проверки инвариантов**, называющие нарушенный контракт вместо тишины;
- **дампы ядра** (`debug_json`) для багов физики;
- **детектор рассинхрона предикта** (`take_divergence`);
- **браузерная половина**, записывающая живой матч в тот же формат
  сценария, — пойманный человеком баг прогоняется headless.

От игрового плагина ничего не требуется: всё приезжает через ABI-макросы
(`export_game_core_abi!`/`export_client_core_abi!`) и через trait-методы с
дефолтами, поведение в проде не меняется (`ENGINE_API_VERSION` не
бампается).

## Контур в одной команде

```bash
npm run sim                       # встроенный смоук на фикстуре miniGame
npm run sim -- --scenario s.json  # прогон сценария
npm run sim:replay s.json         # то же короче (`--scenario` уже подставлен)
npm run sim:check                 # вердикт только в stdout, файлы не пишутся
```

Опции CLI (`packages/engine/bin/vimp-sim.js`, он же bin `vimp-sim` пакета
`vimp-engine`):

| Опция | Смысл |
| --- | --- |
| `--scenario <path>` | JSON сценария; без неё идёт встроенный смоук |
| `--game <path>` | каталог пакета игры или прямо `dist/manifest.json` |
| `--core <path>` | node-сборка ядра игры, перекрывает `entries.wasmNode` |
| `--out <dir>` | корень отчётов (по умолчанию `.debug`) |
| `--no-write` | печатать отчёт в stdout вместо записи файлов |
| `--determinism` | прогнать сценарий дважды и сравнить потоки кадров (инвариант 12) |
| `--help` | подсказка |

**Код возврата — это вердикт**: `0`, если не упал ни один инвариант, `1`,
если упал хотя бы один (имена нарушенных проверок печатаются в stderr).
Именно это делает цикл автономным: правка → прогон → чтение текста →
повтор.

### На каком ядре идёт прогон

Порядок поиска в `devtools/pluginLoader.js`, по убыванию точности:

1. `--game <путь>` → читается манифест, `engineApi` сверяется с этой
   сборкой движка, импортируются `entries.host`/`entries.client`, ядро
   берётся из `entries.wasmNode` (**node**-сборка WASM-ядра, по конвенции
   `dist/core-node/`);
2. `--core <путь>` → перекрывает `entries.wasmNode`;
3. ничего → фикстура `miniGame` из поставки движка
   (`packages/engine/tests/fixtures/miniGame/`), её ядра — обычный JS.
   Ради этого фолбэка `packages/engine/package.json:files` публикует
   `tests/fixtures` — «чистка» этого списка молча сломает `npm run sim` без
   `--game`.

`entries.wasmNode` опционально. Игра без него просто не прогоняется
headless на своём настоящем ядре — runner скажет об этом прямо, а не будет
угадывать. Объявленный файл обязан существовать: манифест, указывающий на
node-ядро, которого нет в опубликованном пакете, валится именно этой
фразой, а не сырым `ERR_MODULE_NOT_FOUND` из резолвера модулей. Кладите
глюe **внутрь публикуемого `dist/`** — ignore-правила действуют и внутри
каталогов из `files`. Обе половины плагина дополнительно сверяются с
`engineApi` манифеста: это ловит пересобранный манифест рядом с отставшим
`dist/`. См. [plugin-api.md](plugin-api.md#gamemanifest).

Ещё одно про `--game`: runner импортирует **клиентский** бандл игры, а его
внешние зависимости обязаны резолвиться от места, где лежит пакет, — прежде
всего `pixi.js` (peer-зависимость плагина). Установленная копия
(`node_modules/<пакет>`) резолвит его от проекта, а тарбол, распакованный в
произвольный каталог, — нет, и прогон падает с
`Cannot find package 'pixi.js'`. Распаковывайте внутрь проекта с
зависимостями либо ставьте пакет.

## Формат сценария

```json
{
  "version": 1,
  "seed": 3812,
  "map": "arena",
  "config": { "timers": { "networkSendRate": 1 } },
  "participants": [{ "id": "p1", "name": "P1", "model": "m1" }],
  "timeline": [
    { "tick": 0,  "op": "join", "who": "p1", "team": "team1" },
    { "tick": 12, "op": "key",  "who": "p1", "action": "down", "name": "forward" },
    { "tick": 30, "op": "chat", "who": "p1", "text": "/nr" }
  ],
  "unusedSnapshotKeys": ["e1"],
  "divergence": { "thresholds": [0.5, 0.5], "capacity": 64 },
  "ticks": 1200,
  "dumpTicks": [6, 1200]
}
```

| Поле | Смысл |
| --- | --- |
| `version` | обязательно `1` |
| `seed` | uint32, уезжает в `room.seed` — тот же seed даёт тот же мир (по умолчанию `1`) |
| `map` | стартовая карта (по умолчанию — дефолт игры) |
| `game` | `{ version }` пакета игры, как его прислало бы лобби |
| `room` | прочие переопределения комнаты (`applyRoomOverrides`) |
| `config` | патч, вливаемый в собранный конфиг игры до создания ядра; **таймеры — только внутри `config.timers`**: ключ верхнего уровня правит конфиг игры и в таймеры не роутится |
| `participants` | `[{ id, name, model }]`, непустой; `id` — локальный для сценария идентификатор, на него ссылается `who` |
| `timeline` | операции, при разборе сортируются по `tick` |
| `unusedSnapshotKeys` | ключи схемы, которых этот сценарий заведомо не порождает (инвариант 2) |
| `divergence` | пороги детектора предикта; `{}` — дефолты ядра, `null` — детектор выключен |
| `ticks` | сколько тиков прогонять (по умолчанию `600`) |
| `dumpTicks` | тики, на которых снимается срез сцены (по умолчанию — последний) |

Операции:

| `op` | Поля | Действие |
| --- | --- | --- |
| `join` | `who`, `team` | участник заходит, под него создаётся настоящий `ClientCore` |
| `leave` | `who` | участник выходит |
| `key` | `who`, `action` (`down`/`up`), `name` | `HostGame.updateKeys` плюс тот же ввод применяется к клиентскому ядру участника |
| `chat` | `who`, `text` | `HostGame.pushMessage` (включая чат-команды) |
| `vote` | `who`, `data` | `HostGame.parseVote` |

Два свойства стоит знать до того, как писать сценарий руками:

- **Шаг тика не задаётся сценарием.** Он берётся из конфига игры
  (`timers.timeStep`): виртуальные часы прокручиваются ровно на шаг, и
  боевой самокорректирующийся цикл `TimerManager` делает ровно один тик.
  Runner крутит настоящий цикл, а не подменяет его.
- **Ввод применяется синхронно**, очереди нет — поэтому `tick` в таймлайне
  это граница тика, на которой ввод приземлился. `op: key` намеренно
  дублируется на клиентское ядро: без этого дрейфу предикта не с чем было
  бы сравниваться.
- **Виртуальный клиент проводится как браузерный.** `VirtualClient`
  повторяет то, что делает с ядром `client/main.js`: `{ name, model }`
  участника уходит в `hooks.onAuth` при создании, `MAP_DATA` — в `set_map`,
  кадры панели — в `hooks.onPanel`, `KEYSET_DATA` — в `set_active`;
  `FIRST_SHOT_DATA` применяется немедленно (снапшот мира первого кадра), а
  `CLEAR` снимает сущности и сбрасывает ядро — ровно как браузер на каждом
  рестарте раунда и смене карты. Без этого ядро крутилось бы в состоянии,
  которого в игре не бывает: без модели, с выключенным предиктом и со
  сценой, где живут уже снятые с холста сущности. Порядок при этом — тот же,
  что на проводе: записывающий транспорт публикует кадр в момент, когда
  боевой код отдаёт нагрузку сокету, поэтому составной отправитель приходит
  раньше вложенных в него вызовов (`FIRST_SHOT_DATA` → `STAT` → `PANEL` →
  `KEYSET`). На `sendPing` ответ отправляется сразу
  (`updateRTT`) — иначе хост честно кикнет участника по таймауту RTT
  посреди длинного прогона.
- **Сброс спавна доезжает до клиента с задержкой.** Камера с `force_reset`
  приходит через буфер интерполяции (`interpolation.delay`) и сбрасывает
  зажатые клавиши предиктора. Нажатие в первые ~`delay` миллисекунд после
  `join` поэтому теряется на клиенте, хотя хост его держит, — начинайте
  ввод сценария на несколько десятков тиков позже join.

## Инварианты

По итогам прогона runner выполняет 12 проверок
(`packages/engine/src/devtools/invariants.js`). Каждая — `pass`, `fail` или
`skip`; `skip` означает «в этом прогоне нечего проверять» и никогда не
маскирует нарушение. Каждое нарушение — строка с именем клиента, ключа и
значения.

| № | Имя | Что ловит |
| --- | --- | --- |
| 1 | `finiteValues` | `NaN`/`Infinity` в декодированных полях и hot-буфере |
| 2 | `snapshotKeysUsed` | ключ схемы не дал ни одной строки — «сущность не спавнится» либо несовпадение id ключа (намеренные случаи объявляются в `unusedSnapshotKeys`) |
| 3 | `fieldWidths` | число декодированных полей ≠ числу полей схемы — уехала позиционная привязка в `interpolator.rs` |
| 4 | `frameFormat` | байт версии кадра ≠ `SNAPSHOT_FORMAT_VERSION` либо падение `decode_frame` |
| 5 | `hotLayout` | обход hot-буфера потребил не ровно `len` float'ов — дрейф ширины записи или порядка групп |
| 6 | `panelContract` | объявленное поле `panel` не доезжает до клиентского конфига (значение приходит с именем `undefined`) |
| 7 | `renderCoverage` | живой ключ снапшота отсутствует в `gameSets`/`entitiesOnCanvas` — класс «чёрный холст» |
| 8 | `keyBindings` | `playerKeys` хоста ↔ keyset'ы клиента ↔ имена клавиш из сценария |
| 9 | `predictionDrift` | дрейф предикта выше порога (см. ниже) |
| 10 | `roundLifecycle` | раунд закончился, победитель назначен, респауны прошли, участники не утекли |
| 11 | `actorLeak` | `players_data()` расходится с активными участниками |
| 12 | `determinism` | два прогона одного сценария дают одинаковый поток кадров — кадры сравниваются по хешу, и хеши собираются только под `--determinism` (на длинном матче сам поток стоил бы мегабайтов отчёта) |

Инвариант 12 — самопроверка всего остального: он держится только потому,
что время, таймеры и случайность хоста идут через подменяемый `clock` (см.
[configuration.md](configuration.md#libclockjs)), а seed фиксируется
сценарием.

## Отчёт

Пишется в `.debug/run-<метка времени>/` (`.debug/` в `.gitignore`):

| Файл | Содержимое |
| --- | --- |
| `report.md` | вердикт для человека/нейросети |
| `report.json` | тот же прогон машинно, плюс `snapshotSchema` |
| `scene-<tick>.json` | по файлу на снятый тик: сцена каждого клиента, камера, панель и дамп ядра |

Срезы сцены вынесены в отдельные файлы: они самые объёмные и читаются
точечно; в `report.json` от них остаются только номера тиков в
`sceneTicks`.

Секции `report.md`:

- шапка — id и источник игры, seed, шаг, длительность, карта, участники;
- `## Outgoing frames` — счётчик по методам `SocketManager`;
- `## Clients` — по клиенту: сущности на холсте, ошибки декодирования,
  принятые порты;
- `## Map changes`;
- `## World (core dump)` — тела, коллайдеры, карта, узлы нава, сущности
  spatial-сетки, состояние rng, аккумулятор фикс-шага последнего среза;
- `## Prediction drift` — реконсиляции, нарушения, максимум |Δ| по
  компонентам;
- `## Invariants` — ради чего всё и затевалось: `✅/❌/⏭️`, имя проверки,
  её заголовок и каждая строка нарушения.

## Дампы ядра: `debug_json()`

Оба ядра отдают курированный дамп (сырой serde-вывод rapier нечитаем):

- **игровое ядро** — `GameCore.debug_json()` (экспортируется
  `export_game_core_abi!`, поэтому достаётся каждому плагину даром):
  `bodies` (`tag`, `userData`, `translation`, `rotation`, `linvel`,
  `angvel`, `mass`, `bodyType`, `ccd`), `colliders` (`shape` +
  `halfExtents`/`radius`, `isSensor`, группы столкновений/солвера в hex,
  `parent`), `map` (`setId`, `step`, размеры сетки, счётчики
  статики/динамики, респауны), `nav` (узлы/рёбра/шаг сетки), `spatial`
  (размер ячейки, заполненность по ячейкам), `rng.state`,
  `step.accumulator`;
- **клиентское ядро** — `ClientCore.debug_json()`: `myGameId`, `offset`,
  `hotLen`, `framesOut` и `interpolator` (глубина буфера, `seqWindow`,
  `seq`/`serverTime` последнего кадра, `offset`, `lastRenderTime`).

Порядок записей детерминирован — дампы двух прогонов сравниваются дифом.

Из JS дамп доступен через `GameCoreAdapter.debugJson()`,
`HostGame.debugSnapshot()` (мета хоста + дамп ядра) и
`VirtualClient.debug()`. Все они отдают `null`, если ядро игры собрано
против движка без этого метода, — старая сборка плагина прогон не роняет.

## Детектор рассинхрона предикта

Расхождение клиентского предикта с авторитетным состоянием — классический
«резиновый» баг, и в отдельно взятом кадре он не виден. Детектор сравнивает
обе величины **в момент прихода авторитетного кадра**, непосредственно
перед тем, как `on_server_state` затрёт предикт.

Два уровня, чтобы в базовом случае от плагина не требовалось ничего:

- **уровень 0** — без правок плагина: камера `render_overlay()` (для
  предсказывающего плагина это предсказанная позиция) против
  `state[0]`/`state[1]` авторитетного player-блока. **Это контракт**:
  уровень 0 считает, что первые два компонента player-блока — мировые x/y.
  Если раскладка начинается с другого, реализуйте `predicted_state()` —
  иначе инвариант 9 будет врать. В записях уровня 0 компоненты названы
  `x`/`y`; на уровне 1 они адресуются индексом, потому что их смысл —
  игровой;
- **уровень 1** — один опциональный trait-метод
  `GameClientDef::predicted_state() -> Option<[f32; PLAYER_STATE_LEN]>`
  (дефолт `None`), сравнение покомпонентное; парный необязательный
  `replayed_inputs() -> Option<(f64, f64, usize)>` отдаёт окно истории
  ввода, переигранное последним реконсилем.

Настройка — опциональная секция `divergence` движкового клиентского
конфига (в боевом конфиге её нет, и тогда путь кадра не меняется вовсе):

```json
{ "thresholds": [0.5, 0.5], "defaultThreshold": 1.0, "capacity": 64 }
```

`thresholds` задаются **позиционно** по player-блоку (его раскладка —
игровая); недостающие компоненты берут `defaultThreshold`. Записи ложатся в
кольцевой буфер на `capacity` элементов, вытесненные считаются как
`dropped`. Запись кладётся, только если хотя бы один компонент вышел за
свой порог, — иначе отчёт утонул бы в шуме.

Калибровка порогов — часть написания сценария. Есть два источника
**ожидаемой** разницы, и порог ниже них превращает проверку в шум:

- **отставание на один фикс-шаг.** Сравнение происходит в момент прихода
  кадра, между рендер-тиками, поэтому реплика отстаёт до одного `timeStep`:
  на максимальной скорости это `скорость × timeStep` единиц позиции и один
  шаг ускорения по скорости.
- **то, что реплика не симулирует.** Коллизии, импульсы взрывов и телепорты
  бывают только авторитетными; каждый даёт одиночный крупный выброс,
  который следующая реконсиляция гасит. Держите их вне сценария, следящего
  за дрейфом, либо выключайте детектор для такого сценария
  (`"divergence": null`).

Проверка нужна для дрейфа, который **растёт**: разошедшаяся формула ядра и
реплики обратно не сходится.

`ClientCore.take_divergence()` (экспорт `export_client_core_abi!`)
вычерпывает буфер и отдаёт:

```json
{ "samples": 29, "violations": 0, "dropped": 0, "maxDelta": [0.0, 0.0],
  "records": [{
    "source": "predicted", "serverTime": 1234, "localNow": 5678,
    "offset": 12.5, "inputSeq": 41,
    "replayed": { "from": 5600, "to": 5678, "count": 7 },
    "predicted": [...], "authoritative": [...], "delta": [...],
    "thresholds": [...], "exceeded": [1]
  }] }
```

Существенно: сопоставление идёт **по времени, а не по `seq`** — предиктор
переигрывает историю ввода от момента авторитетного состояния. Поэтому в
записи есть `serverTime`, `offset` и окно переигранного ввода: именно они
локализуют уехавшую формулу.

## Браузерная половина

Headless-прогон не воспроизводит настоящий WebRTC, PixiJS и живой ввод
человека. Браузерная половина захватывает всё это в тот же формат сценария.

Всё описанное ниже живёт только в dev: рекордер висит на
`gameConfig.isDevMode` (выставляется из `room.isDevMode`, который
`client/main.js` берёт из `import.meta.env.DEV`), и прод-бандл вырезает
ветку сборкой.

### `window.__vimpDebug`

Доступен в dev-сборке; рассчитан на вызов из DevTools или через Chrome MCP
(`javascript_tool`, `read_console_messages`) — без участия человека в
разборе.

| Вызов | Что делает |
| --- | --- |
| `dump({ save, note })` | мета хоста + дамп ядра (через Worker) рядом со сценой этого клиента; по желанию выгружает |
| `startRecording()` | начинает запись живого матча; `false` — комната поднята без dev-режима |
| `stopRecording({ save = true, note })` | останавливает и (по умолчанию) выгружает записанный сценарий, отдаёт `{ scenario, file }` |
| `divergence()` | вычерпывает детектор рассинхрона этого клиентского ядра |
| `save(kind, payload, note)` | выгружает произвольную нагрузку (`scenario`/`dump`/`divergence`) |

Молчаливого отказа нет: вкладка, не хостящая комнату, бросает исключение с
текстом, а не возвращает `null`.

### Рекордер

`host/DebugRecorder.js` (Worker-safe — только `clock`) пишет живой матч в
формат сценария выше: seed, входы, каждый
`updateKeys`/`pushMessage`/`parseVote` с номером тика плюс
последовательность `dt`. Участники, вошедшие до старта записи, становятся
операциями `join` нулевого тика — иначе реплей стартовал бы с пустой
комнаты. Идентификаторы у сценария свои (`p1`, `p2`, …): `gameId`
переиспользуется после выхода игрока и склеил бы двух разных людей в одну
запись. Кап (`maxOps`/`maxDtSamples`) не молчит — переполнение уезжает в
`meta` сценария.

На фасаде хоста: `startRecording()`, `stopRecording()`, `isRecording`,
`debugSnapshot()`. Worker отдаёт их парой сообщений запрос/ответ
(`debug` → `debug_result` с `requestId`), которую `HostController`
заворачивает в промисы — см. [host.md](host.md).

### Выгрузка: `POST /debug/report`

Мастер поднимает маршрут **только вне прода**; файл ложится в тот же
`.debug/`, куда пишет headless-runner, — оба источника читаются одинаково.
Тело: `{ kind, payload, note }`, где `kind` из закрытого списка
(`scenario`, `dump`, `divergence`), лимит 8 MB. Ответ: `{ file, bytes }`.
См. [master.md](master.md#post-debugreport-только-dev).

### Логи хоста в консоли клиента

Worker изолирован от DevTools вкладки, поэтому отладочные события
авторитетной половины уходят портом 12 (`CONSOLE`,
`SocketManager.sendConsole`), а клиент печатает их как
`[vimp:debug][host] …`. Всё, что логирует отладочный API, несёт тот же
префикс `[vimp:debug]`, поэтому Chrome MCP фильтрует консоль по шаблону
вместо чтения всего потока.

### Из браузера в headless

```
запись в браузере → .debug/scenario-<ts>-N.json → npm run sim:replay <файл>
```

Записанный файл принимается `npm run sim:replay` без правок —
`tests/devtools/replayRecording.test.js` записывает матч фикстурным хостом
и тут же прогоняет результат через `runScenario`, так что это проверяемый
контракт, а не декларация.

**Известный предел: реплей — это новый матч, а не продолжение.** Рекордер
стартует с `tick = 0` и пишет только вход и ввод, но не состояние мира на
этот момент (позиции, фаза раунда, счёт, ротация карт), а сам реплей
крутится фиксированным `timeStep`, тогда как живой матч шёл с плавающим
`dt`. Значит «баг, пойманный в браузере, догоняется `sim:replay`» верно для
багов, воспроизводимых **с начала матча**. Начав запись на пятой минуте, вы
получите реплей без той ситуации, которую видели. Снять предел можно
снимком `initialState` в записи (в движке уже есть `serialize_state()` для
эстафеты Worker'ов) — это отдельная задача.

## Рекомендуемый порядок для нового плагина

1. Собрать node-сборку ядра (`core/pkg-node/`) и указать на неё
   `entries.wasmNode`.
2. `npm run sim -- --game <пакет> --scenario <сценарий>` — устранить все
   нарушения инвариантов. Большинство багов «чёрный холст»/«ничего не
   спавнится» умирает здесь, текстом, без браузера.
3. Когда матч стабилен — добавить `--determinism`.
4. И только потом открывать две вкладки ради ручного смоука; если там что-то
   не так, `startRecording()` → `stopRecording()` → `npm run sim:replay`
   возвращает случай на шаг 2.
