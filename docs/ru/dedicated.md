# Dedicated-сервер (Node.js)

Dedicated-сервер — отдельный процесс Node.js, который держит один
авторитетный матч одной игры 24/7. Симуляция крутится **в самом процессе**
(без Worker'а и без вкладки хостера), браузеры подключаются к нему прямым
WebSocket, лобби, OAuth и WebRTC не участвуют вовсе.

Это третий контур движка — рядом с P2P-лобби ([master.md](master.md)) и
браузерным SDK ([standalone.md](standalone.md)).

```
  вкладка браузера                 процесс Node.js
  ┌──────────────────┐             ┌──────────────────────────────────┐
  │ клиент движка    │  WebSocket  │ WebSocketServer  (путь /game)    │
  │ (mode=dedicated) │ ──────────► │   └─ PortMachine (хендшейк)      │
  │                  │  ws://…/game│        └─ HostGame + ядро игры   │
  └──────────────────┘             │ express: /config, /games/*, SPA  │
                                   └──────────────────────────────────┘
```

Код: `packages/engine/src/dedicated/main.js`.

## Точка входа

`packages/engine/src/master/main.js` — диспетчер:

```js
if (process.env.VIMP_DEDICATED_GAME) {
  await import('../dedicated/main.js');   // dedicated-сервер
} else {
  await import('./lobby.js');             // лобби-мастер
}
```

Поэтому у обеих ролей общие `CMD ["node", "src/master/main.js"]`,
`npm start`, `npm run dev` и watch-списки nodemon — роль выбирает только
окружение.

## Запуск

```bash
VIMP_DEDICATED_GAME=tanks npm run dedicated  # разработка (HTTP, nodemon)
VIMP_DEDICATED_GAME=tanks npm start          # production (HTTP за Nginx)
```

`npm run dedicated` — это `npm run dev` плюс `src/host` в watch-списке
nodemon: здесь хост крутится в этом же процессе, поэтому правка хоста
обязана перезапускать сервер.

Пакет игры должен быть установлен (или подключён через `npm link`) и
**собран**, включая node-сборку ядра: процесс импортирует host-плагин как
обычный ES-модуль и грузит `entries.wasmNode` (`core/pkg-node`,
`npm run core:build:node` в репозитории игры). Без неё сервер отказывается
стартовать именованной ошибкой, а не сырым отказом резолвера.

| Переменная | Значение |
| --- | --- |
| `VIMP_DEDICATED_GAME` | id игры из `master:games`; она же переключатель роли |
| `VIMP_MASTER_PORT` | порт HTTP + WebSocket (по умолчанию `3002`) |
| `VIMP_DOMAIN` | прод-домен — используется при проверке `Origin` |
| `GAMES_MATRIX` | JSON `[{id, package, version}]`, каталог игр (формат мастера) |
| `VIMP_DEDICATED_ROOM` | JSON с настройками комнаты: `map`, `maxPlayers`, `roundTime`, `mapTime`, `friendlyFire`, `seed` |

В отличие от лобби-мастера dedicated-сервер читает их **и в dev**
(`packages/engine/src/config/env.js`): другого источника игры, порта и
настроек комнаты у него нет. Мусор в `VIMP_DEDICATED_ROOM` — именованный
отказ при старте, а не молчаливый дефолт.

Всё остальное берётся из `packages/engine/src/config/master.js` — см.
[configuration.md](configuration.md#packagesenginesrcconfigmasterjs).

## HTTP

Security-заголовки ставит тот же middleware, что и у мастера
(`packages/engine/src/master/httpSecurity.js`).

### GET /config

```json
{ "mode": "dedicated", "gameId": "tanks", "gameVersion": "0.6.0", "wsPath": "/game" }
```

Клиент движка пробингует этот эндпоинт на старте и переключается на загрузку
с прямым WebSocket; лобби-мастер по тому же URL отвечает
`{ "mode": "lobby" }` — см. [client.md](client.md#режимы-загрузки-bootjs).

### Каталог игры

Те же URL-ы, что у мастера, но всегда ровно об одной игре:

- `GET /games/manifest.json` → массив из единственного манифеста;
- `GET /games/:id/manifest.json`;
- `GET /games/:id/maps/manifest.json`, `GET /games/:id/maps/:name`;
- `/games/:id/*` → статика из `dist/` пакета игры.

Клиентскую половину игры и её `.wasm` браузер грузит по этим URL-ам ровно
так же, как в лобби-контуре, поэтому `GameCatalog` переиспользуется целиком
(включая dev-вариант манифеста с исходниками Vite `/@fs/`). Сам клиент
движка раздаёт ViteExpress: в dev — из исходников, в проде — статику из
`packages/engine/dist`.

## Игровой WebSocket

`ws://<host>:<port>/game` (`wss://` за Nginx). Формат кадров тот же, что
везде в движке — `JSON.stringify([port, data])` для протокольных кадров и
бинарный кадр снапшота для состояния мира (см. [network.md](network.md)), —
поэтому клиент транспорты не различает.

- каждое соединение получает socketId (`crypto.randomUUID()`) и собственное
  состояние в `PortMachine` (автомат хендшейка общий с Worker-хостом и
  standalone SDK — [host.md](host.md));
- `Origin` проверяется как в сигнальном сервере; соединение без заголовка
  `Origin` разрывается;
- лимит участников обеспечивает сама порт-машина (`roomFull`, код закрытия
  `4006`);
- бэкпрешер: при `bufferedAmount` больше 256 КБ ненадёжные кадры
  (позиционные снапшоты) этому клиенту дропаются — надёжные не дропаются
  никогда. Разделения meta/state у WebSocket нет, поэтому PING/PONG идёт
  надёжным каналом и RTT фактически меряет TCP-путь;
- отключение снимает участника — и только: матч продолжается даже без
  единого игрока в комнате.

Процесс публичный, живёт 24/7 и не прикрыт ни лобби-гейтом, ни OAuth, поэтому
адаптер (а не изоморфная `PortMachine`) держит четыре ограничения:

| Ограничение | Значение | Зачем |
| --- | --- | --- |
| `maxPayload` | 64 КБ | легитимный кадр клиента — строка чата, клавиши, голос: килобайты; дефолт `ws` — 100 МиБ, то есть память по запросу |
| частота сообщений | 300 кадров/с на сокет | на пике клиент шлёт ~60 кадров/с (клавиши + pong); кадры сверх лимита молча отбрасываются |
| частота подключений | 30 в минуту с адреса | каждое соединение стоит серверу `CONFIG_DATA` **до** всякой аутентификации, то есть без лимита сокет — усилитель. Отказ кодом 4009 |
| таймаут хендшейка | 120 с | соединение, не ставшее участником, слота в комнате не занимает, но держит сокет — тривиальный slowloris. Закрытие кодом 4008 |

Ключ лимита подключений — адрес клиента из `clientIp()`
(`src/lib/clientIp.js`, общий с мастером): адрес сокета, а в проде —
`X-Real-IP`, который Nginx деплоя перезаписывает из `$remote_addr`.
`X-Forwarded-For` не используется намеренно: тот же Nginx ставит его через
`$proxy_add_x_forwarded_for`, то есть *дописывает* реальный адрес к
присланному клиентом, поэтому первый адрес списка задаёт сам клиент — ключ по
нему снимался бы одним заголовком на соединение, а заполнив бакет чужого
адреса, атакующий закрыл бы вход конкретному игроку. Соединение, у которого
адреса нет вовсе (сокет уже разорван), обрывается, а не делит общий бакет со
всеми такими же.

Таймаут хендшейка щедрый намеренно: участник появляется только после
`AUTH_RESPONSE`, поэтому в окно укладываются инициализация WebGL и запекание
ассетов у клиента (`CONFIG_READY` уходит после них) **плюс ввод ника игроком**.

Любой отказ закрывает сокет кодом, который клиент понимает
(`client/network/policyClose.js`). На всех четырёх — 4001 (`invalidOrigin`),
4006 (`roomFull`, его шлёт порт-машина), 4008 и 4009 — клиент **остаётся на
месте**, а не перезагружает страницу через 3 с, как при обычном разрыве:
перезагрузка потратила бы ещё одно соединение того же лимита, заново запустила
бы тот же таймер хендшейка, никак не поменяла бы origin страницы и не
освободила бы слот в комнате. Брошенная вкладка перезагружалась бы вечно, а
ждущий слот игрок за 30 витков сам упёрся бы в лимит подключений — и увидел бы
его сообщение вместо своей причины. Текст причины даёт `POLICY_CLOSE_INFORMS`
для 4001/4008/4009; 4006 в нём нет намеренно — эту причину порт-машина
доставляет сама, кадром `TECH_INFORM` непосредственно перед закрытием.

## Идентичность и профили

Вход только гостевой: ник — поле формы, которое валидирует движковый
`isValidName` (`createGuestIdentity`,
`packages/engine/src/host/identity.js`), а запросы профиля отвечают offline
-дефолтами (`packages/engine/src/lib/offlinePlayerData.js`). Центрального
auth-сервиса в этом контуре нет, поэтому **гостевые ники не уникальны и не
подтверждены**, а `rank`/`state` не персистятся. Центральный JWT для
dedicated — возможное продолжение, сегодня в контур не входит.

## Останов

По `SIGTERM`/`SIGINT` закрываются клиентские соединения, затем
`host.destroy()` (снимает таймеры и досинхронизирует профили), затем
HTTP-сервер, после чего процесс выходит.

## Отличия от P2P-хоста и ограничения

- **Одна комната на процесс.** Мета-модули движка (`TimerManager`, `Panel`,
  `Stat`, `Vote`, `Chat`) — модульные синглтоны; несколько комнат = несколько
  процессов/контейнеров.
- **Эстафеты Worker'ов нет.** Браузерный хост меняет Worker на границе раунда
  и матч переживает деплой; деплой dedicated-сервера — это перезапуск
  процесса и разрыв матча.
- **Ботов на старте нет.** Scripted-участники — понятие *игры*: их спавнит
  чат-команда игрока (`/bot 4` у танков), движок сам их не создаёт.
- **Пустая комната продолжает тикать.** `RoundManager.createMap()` запускает
  игровые таймеры прямо в конструкторе `HostGame`, поэтому симуляция крутится
  на заданной частоте (по умолчанию 120 Гц) даже без единого подключения —
  круглосуточно. Замер на фикстуре `miniGame` с пустой комнатой: ~3% ядра;
  настоящее Wasm-ядро стоит дороже — пропорционально пустому миру. Пауза на
  пустой комнате (`stopGameTimers()` при уходе последнего сокета,
  `resumeGameTimers(mapTimeLeft)` и `initiateNewRound()` на первом входе) —
  отдельный шаг: семантика таймеров раунда и карты требует своего разбора.
- **Рейтинга серверов и `GET /servers` нет.** Dedicated-сервер не
  регистрируется в каталоге лобби и через него не находится — игроки заходят
  по его адресу.

## Тесты

`tests/dedicated/dedicatedServer.test.js` (проект `engine-node`) поднимает
настоящий сервер на свободном порту поверх фикстуры `miniGame`, проводит
реальный `ws`-клиент через весь хендшейк до бинарного кадра снапшота,
проверяет `GET /config` и маршруты каталога и доказывает, что отключение
клиента не останавливает симуляцию (второй клиент входит и получает кадры).
