# Публикация релиза

## Короткий путь: `npm run release`

Одна команда вместо ~25 ручных шагов ниже. Запускается из репозитория
`vimp` и спрашивает перед всем необратимым. Чистая ветка `main` с upstream
обязательна только тогда, когда прогон пишет в этот репозиторий — крейт,
движок, скаффолдер или деплой; релиз одной игры печатает состояние дерева
замечанием и идёт дальше: игра здесь не меняет ни файла и собирается против
копий движка **из реестра**:

```bash
npm run release -- --dry-run     # репетиция: все проверки, ничего не публикуется
npm run release
```

Что скрипт решает сам:

- **Какие артефакты публиковать** — по трём независимым сигналам:
  изменённые пути от базовой точки (тег релиза, а пока тегов нет — коммит, в
  котором версия стала текущей), локальная версия против опубликованной
  (`npm view`, `index.crates.io`) и непустая секция `## [Unreleased]`. У игры
  те же три сигнала свои — неопубликованная локальная версия и коммиты после
  её тега `vX.Y.Z`, поэтому релиз одной только игры работает без движка.
  Затем применяются правила распространения из таблицы ниже: публикация крейта
  или движка игру только **предлагает** — опубликованная игра везёт своё
  собранное ядро и продолжает работать, поэтому о такой игре единственный
  вопрос — «выпустить?» (по умолчанию «нет»; под `--yes` — только с
  `--follow-games`). Невыпущенная игра всё равно получает на шаге прода
  строгий `sim` своей опубликованной `latest` против движка, который уходит
  в деплой; публикация крейта делает **обязательной** публикацию `vimp-engine` в том же
  прогоне (в его тарболе лежит `core/Cargo.toml` — версия крейта, с которой
  `vimp-contract` сверяет пин игры, а бамп крейта её переписывает);
  публикация крейта или движка делает **обязательной** и публикацию
  `create-vimp-game` — его хук `prepack` вшивает эти две версии в тарбол,
  и отставший скаффолдер молча генерирует игры на устаревших пинах.
- **Какую версию предложить** — по под-заголовкам `[Unreleased]`; это
  закрытый список, который фиксирует уровень ещё при написании кода, см.
  [Заголовки CHANGELOG задают версию](#заголовки-changelog-задают-версию).
  Enter принимает, либо вводится `patch`/`minor`/`major`/своя версия. Журнал
  игры уровень не задаёт: предложение для игры всегда patch и всегда
  подтверждается. Пин `vimp-engine-core`, отставший от крейта в реестре, —
  именно это остаётся после прерванного прогона — предлагает игру так же, как
  публикация крейта. Пин читается из `core/Cargo.toml`, а если крейт
  берёт зависимость из workspace (`{ workspace = true }`) — из корневого
  `Cargo.toml` игры; этот же файл переписывает шаг B.
- **Какие игры-плагины есть на машине** — по симлинкам `npm link`,
  глобальному реестру ссылок и соседним каталогам. Каждый кандидат
  валидируется (scope, версия вида `X.Y.Z`, зависимость `vimp-engine`,
  скрипты `build`/`core:build`, `vimp-engine-core` в `core/Cargo.toml`,
  чистое git-дерево с remote и upstream) и подтверждается по одному.

Что скрипт делает вокруг работы: снимает локальные `npm link` до любой
сборки и возвращает ровно те же пары после — включая падение и Ctrl-C;
запускает все проверки с захватом вывода (в консоли одна строка
на проверку, полный лог печатается только при падении — упавшая проверка
останавливает прогон **до** публикации). Для игры он собирает настоящий
тарбол, распаковывает из него `package/dist` и гоняет по тому, что реально
уедет в npm, `checkGamePackage` мастера — тот же вердикт, которым реестр
отвечает на заявку, только до того, как версия потрачена.

**Сам скрипт никогда не запускает `npm publish`/`cargo publish`.** Как
только артефакт закоммичен и его dry-run проверка прошла, скрипт создаёт
релизный тег (`<name>@X.Y.Z` для крейта/движка/скаффолдера, `vX.Y.Z` в
репозитории игры) и пушит его — этот пуш запускает
`.github/workflows/release.yml` в соответствующем репозитории, который
публикует через **npm/crates.io OIDC Trusted Publishing** (без `npm
login`/`cargo login`, без токена, без запроса 2FA — на этой машине ничего
вводить не нужно). CI занимает от полуминуты (движок) до трёх минут (игра:
тулчейн, сборка WASM, сама публикация; допускается до 10 минут), поэтому
скрипт не останавливается ждать: он запускает опрос реестра и идёт дальше, а
ждёт только там, где версия действительно нужна, — крейт и движок перед
первой игрой (`cargo update --precise`, `npm i -D`; E2E скаффолдера между
ними от реестров не зависит), каждую игру — перед её строгим `sim` на шаге
прода, всё остальное — перед пушем. Пока ждёт, раз в 30 секунд пишет об этом
и показывает страницу Actions репозитория. Игра всегда собирается против
версий, **лежащих в реестре**, а не против тех, что публикует именно этот
прогон, поэтому прерванный релиз не может оставить плагин на старом ядре.
Последний шаг пушит `main` — это деплой прода — **без вопроса**: к этому
моменту все артефакты уже опубликованы необратимо, а любой сбой проверок или
публикации остановил прогон раньше, так что придержанный пуш лишь оставил бы
`main` позади реестров. Отложить деплой (он перезапускает мастер) —
`--no-deploy`. Деплой не делается и тогда, когда публикация так и не
подтвердилась, а вы решили продолжать без неё («… не появился в реестре.
Продолжать без него?»). В обоих случаях `git push` попадает в итоговый список
«осталось». Если прогон падает, фоновые опросы реестра обрываются вместе с
ним.

Перед пушем тег сверяется и с `HEAD`, и с `origin`: пуш, который ничего не
меняет, ничего и не запускает. Тег, уже стоящий в `origin` на `HEAD` (прошлый
запуск CI упал), после подтверждения (по умолчанию «нет») удаляется там и
пушится заново — убедитесь, что тот запуск упал, а не ещё идёт. Тег, оставшийся на другом
коммите (фикс сделан после упавшего запуска), переставляется на `HEAD`
только по явному «да»: иначе релиз опубликовал бы старый коммит. В обоих
случаях номер версии не сжигается. Каждый `release.yml` — три джоба движка и
джоб каждой игры — вдобавок отказывает тегу, чья версия расходится с
`package.json`/`Cargo.toml`.

| Флаг | Действие |
| --- | --- |
| `--dry-run` | всё показать и проверить, ничего не коммитить/не тегировать/не пушить. **Только после `--`**: `npm run release --dry-run` отдаёт флаг npm, а не скрипту — прогон тогда идёт боевым. Preflight отказывается работать, найдя в окружении `npm_config_dry_run`, а из дочерних команд переменная вырезается. Холостой прогон не пишет версию, поэтому проверочный `npm publish --dry-run` для артефакта с бампом отвечает «нельзя опубликовать поверх уже опубликованной» — этот отказ в холостом прогоне гасится, любой другой по-прежнему валит шаг |
| `--only=crate,engine,scaffold,games,prod` | подмножество шагов |
| `--game=<путь>` | игра для неинтерактивного режима (можно повторять) |
| `--relink` | только (пере)привязать найденные/выбранные игры и выйти; работает без сети — в реестры не ходит. Аварийно — восстановить линки после `SIGKILL`. В обычной работе — `npm run link:games`, тот же флаг под более заметным именем, для настройки локальных чекаутов игр (см. [getting-started.md](getting-started.md#подключение-локального-чекаута-игры-плагина)) |
| `--yes` | принять предложенные версии и план; игры при этом берутся только из `--game`; перевыставление тега всё равно спрашивается |
| `--no-deploy` | выпустить всё, но `main` не пушить: деплой откладывается, `git push` попадает в итоговый список «осталось» |
| `--follow-games` | вместе с `--yes`: выпускать игры из `--game` и тогда, когда их только предлагает релиз крейта/движка (без флага такие игры не выпускаются) |
| `--help` | полное описание |

Флага пропуска проверок нет. Файла состояния тоже нет: источник истины —
репозитории и реестры, поэтому повторный запуск после сбоя видит уже
уехавшую версию и не публикует её дважды.

Шаги ниже — это то, что скрипт делает под капотом, и то, как сделать руками.

## Артефакты

Наружу уходят пять артефактов, и зависят они друг от друга в одном
фиксированном порядке:

- **`vimp-engine-core`** — Rust-крейт на crates.io
  (`packages/engine/core/`, rlib, против которого компилируется ядро любой
  игры);
- **`vimp-engine`** — пакет движка в npm (`packages/engine`, ровно те пути,
  что перечислены в его `files`: `src/lib`, `src/config`, `src/host`,
  `src/client`, `src/standalone`, `src/devtools`, `tests/fixtures`, `bin`);
- **`create-vimp-game`** — скаффолдер в npm (`packages/create-vimp-game`,
  пути из его `files`: `bin`, `src`, `templates`), пакет, стоящий за
  `npm create vimp-game`;
- **`@vimp-games/tanks`** — игра-плагин в npm, собирается и публикуется из
  отдельного репозитория
  [vimp-tanks](https://github.com/lgick/vimp-tanks);
- **мастер-сервер** — Docker-образ, который собирает CI и раскатывает на все
  VPS из `SERVERS_MATRIX` (см. [deployment.md](deployment.md)).

`packages/auth` в этом списке нет: он `private: true` и в npm не уезжает —
для него релиз состоит из одного деплоя прода.

## Почему порядок именно крейт → движок → скаффолдер → игра → прод

```
vimp-engine-core (crates.io)
      │  крейт игры зависит от него по версии, а не по пути:
      │  vimp-tanks/core/Cargo.toml → vimp-engine-core = "X.Y.Z"
      ▼
vimp-engine (npm)
      │  игра держит его в devDependencies, а
      │  scripts/build-game-manifest.js читает ENGINE_API_VERSION из
      │  установленной копии и штампует им dist/manifest.json
      ├─────────────────────────────┐
      ▼                             ▼
@vimp-games/tanks (npm)      create-vimp-game (npm)
      │                             хук prepack снимает ОБЕ версии выше в
      │                             src/versions.generated.json; шаблон
      │                             пинит их как vimp-engine ^X.Y.Z и
      │                             vimp-engine-core "A.B.C"
      │  прод игру НЕ пинит: мастер качает её из npm сам, по записи
      │  реестра игр auth-сервиса — деплоя релиз игры не требует
      ▼
прод (push в main → deploy.yml; нужен движку и крейту, не игре)
```

При нарушении порядка ломается тремя способами: WASM-ядро игры молча
соберётся против предыдущего релиза крейта; манифест получит устаревший
`engineApi`, который `GameCatalog` отвергнет при загрузке — лобби
поднимется, но комната не создастся; а скаффолдер увезёт снимок предыдущих
движка и крейта, и следующий `npm create vimp-game` сгенерирует игру на уже
отставших пинах — всплывёт это только на сборке её ядра.

### Бамп `ENGINE_API_VERSION` обесценивает каждую опубликованную игру

**Историческое, оставлено для чтения старых релизов (последний такой бамп —
0.21.0).** `ENGINE_API_VERSION` заморожена на 4 и гейтом совместимости больше
не является (`plan/plugin-forward-compat`), поэтому ситуация повториться не
может: опубликованная игра не отвергается за возраст, и описанный ниже
пропуск в релиз-скрипте не срабатывает. Новые возможности движка вместо
бампа регистрируются в `src/lib/capabilities.js` — см.
[Заголовки CHANGELOG задают версию](#заголовки-changelog-задают-версию).
Дальше — как скрипт вёл себя при бампе.

`npm run release` снимает локальные линки на чекауты игр и работает на копиях
**из реестра** (`scripts/release/links.js`) — релиз обязан проверяться на том,
что реально поставят пользователи. Но тогда каждая уже опубликованная игра
везла в манифесте СТАРЫЙ `engineApi`, и `assertEngineApiCompatible`
**отказывался** грузить её на новый движок. То есть на шаге движка совместимой
опубликованной копии ещё не существовало: её пересобирал и переиздавал шаг
`games`. (Сегодня этого отказа нет — движок принимает пакет любого поколения, —
а оставшаяся проверка стережёт лишь случай, когда пакет собран одним движком, а
пинуется к другому.)

Скрипт разбирается с этим сам, и правило у него такое:

- на шаге **движка** игра, чей установленный `engineApi` отличается от версии
  этого чекаута, **пропускается** с печатью причины — это невозможность
  проверки, а не её провал;
- на шаге **прода** то же расхождение — **отказ**. К этому моменту игра уже
  переопубликована, поэтому несовпадение значит, что её выпустили без
  пересборки под новый API.

Покрытие пропуском не теряется: шаг прода прогоняет те же игры, но на копиях,
которые действительно опубликованы. Пинов игр в корневом `package.json`
больше нет, поэтому эти копии шаг **ставит себе сам** — `npm install
<игра>@<версия>` во временный каталог, который затем сносится. Ни
`node_modules` репозитория, ни локальные линки при этом не трогаются; шаг
движка делает то же с версией, живущей в реестре сейчас (`latest`).

Что это требует от вас: **при изменении `ENGINE_API_VERSION` выпускайте игры в
том же прогоне** (в таблице ниже они и так помечены как **обязательно**), и не
пушьте в `main`, пока игры не вышли — см. предупреждение в шаге A2.

## Что вообще нужно публиковать

| Что изменилось | Крейт | Движок в npm | Скаффолдер в npm | Игра в npm | Прод |
| --- | --- | --- | --- | --- | --- |
| Мастер, вёрстка, деплой-скрипты | — | — | — | — | ✅ |
| `src/lib`, `src/config`, `src/host`, `src/client`, `src/standalone`, `src/devtools`, `bin`, фикстуры | — | ✅ | **обязательно** (пины) | когда удобно | ✅ |
| `packages/engine/core/` (Rust) | ✅ | **обязательно** (`core/Cargo.toml`) | **обязательно** (пины) | по желанию (пересборка против нового крейта) | ✅ |
| Контракт плагина без бампа `ENGINE_API_VERSION` | — | ✅ | **обязательно** (пины) | когда удобно | ✅ |
| Бамп `ENGINE_API_VERSION` | — | ✅ | **обязательно** (пины) | **обязательно** | ✅ строго последним |
| Только игра (правила, карты, ассеты, игровое ядро) | — | — | — | ✅ | — (версия поднимается из лобби, деплоя нет) |
| `packages/create-vimp-game/{bin,src,templates,scripts}` | — | — | ✅ | — | — |
| `packages/auth/` | — | — | — | — | ✅ отдельный джоб `deploy_auth`, отдельная миграция (пропускается, если `AUTH_SERVER_IP` не задан) |

«**обязательно** (пины)» — собственное правило распространения у
скаффолдера: своего кода в такой правке не меняется ни строки, но хук
`prepack` копирует версии движка и крейта в публикуемый тарбол, поэтому
бамп над ним всегда означает переиздание. `npm run release` выводит это сам
— и ловит в том числе случай прерванного прогона, когда движок уже уехал, а
скаффолдер за ним не поехал: он сравнивает пины на базовой точке с текущими.

Всё, чего нет в `files` пакета движка (`src/master`, шаблоны,
scratch-файлы `src/client/_*`), в npm не попадает вовсе — для таких правок
релиз состоит из одного шага «прод».

Со standalone SDK публикуется и клиентская половина движка (`src/client`,
`src/standalone`, экспорты `./client/*`, `./standalone`, `./style.css`).
Отсюда два следствия:

- всё, что импортирует публикуемый клиент, входит в публичную поверхность:
  поэтому `howler` живёт в `dependencies`, а не в `devDependencies`, а
  bare-импорт из `src/client`/`src/standalone`, которого нет в
  `dependencies`, ломает установку у потребителя SDK (страхует
  `tests/scripts/packageSurface.test.js`);
- правка в `src/client` больше не «только прод»: она уезжает в npm и
  требует записи в CHANGELOG наравне с остальным публикуемым кодом.

## Версии

Версии проставляет разработчик, он же запускает публикации. Правила бампа:

| Артефакт | Файл | Правило |
| --- | --- | --- |
| `vimp-engine-core` | `packages/engine/core/Cargo.toml` | semver cargo (в `0.x` ломающее бампает minor) плюс запись в `packages/engine/core/CHANGELOG.md` |
| `vimp-engine` | `packages/engine/package.json` | то же плюс запись в `packages/engine/CHANGELOG.md` |
| `create-vimp-game` | `packages/create-vimp-game/package.json` | то же, плюс запись в `packages/create-vimp-game/CHANGELOG.md`; релиз, вызванный одними пинами, уходит патчем и получает автоматическую запись с новыми пинами |
| `@vimp-games/tanks` | `vimp-tanks/package.json` | то же, в репозитории игры |

Бамп крейта доходит до игры через её пин, `vimp-tanks/core/Cargo.toml` →
`vimp-engine-core = "X.Y.Z"`: `npm run release` переписывает его на шаге B,
руками это первая команда шага B.

## Заголовки CHANGELOG задают версию

Под-заголовок, под который попадает запись, — не украшение: он **и есть**
уровень релиза, выбранный в момент написания кода, а `npm run release`
выводит из него точный номер (текущая версия + уровень). Список закрыт —
шесть имён Keep a Changelog плюс два собственных:

| Под-заголовок | Уровень | Для чего |
| --- | --- | --- |
| `### ⚠️ Breaking` | minor в `0.x`, major от `1.0` | всё, что может отвергнуть плагин или конфиг, который раньше грузился |
| `### Added` | minor | новый публичный API или поведение |
| `### Changed` | patch | изменение, которое не может сломать потребителя |
| `### Deprecated` | patch | объявление о будущем удалении |
| `### Removed` | patch | удаление, которое не может сломать потребителя |
| `### Fixed` | patch | исправление |
| `### Security` | patch | закрытая уязвимость |
| `### Migration` | — | обязательный спутник `⚠️ Breaking`, отдельно не встречается |

Что скрипт проверяет в preflight, до любой сборки и публикации — и только для
артефактов этого прогона, так что опечатка в журнале, который остаётся на
месте, никому не мешает:

- **Заголовок вне списка останавливает релиз.** Незнакомое имя иначе
  провалилось бы в patch и молча выпустило заниженную версию.
- **`⚠️ Breaking` и `### Migration` ходят парой**, в обе стороны. Пар в одной
  секции может быть несколько — так сейчас в `core/CHANGELOG.md`.
- Заголовок может нести уточнение после ` — ` или в круглых скобках:
  `### ⚠️ Breaking — reset() also clears my_game_id`,
  `### Migration (game plugins)`. Имена чувствительны к регистру; сам `⚠️`
  для разбора необязателен, но в обоих журналах он есть — придерживайтесь
  формы из таблицы.
- **Каждая запись лежит под `###`-заголовком.** Текст без заголовка над ним,
  `##` вместо `###` и отсутствующая секция `[Unreleased]` тоже останавливают
  релиз: каждый из этих случаев оставил бы секцию без заголовков и тихо свёл
  уровень к patch. Пустая `[Unreleased]` — норма: правка фикстур или `bin/`
  записью не является.
- Журнал артефакта, который **не** публикуется, даёт предупреждение — но даёт.
  `##` вместо `###` обнуляет секцию, а пустая секция и позволяет артефакт
  пропустить, так что дефект иначе спрятался бы за «нет изменений с X.Y.Z».
- **Примеры внутри блоков кода не разбираются** (``` ``` ``` или `~~~`),
  поэтому секция `Migration` может показывать фрагмент журнала, не сдвигая
  уровень.

Что проверить нельзя — и ради чего уровень выбирается так рано:

- **`ENGINE_API_VERSION` больше не бампается.** Константа заморожена на 4
  (`plan/plugin-forward-compat`), а новая движковая возможность вместо этого
  *регистрируется*: append-only запись в `src/lib/capabilities.js` плюс
  описание под `### Added`. Игра просит её через необязательное
  `GameManifest.requires`, а игра, которая не просит, продолжает работать.
  То, что раньше было принудительной пересборкой всего парка игр, стало
  обычным minor-релизом.
- Новый публичный экспорт идёт под `Added`, а не под `Changed`. Это ровно
  разница между minor и patch.
- Удаление, способное сломать плагин, идёт под `⚠️ Breaking` + `Migration`, а
  не под `Removed`.
- Тесты, рефакторинг и `docs/` записями не являются вовсе.

Сам номер в `[Unreleased]` не пишется: единственный источник уровня — это
заголовок, номер скрипт считает в момент релиза. Уровень игры из её журнала не
выводится: это patch, и он всегда подтверждается руками.
Собственный `CHANGELOG.md` игры, если он есть, всё равно датируется в
релизном коммите: непустая `[Unreleased]` становится `## [X.Y.Z] - дата` под
новой пустой `[Unreleased]`, без блока ссылок на теги. Разделитель берётся из
уже датированных записей самого файла; если их ещё нет — дефис для игры и
тире для журнала движка.

Вынужденный релиз с пустой `[Unreleased]` оставил бы в журнале дыру между
двумя версиями, поэтому запись скрипт пишет сам, под `### Changed`: движок,
выпущенный ради нового крейта, называет `core/Cargo.toml`, который везёт;
скаффолдер, выпущенный ради пинов, — сами пины; игра, выпущенная только
вслед за крейтом/движком, — то, против чего пересобрана. Непустая секция не
трогается никогда.

## Шаг 0: отвязать локальные чекауты (перед любым релизом)

Локальная разработка линкует репозитории друг в друга. Уцелевший линк
означает, что игра соберёт манифест против движка из вашей рабочей копии
вместо опубликованного, а WASM-ядро — против того `[patch.crates-io]`,
который вы могли добавить. Развязать **до** любой релизной сборки, в обоих
репозиториях:

```bash
cd vimp
npm unlink --no-save @vimp-games/tanks   # снимает симлинк, манифест не трогает
npm install                              # вернуть регистри-копию по lock-файлу
npm ls @vimp-games/tanks                 # в выводе нет "-> ./../vimp-tanks"

cd ../vimp-tanks
npm unlink --no-save vimp-engine
npm install
npm ls vimp-engine                       # нет "-> ./../vimp/packages/engine"
```

> ⚠️ **`--no-save` не опционален.** `npm unlink <pkg>` — алиас
> `npm uninstall`, поэтому без флага он заодно удаляет зависимость из
> `package.json` **и** `package-lock.json`, а `npm link` шага D обратно её
> не пишет. В `vimp` так молча пропадает `@vimp-games/tanks` — а прод
> ставит плагин именно из этого lock-файла (`npm ci`), то есть пропажа
> уезжает в релизный коммит.

Rust-сторона: `vimp-tanks/core/Cargo.toml` обязан зависеть от
`vimp-engine-core` по версии — напрямую или через
`[workspace.dependencies]` корневого `Cargo.toml` игры, и ни в одном `Cargo.toml` не должно остаться
`[patch.crates-io]` с локальным путём. Если добавляли его для разработки
крейта — уберите и выполните `cargo update -p vimp-engine-core`.

## Шаг A1: публикация крейта `vimp-engine-core`

Нужен, только если менялся `packages/engine/core/`.

```bash
cd vimp

npm run core:test                              # cargo test --workspace
cargo package -p vimp-engine-core --list       # что попадёт в тарболл

# поднять версию в packages/engine/core/Cargo.toml и добавить запись в
# packages/engine/core/CHANGELOG.md руками, затем:
cargo build                                    # обновить Cargo.lock
# снимок пинов идёт следом ТЕМ ЖЕ коммитом: шаг A2 гоняет `npm test`, а
# tests/scaffold/versions.test.js сверяет снимок с версией крейта — шаг A3
# обновил бы его слишком поздно
node packages/create-vimp-game/scripts/write-versions.js
git add -A && git commit -m "chore: bump vimp-engine-core to X.Y.Z"

cargo publish -p vimp-engine-core --dry-run

git tag vimp-engine-core@X.Y.Z
git push origin vimp-engine-core@X.Y.Z   # запускает release.yml: cargo publish через OIDC
```

Публикует именно пуш тега — `.github/workflows/release.yml` подхватывает его
и гонит `cargo publish` через crates.io Trusted Publishing (OIDC, без
`cargo login`/токена на этой машине). Дождитесь зелёного прогона в Actions,
прежде чем переходить к шагу A2: игра (шаг B) нуждается в этой версии живой.
Ссылки на релиз в CHANGELOG резолвятся именно в этот тег — без него они ведут
в 404.

## Шаг A2: публикация `vimp-engine` в npm

```bash
cd vimp

# 1. Полная проверка
npx eslint .
npm test
npm run core:test
npm run sim:check                                       # фикстура: 9/0/3
npm run sim -- --game node_modules/@vimp-games/tanks    # настоящий плагин

# 2. Версия и changelog правятся руками:
#    packages/engine/package.json, packages/engine/CHANGELOG.md
npm install                          # обновить package-lock.json
git add -A && git commit -m "chore: bump vimp-engine to X.Y.Z"

# 3. Публикация
npm publish -w vimp-engine --dry-run # посмотреть содержимое тарболла
git tag vimp-engine@X.Y.Z
git push origin vimp-engine@X.Y.Z    # запускает release.yml: npm publish через OIDC

# 4. Проверка, после зелёного прогона в Actions
npm view vimp-engine version
```

> ⚠️ **`git push` здесь заодно раскатывает прод.**
> [deploy.yml](../../.github/workflows/deploy.yml) срабатывает на любой push
> в `main`, независимо от `test.yml`. Обычно это не проблема — прод просто
> получает новый движок раньше новой игры, — но если менялся
> `ENGINE_API_VERSION`, пуш надо отложить до шага C, иначе раскатанный
> мастер отвергнет ту версию плагина, которая у него ещё запинена.

## Шаг A3: публикация `create-vimp-game` в npm

Идёт **после** A1 и A2, никогда раньше: хук `prepack`
(`packages/create-vimp-game/scripts/write-versions.js`) читает *локальные*
`packages/engine/package.json` и `packages/engine/core/Cargo.toml` — те
самые файлы, которые эти два шага только что подняли, — и пишет снимок в
`src/versions.generated.json`, из которого вне монорепозитория и берутся
`{{ENGINE_VERSION}}` / `{{CORE_VERSION}}` шаблона. Публикация раньше вошьёт
в тарбол предыдущие версии.

```bash
cd vimp

# 1. Сначала обновить снимок пинов — prepack сделал бы это только на
#    publish, а tests/scaffold/versions.test.js сверяет снимок с версией
#    движка, которую шаг A2 только что поднял
node packages/create-vimp-game/scripts/write-versions.js

# 2. Полная проверка — E2E единственный, кто реально разворачивает шаблон
#    и собирает его ядро (cargo + wasm-pack, минуты)
npx eslint .
npm test
npm run test:scaffold

# 3. Версия и changelog, руками:
#    packages/create-vimp-game/package.json,
#    packages/create-vimp-game/CHANGELOG.md
npm install
git add -A && git commit -m "chore: bump create-vimp-game to X.Y.Z"

# 4. Публикация
npm publish -w create-vimp-game --dry-run   # prepack печатает вшитые пины
git tag create-vimp-game@X.Y.Z
git push origin create-vimp-game@X.Y.Z      # запускает release.yml: npm publish через OIDC

# 5. Проверка, после зелёного прогона в Actions — пины должны совпасть с тем, что опубликовали A1/A2
npm view create-vimp-game version
npm create vimp-game@latest /tmp/pin-check -- --yes
grep vimp-engine /tmp/pin-check/package.json /tmp/pin-check/Cargo.toml
```

`src/versions.generated.json` под версионным контролем, поэтому снимок
уезжает в релизный коммит — без него следующий релиз упрётся в «рабочее
дерево не чистое»: `prepack` всё равно перезапишет файл на `npm publish`.
Когда скаффолдер едет только из-за бампа пинов, его `[Unreleased]` пуста,
релиз уходит патчем, а `npm run release` пишет и датирует запись
`### Changed` с новыми пинами.
Если движок вышел в том же прогоне, скрипт пропускает у скаффолдера
`npx eslint .`: шаг движка только что его прогнал, а с тех пор поменялись
лишь версии и снимок пинов. `npm test` идёт всё равно — шаг движка гнал его
до своего бампа, и дерево, уходящее в тарбол скаффолдера, ещё никто не
проверял, — как и `test:scaffold`.

## Шаг B: публикация `@vimp-games/tanks`

Выполняется в репозитории игры. Нужен Rust-тулчейн (`rustup` +
`wasm-pack`) — см. `docs/ru/getting-started.md` того репозитория. Шаги 1–4
ниже собирают и проверяют **локально** (CI их для игры не повторяет — см.
`vimp-tanks/.github/workflows/release.yml`); реально публикует шаг 5:
`git push --tags` запускает этот workflow, который заново собирает
WASM-ядро + `dist/` и гонит `npm publish` через OIDC Trusted Publishing
(без локального `npm login`/токена). Так же для `@vimp-games/snakes` через
`vimp-snakes/.github/workflows/release.yml` (её собственные локальные шаги
здесь не задокументированы — см. `CLAUDE.md` того репозитория).

```bash
cd vimp-tanks

# 1. Подтянуть обе свежие половины движка
#    - крейт: поднять в core/Cargo.toml до vimp-engine-core = "X.Y.Z"
cargo update -p vimp-engine-core
#    - npm-пакет: именно он штампует engineApi в манифест
npm i -D vimp-engine@^X.Y.Z
npm ls vimp-engine                   # регистри-копия, а не линк

# 2. Сборка: сначала WASM, потом dist/
npm run core:build                   # pkg-web + pkg-node
npm run build                        # бандлы, ассеты, карты, manifest.json

# 3. Проверки
npx eslint .
npm test
npm run core:test
npm run sim                          # смоук-прогон движка на этой игре
npm run sim:scenarios                # собственные сценарии игры
npm run check:pack                   # манифест смотрит внутрь dist/ (также на prepack)

# 4. Версия: `npm version patch` (поднимет package.json и корень
#    package-lock.json, создаст коммит и тег); руками — правьте оба файла:
#    отставший корень lock перепишет ближайший npm link, и дерево станет грязным

# 5. Публикация (scope публичный, задан в publishConfig): dry-run — это
#    только просмотр тарболла, реально публикует пуш тега, он запускает CI
npm publish --dry-run
git push && git push --tags

# 6. Проверка, после зелёного прогона в Actions
npm view @vimp-games/tanks version
```

Дальше — глазами в `dist/manifest.json`: `engineApi` обязан совпасть с
`ENGINE_API_VERSION` опубликованного движка, а `entries.wasmNode` —
указывать на `./core-node/<crate>.js`, то есть внутрь `dist/`,
единственного каталога, который пакет везёт с собой.

> `npm run release` читает это за вас — и делает ещё одно: собирает тарбол,
> распаковывает из него `package/dist` и гоняет по нему
> `packages/engine/src/master/gamePackageCheck.js`, тот самый модуль, которым
> мастер встречает `POST /games/submit` и `POST /games/mine/:id/version`
> (entries внутри `dist/`, каждая карта из `maps.list` на диске, каждое поле
> `roomForm` отвечено `roomDefaults`). Пакет, который отверг бы реестр,
> отвергается здесь — до того, как на него потрачена неперезаписываемая
> версия в npm. Несовместимый `requires` — не отказ, а предупреждение с
> подтверждением: мастер такую игру из каталога не выбрасывает, а лобби
> показывает её неиграбельной.

## Шаг C: раскатка прода

```bash
cd vimp

# 1. Доказать, что пара версий работает вместе, до отправки (по ЛОКАЛЬНОМУ чекауту)
npm test
npm run sim -- --game node_modules/@vimp-games/tanks

# 2. Пуш в main — это и есть деплой
git push
```

> **Корневой `package.json` игр больше не пинит.** Игры не зависимости этого
> репозитория и не часть образа: прод читает каталог из реестра игр central
> auth-сервиса, а пакет мастер качает из npm сам. Поэтому публикация новой
> версии игры не требует ни релиза движка, ни деплоя вообще — разработчик
> поднимает версию из лобби («Мои игры» → «Обновить версию»), админ
> подтверждает её в «Moderation», и каждый мастер подхватывает её ближайшим
> проходом синхронизации. Игра, которой ещё нет в каталоге, подаётся тем же
> путём. См.
> [deployment.md → Добавление игры](deployment.md#добавление-игры-в-каталог).
> Эти два действия — всё, что стоит между опубликованной версией и игроками,
> поэтому скрипт повторяет их по каждой игре в итоговом списке «осталось»,
> дописывая адрес лобби, если в окружении выставлен `VIMP_LOBBY_URL`.
>
> Отсюда и поведение `npm run release`: в прогоне, где публикуются одни игры,
> строка «прод» плана стоит как **«нет (только sim)»**. Шаг выполняется, но
> делает ровно одно — гонит `sim` в строгом режиме по каждой выпущенной игре,
> подтверждая, что опубликованная версия работает с текущим движком. Ни
> `npm test`, ни снимка пинов, ни `git push` не будет: в этом репозитории
> релиз игры не меняет ни файла.
>
> Исключение — прерванный прогон. Если крейт или движок уже опубликованы
> прошлым запуском, их бампы закоммичены и затегированы, а `git push` так и
> не прошёл, то `publish` у обоих артефактов уже `false`, но на ветке лежат
> незапушенные коммиты. Скрипт видит их (`@{u}..HEAD`) и ставит «прод» в
> **«да (push в main)»** с причиной «в main есть незапушенные коммиты
> (прошлый релиз?) — пуш будет деплоем» — даже когда публиковать в этом прогоне больше нечего.
> Тег на этих коммитах, которого ещё нет в `origin`, **не** пушится: пуш
> релизного тега — это публикация, а тег прерванного прогона мог остаться на
> коммите до фикса. Он попадает в итоговый список «осталось» вместе с
> `git push origin <тег>` — проверьте коммит и запушьте сами. Теги текущего
> прогона их шаги уже запушили сами.

Дальше CI собирает образ мастера, публикует его в GHCR и заходит по SSH на
каждый сервер из `SERVERS_MATRIX` (`docker compose pull && up -d`);
auth-сервис собирается, раскатывается и мигрируется отдельными джобами
(пропускаются, если `AUTH_SERVER_IP` не задан). Подробности —
[deployment.md](deployment.md).

```bash
gh run watch                                    # следить за прогоном
curl -s https://<ваш-домен>/servers | head      # лобби отвечает
```

Финальная проверка руками: открыть лобби, создать комнату, зайти вторым
табом. Расхождение `engineApi` проявляется ровно здесь — лобби грузится,
создание комнаты падает, а в логах мастера виден отказ `GameCatalog`.

## Шаг D: вернуть локальную связку

После релиза оба репозитория сидят на регистри-копиях. Чтобы вернуться в
локальный контур:

```bash
cd vimp-tanks && npm run core:build && npm run build   # WASM + dist/

cd vimp-tanks && npm link                     # зарегистрировать @vimp-games/tanks
cd ../vimp/packages/engine && npm link        # зарегистрировать vimp-engine

cd ../.. && npm link @vimp-games/tanks        # движок ← плагин
cd ../vimp-tanks && npm link vimp-engine      # плагин ← движок
```

Если игр-плагинов несколько, линкуйте их **одной** командой —
`npm link @vimp-games/tanks @vimp-games/snakes`. Состояние линков `npm link`
нигде не хранит: второй вызов реифицирует дерево по `package.json` и
подменяет ранее слинкованный пакет копией из реестра.

Важны обе стороны: без обратного линка импорты `vimp-engine/*` внутри
плагина резолвятся в регистри-копию в его собственном `node_modules` —
второй экземпляр модуля с молча разъехавшимся `ENGINE_API_VERSION`. См.
[getting-started.md](getting-started.md#подключение-локального-чекаута-игры-плагина).

## Грабли

- **Забытый `npm link` или `[patch.crates-io]`.** Закрывается шагом 0; это
  самый частый способ опубликовать пакет, собранный против кода, которого
  больше ни у кого нет.
- **Пуш тега, который в `origin` уже есть, ничего не запускает.** После
  упавшего `release.yml` повторный пуш того же тега — no-op; удалите его в
  `origin` (`git push origin :refs/tags/<тег>`) и запушьте снова — скрипт
  предлагает ровно это. Тег на коммите, чей `package.json` говорит другую
  версию, отвергает проверка версии в самом workflow.
- **Версии в npm неперезаписываемы, на crates.io — тоже.** Откат всегда
  новая патч-версия; на crates.io плохую версию можно дополнительно скрыть
  через `cargo yank --version X.Y.Z`.
- **`npm view` видит свежую версию на минуты раньше, чем `npm install`.**
  Установка читает сокращённый манифест с CDN реестра, который отстаёт, и
  отвечает `ETARGET`. Релиз-скрипт опрашивает реестр через
  `npm view --prefer-online`, а обе его установки — движка в игру и
  опубликованной игры во временный каталог sim — идут с `--prefer-online` и
  повторяются на `ETARGET` (10 × 15 с); руками — просто повторите установку
  через минуту.
- **`deploy.yml` не ждёт `test.yml`.** Зелёные тесты до пуша — ваша
  ответственность, CI прод не защищает.
- **`dist/` и `core/pkg-*` в репозитории игры в `.gitignore`.** Тарболл
  собирается из того, что лежит на диске: публикуйте только сразу после
  чистой `npm run core:build && npm run build`, иначе уедет вчерашний
  `dist/`.
- **Свежесозданный пакет в GHCR приватный.** Это важно только при поднятии
  нового сервера, см. [deployment.md](deployment.md).

## Откат

| Что сломалось | Как откатить |
| --- | --- |
| Крейт на crates.io | Опубликовать исправленную патч-версию; плохую скрыть через `cargo yank` |
| Пакет движка или игры в npm | Опубликовать исправленную патч-версию (перезаписать нельзя) |
| На проде плохая версия плагина | Подать прежнюю версию из лобби («My games» → «Update») и одобрить её в «Moderation» — монотонность версий нигде не проверяется. Ни релиза, ни деплоя: каждый мастер подхватит её на ближайшем проходе синхронизации |
| На проде плохая сборка мастера | `git revert` деплойного коммита и пуш — CI пересоберёт и раскатает прежнее состояние |
