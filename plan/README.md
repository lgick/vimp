# План: разделение на два репозитория + авторизация на лобби + рейтинг серверов

Все три направления реализованы и заархивированы в [`plan/done/`](done/):

- [done/repo-split/](done/repo-split/) — направление A: вынос игры в
  отдельный репозиторий, публикация движка как npm-пакета + Rust-crate
  (`split_a1.md`–`split_a5.md`).
- [done/central-auth/](done/central-auth/) — направление B: OAuth-авторизация
  на лобби, глобальный ник, rank/state через центральный auth-сервис
  (`auth_b1.md`–`auth_b6.md`, `auth_fixes.md`).
- [done/engine-game-split/](done/engine-game-split/) — более ранний архив:
  разделение движка/игры на рантайм-уровне (Этапы 1–8 + доработки Д1–Д7).
- [done/server-rating/](done/server-rating/) — направление C: рейтинг серверов
  (`/like`·`/unlike`), модель доверия игр к профилю, аннулирование rank/skills
  при бане хостера (`stage_1.md`–`stage_5.md`, `review.md`).

**Зафиксированные решения:**

- Подключение игр — готовые npm-бандлы (игра сама собирает `dist/`,
  включая WASM, в своём CI и публикует пакет).
- Аккаунты/рейтинг — центральный auth-сервис с общей БД PostgreSQL, все
  мастера ходят к нему по API.
- Ник/rank — JWT + отчёт хоста: мастер выдаёт подписанный токен, хост
  проверяет подпись и берёт ник из токена, итоги матча хост шлёт на мастер
  аутентифицированным REST.
- Реестр пакетов движка (2026-07-26): `@vimp/engine` — **публичный npm**,
  `vimp-engine-core` — **публичный crates.io** (не приватный registry, не
  git-зависимость) — игры создают сторонние разработчики, приватный registry
  требовал бы от них токена на чтение фактически публичного пакета. См.
  [done/repo-split/split_a1.md](done/repo-split/split_a1.md).
- Публичность (2026-07-26): публично только то, что нужно стороннему
  разработчику игры — это и есть SDK: `@vimp/engine` + `vimp-engine-core`.
  `@vimp/auth` — **приватный сервис** (`private: true`, не пакет), секреты
  только в `.env`. Плагины игр — на усмотрение автора (грузятся по URL, npm не
  обязателен); референс `@vimp/tanks` — публичный.
- Модель доверия игр к профилю (2026-07-26): писать rank/skills может **любая
  игра из каталога мастера** (курируемый онбординг — `gameId` выдаёте вы),
  каждая пишет **только в свой namespace** (`game_id`). **rank** — общий формат
  для всех игр (рисуется на сайте мастера единым шаблоном, часть публичного
  SDK-контракта); **skills** — приватный формат игры (JSONB `state`); ник/
  идентичность игра не трогает (только JWT). См. [done/server-rating/](done/server-rating/).

## Контекст

Проект уже прошёл внутреннее разделение движка и игры: граница
«движок↔игра» — это **URL-driven плагин-контракт**. Движок нигде не импортирует
игру статически; он грузит её только динамически по манифесту:
`import(manifest.entries.client)` в клиенте, `import(room.game.hostEntryUrl)` в
Worker хоста, `GameCatalog` на мастере читает `dist/manifest.json`. Барьер
ESLint (`no-restricted-imports`) и Rust-трейты `GameDef`/`GameSim`/
`GameClientDef` уже разводят код.

Авторизация реализована: центральный auth-сервис (`packages/auth`, см.
[docs/en/auth.md](../docs/en/auth.md)) выдаёт OAuth-логин, глобальный ник,
JWT-идентичность и rank/state по играм; хост верифицирует токен по `/jwks`,
итоги матча репортит на мастер аутентифицированным REST.

Оговорка (важно держать в доках): хост — недоверенный браузер, поэтому любые
присылаемые им rank/скиллы **технически подделываемы**. Это ограничение
P2P-архитектуры; полноценный анти-чит вне рамок этого плана. JWT защищает
идентичность (ник нельзя подменить), но не защищает от накрутки результата
своего матча. Единственная реально принятая мера — социальная: рейтинг
сервера `/like`·`/unlike` ([server-rating](done/server-rating/README.md)) даёт
игрокам топить накручивающего хостера голосами до блокировки, после которой
его вклад в rank/skills аннулируется (см.
[docs/en/master.md](../docs/en/master.md#server-rating-likeunlike),
[docs/en/auth.md](../docs/en/auth.md#schema)) — это компенсация, а не
предотвращение подделки.

## Что осталось сделать

### 1. Публикация пакетов движка (блокер для полной верификации A)

Код и конфигурация (`publishConfig`, `files`, `Cargo.toml`) готовы, сама
публикация — сознательно отложенное, ещё не выполненное действие:

- Опубликовать `@vimp/engine` в публичный npm registry
  (`packages/engine/package.json`, `publishConfig.access` уже `"public"`).
- Опубликовать `vimp-engine-core` в публичный crates.io.
- После публикации прогнать то, что от неё зависит:
  - реальный CI-билд `vimp-tanks` против опубликованного `@vimp/engine`
    (не path/symlink-зависимость);
  - живой `docker build` движкового образа без Rust-тулчейна, игра ставится
    из registry;
  - проверка контракта версий: игра, собранная с `engineApi` ≠
    `ENGINE_API_VERSION` мастера, отклоняется с внятной ошибкой;
  - живой браузерный тест на двух вкладках (создание комнаты, движение,
    выстрел, панель, звук) — см. `done/repo-split/split_a3.md`, пункт A3.6.

### 2. Ручная верификация авторизации (B)

Код и интеграционные тесты зелёные; следующее требует реального окружения
(реальные OAuth-провайдеры, минимум два домена-мастера) и делается руками:

1. Логин через провайдера (Google/Apple/GitHub), выбор уникального ника,
   повторная попытка занятого ника → отказ.
2. Вход в игру: ник в игре совпадает с ником лобби; поддельный/просроченный
   JWT → хост отклоняет.
3. Сыграть матч → rank/state обновились на auth-сервисе; переигровка на
   **другом** домене-мастере → подгрузились те же rank/state (проверка
   «глобальности»).
4. `/rank` в чате печатает актуальный рейтинг.
5. CSP: OAuth-редиректы проходят, политика не ослаблена сверх необходимого.

### 3. Ручная верификация рейтинга серверов (C)

Код реализован (все 5 этапов), кодревью пройдено — все находки 🔴/🟠/🟡, кроме
двух низкоприоритетных мелких (enumeration на публичном `GET
/host-rating/:id`, DRY парсинга `Bearer`), устранены (см.
[done/server-rating/review.md](done/server-rating/review.md)). Не выполнялся
автоматический сквозной smoke-тест (в сессии реализации не было локального
Postgres) — делается руками на чистой БД:

1. Поднять чистый Postgres, `npm run auth:db:migrate` — миграции применяются
   идемпотентно, бэкофилл `rank_events` отрабатывает.
2. `npm run dev:auth` + `npm run dev`, две вкладки (хост + гость), сыграть
   матч. Проверить в БД: `rank_events.hoster_user_id`/`session_id` заполнены,
   `state_snapshots` содержит снимок «до».
3. Гостем `/unlike <reason>` до `blockAt` → WS хоста закрывается `4002`,
   комната пропадает из лобби, повторный `register_host` даёт `blocked`.
4. Проверить откат: rank задетых игроков вернулся без вклада забаненного
   хостера; `states` восстановлены из самого раннего снапшота.
5. Рейтинг в карточке лобби (`+N`/`0`/`-N`) обновляется по `refreshInterval`,
   включая снятие комнаты заблокированного хостера на другом мастере.
