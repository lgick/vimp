# Кодревью: server-rating (коммит 204efff)

## Контекст

Направление `plan/server-rating/` (этапы 1–5) заменяет эфемерную `/ban`-модерацию
по IP на идентичностный рейтинг хостеров (`/like`·`/unlike`), переводит rank в
append-only леджер дельт с атрибуцией к серверу/сессии и добавляет
аннулирование rank/skills при блокировке хостера. Все 5 этапов помечены
✅ выполнен; `npm test` — 758/758 зелёных.

Ревью проведено по коду коммита 204efff. Автоматический сквозной smoke
(`/like`·/unlike → блок → откат → рейтинг в лобби) в сессии реализации **не
выполнялся** (нет локального Postgres) — и именно он вскрыл бы находку №1.
Ниже находки, отсортированные по серьёзности, с предлагаемыми решениями.

## Статус исправления (после ревью)

Все находки 🔴/🟠/🟡 и первая 🟡-мелкая («`Number(null) === 0`») исправлены;
`npx eslint .` чисто, `npm test` — 766/766 зелёных (добавлены тесты на
атрибуцию, эвакуацию, недоступность auth, `maxDelta`, реордер void).
Оставшиеся две мелкие находки (enumeration на публичном `GET
/host-rating/:id`, DRY парсинга `Bearer`) — не исправлены, низкий
приоритет, оставлены на усмотрение автора. Сквозной smoke на чистой БД
(раздел «Верификация» ниже) по-прежнему не выполнялся автоматически (нет
локального Postgres в сессии) — остаётся вручную.

- №1 (атрибуция не доходит до auth) — исправлено: атрибуцию теперь
  проставляет мастер (`attributionFor` в `master/main.js`) из проверенного

  `docs/en/host.md#player-rank-and-state-sync-stage-b4`.
- №2 (глобальный блок не эвакуирует уже запущенные комнаты) — исправлено:

  `refreshRatings` при `json.blocked`.
- №3 (недоступность auth — тихий провал) — исправлено: `_onRegisterHost` и

- №4 (`game_id` не валидируется против каталога) — исправлено:

- №5 (дельта rank не ограничена) — исправлено: `config.rank.maxDelta` +

- №6 (`voidHosterContributions` неатомарен, без драйвера повтора) —
  исправлено реордером: `host_ratings.blocked` пишется только после

- Мелкие: `readAttribution` теперь строго `Number.isInteger` + `> 0`;
  `refreshRatings` — самоперезапускающийся `setTimeout` вместо
  `setInterval`, не наслаивающий циклы.

## 🔴 Критично

### №1. Атрибуция `hosterUserId`/`sessionId` не доходит до auth — этап 4 нерабочий сквозняком

**Что не так.** Весь этап 4 (аннулирование) и снапшоты skills этапа 1 держатся
на том, что каждое `rank_events` и `state_snapshots` привязано к
`hoster_user_id`/`session_id`. Auth умеет их принять
(`readAttribution`, `packages/auth/src/main.js:304-309`) и записать
(`UserRepository.appendRankEvent` / `upsertState` / `snapshotState`,
`packages/auth/src/UserRepository.js:85-158`). Но **ни один вызывающий их не
отправляет**:

- `PlayerDataSync.flush` шлёт тело `{ delta }` и `{ state }` без атрибуции
  (`packages/engine/src/host/meta/modules/PlayerDataSync.js:134-149`);
- `PlayerDataProxy.putRank/putState` — тоже только `{ delta }` / `{ state }`
  (`packages/engine/src/master/PlayerDataProxy.js:33,42`);
- master-прокси `PUT /auth/rank`·`/auth/state` пробрасывает лишь
  `req.body?.delta` / `req.body?.state`
  (`packages/engine/src/master/main.js:215-229`).

Трассировка подтверждает: `grep hosterUserId` по `packages/engine/src/host` и
`.../client` — **пусто**. Единственный `sessionId` в SignalingServer
(`:109-110`) — это id WS-соединения, а не серверной сессии.

**Последствия.** В проде `rank_events.hoster_user_id` и `session_id` всегда
`NULL`; т.к. `upsertState` вызывает `snapshotState` только при
истинном `sessionId` (`UserRepository.js:147`), таблица `state_snapshots`
**никогда не заполняется**. При блокировке хостера `voidHosterContributions`
(`UserRepository.js:213-255`) находит 0 событий и 0 снапшотов и не откатывает
ничего. Заявленная головная фича плана («аннулирование rank/skills при бане»)
не работает end-to-end. Тесты зелёные, т.к. `tests/auth/UserRepository.test.js`
вызывает репозиторий напрямую с атрибуцией — сквозного теста нет.

**Важный нюанс безопасности решения.** Rank/state-синк инициирует **браузер
хостера** (недоверенный — создатель комнаты) под токеном каждого игрока через
stateless-прокси мастера. Если хостер сам положит `hosterUserId` в тело PUT, он
сможет: (а) занизить/подменить атрибуцию, чтобы уйти от аннулирования, или
(б) приписать честные начисления игроков **чужому** хостеру-жертве, чтобы при
его бане их обнулили. Поэтому атрибуцию должен проставлять **мастер по
проверенной идентичности хостера**, а не тело от хоста.

**Решение (рекомендуемое).** Проставлять атрибуцию на мастере из
`hosterUserId`, уже проверенного при `register_host`, и `sessionId`,
выданного мастером в момент регистрации комнаты:

1. При `register_host` мастер уже знает проверенный `hosterUserId` и создаёт
   комнату — выдать/сохранить `sessionId` (напр. `host.hostId` уже уникален на
   жизнь комнаты) в `HostRegistry`.
2. Rank/state-PUT от хоста должен нести признак комнаты (напр. `hostId`), по
   которому мастер в `forwardPlayerData` подставит `hosterUserId`/`sessionId`
   из `registry.get(hostId)` — тело от хоста как источник атрибуции не
   использовать.
3. `PlayerDataProxy.putRank/putState` пробрасывают `hosterUserId`/`sessionId`
   в тело запроса к auth; `readAttribution` их читает как сейчас.

**Решение (лёгкий MVP, если тяжёлый вариант отложить).** Хост кладёт
`hosterUserId = свой sub` + `sessionId` (uuid на комнату) в тело; принять
остаточный риск мис-атрибуции. Тогда обязательно закрыть вектор «фрейма жертвы»:
auth отклоняет запись, если `hosterUserId` в теле ≠ владельцу токена-хостера —
но при player-token это не проверить, поэтому вариант слабее и требует явного
фиксирования риска в `plan/README.md`.

**Тест-покрытие.** Добавить интеграционный тест, проходящий полный путь
host→master→auth и проверяющий, что после матча `rank_events.hoster_user_id`
заполнен, а `state_snapshots` содержит «до»; затем downvote до блока → откат.

## 🟠 Существенно

### №2. Глобальный блок не применяется к уже запущенным комнатам / на других мастерах

**Что не так.** `refreshRatings` (`SignalingServer.js:359-375`) при
периодическом опросе auth обновляет только `score`
(`setRatingForHoster`), но **игнорирует `json.blocked`** — не закрывает WS и не
снимает комнату. Блок фактически применяется лишь в двух точках: при
`register_host` (`:146-155`) и при голосе, который сам пересёк порог на **этом
же** мастере (`_vote`, `:349-352`).

**Последствия.** Хостер, заблокированный голосами на мастере A (или чей блок
случился в прошлом), продолжает держать живую, присоединяемую комнату на
мастере B до попытки перерегистрации. Цель «глобальной блокировки» (README,
решение №2) не достигается для активных комнат.

**Решение.** В `refreshRatings` при `json.blocked === true` эвакуировать все
комнаты этого хостера: для каждого `hostId` хостера закрыть WS кодом `4002` и
`registry.remove`. Вынести эвакуацию в общий приватный метод и переиспользовать
из `_vote`.

### №3. Недоступность auth при `register_host`/голосе → тихий провал без сигнала клиенту

**Что не так.** В `_onRegisterHost` вызов `this._hostRatingProxy.getRating(token)`
(`SignalingServer.js:147`) не обёрнут — при недоступности auth он бросает, и
исключение ловит только диспетчер сообщений (`:88`), который просто логирует.
Хост **не получает ни `host_registered`, ни `error`** — UI «создание комнаты»
зависает. Аналогично `_vote`: `getRating`/`vote` кидают → пользователю уже
сказали «Vote sent», но голос не ушёл и ошибка не всплыла.

**Последствия.** Мастер теперь жёстко зависит от доступности auth для любой
регистрации комнаты (раньше IP-бан был в памяти и не зависел). Отказ auth =
никто не может хостить, без обратной связи.

**Решение.** Обернуть обращения к `hostRatingProxy` в try/catch и слать
`_sendError(session, 'authServiceUnavailable')` (или мягкий degrade-режим —
разрешить регистрацию с `rating: 0`, если это приемлемо по трат-модели).
Зафиксировать выбранную политику в `docs/en|ru/master.md`.

## 🟡 Средне

### №4. `game_id` не валидируется против каталога мастера при записи rank/state

**Что не так.** Стадия 1.2 требует: мастер проверяет `game_id` запроса против
своего каталога (`config/master.js › games`) перед проксированием на auth. В
`forwardPlayerData` (`master/main.js:193-209`) проверки нет — `game` идёт как
есть; auth каталога не имеет. Итог: любой обладатель валидного identity-токена
может писать rank/state в **любой** `game_id`-namespace, в т.ч. игры не из
каталога, и самонакручивать rank прямым `PUT /auth/rank`.

**Последствия.** «Курируемый онбординг» (только игры каталога пишут в профиль)
не обеспечен. С учётом нерабочего аннулирования (№1) сейчас **нет никакого
средства отката** такой накрутки. Замечание частично относится к
пред-существующему прокси B4, но требование именно этой стадии не выполнено.

**Решение.** В `forwardPlayerData` отклонять `game`, отсутствующий в
`gameCatalog.ids` (404/400 `unknownGame`), до вызова прокси. Тест на отказ
записи для не-каталожного `game`.

### №5. Дельта rank не ограничена по величине

**Что не так.** `isValidRankDelta = Number.isInteger(delta)`
(`packages/auth/src/lib/validators.js:13`) — без верхней границы модуля. Один
`PUT /rank` может прислать `delta = 1e9`; кэш клампится в `[0..1_000_000]` при
пересчёте, но в `rank_events` пишется сырое значение, и любой игрок за один
матч может быть разогнан до клампа. Недоверенный хост может как накрутить, так и
обнулить ранг соперника, per-match санити-границы нет.

**Последствия.** Расширяет радиус поражения накрутки со стороны читер-хоста;
единственный задуманный предохранитель (аннулирование) сейчас не работает (№1).

**Решение.** Ввести конфиг `rank.maxDelta` и ограничить
`isValidRankDelta` диапазоном `[-maxDelta..maxDelta]`. Значение согласовать с
реальным потолком начисления за матч (см. `RoundManager.reportKill`).

### №6. `voidHosterContributions` неатомарен и не имеет драйвера повтора

**Что не так.** Операция не в транзакции (осознанно, `UserRepository.js:205-212`),
идемпотентность заявлена «повтор после сбоя пересчитает кэш заново». Но повтор
**никто не инициирует**: триггер стоит только на переходе `false→true`
(`_recomputeHostRating`, `:198`); `host_ratings.blocked` пишется **до** void
(`:187-193`), поэтому при сбое в середине void состояние `blocked` уже
сохранено, а `before.blocked` при следующем голосе уже `true` → void повторно не
запустится. Получается устойчивый частичный откат.

**Решение.** Либо обернуть `voidHosterContributions` в реальную SQL-транзакцию
(`BEGIN/COMMIT` на выделенном клиенте пула), либо разнести так, чтобы `blocked`
фиксировался только после успешного void, и добавить самопроверку
(«есть непогашенные события заблокированного хостера» → до-погасить) в
периодической задаче.

## ⚪ Мелкие / качество

- **`readAttribution`: `Number(null) === 0`** (`main.js:305`). Явный
  `hosterUserId: null` в теле даст `0` → запись атрибутируется к
  несуществующему `user 0` (нарушение FK при вставке). Сейчас недостижимо, но
  латентно. Проверять `Number.isInteger` строго и `> 0`.
- **Публичный `GET /host-rating/:id`** (`main.js:379-388`) отдаёт
  `{ score, blocked }` для любого `user_id` без авторизации — перечисление
  «заблокирован ли» для произвольных пользователей, в т.ч. никогда не хостивших.
  Низкий приоритет (значение и так публично в лобби), но enumeration стоит
  осознать/ограничить rate-лимитом.
- **Скрытый сайд-эффект в `_recomputeHostRating`** (`:198-200`): «пересчёт»
  тихо запускает деструктивный `voidHosterContributions`. Маскирует тяжёлую
  каскадную операцию под безобидное имя — минус к читаемости/тестируемости.
  Рассмотреть явный вызов void из `voteHost` по возвращённому `{ blocked }`.
- **Перекрытие `refreshRatings`** (`master/main.js:340-343`): `setInterval`
  не ждёт завершения; при медленном auth и многих хостерах циклы наслаиваются.
  Заменить на самоперезапуск через `setTimeout` после завершения.
- **DRY**: парсинг `Bearer` повторяется в `auth/main.js` (`requireAuth`,
  `POST /nick`) и `master/main.js` (`forwardPlayerData`). Вынести хелпер.

## Верификация (сквозной smoke, которого не было)

1. Поднять чистый Postgres, `npm run auth:db:migrate` — убедиться, что
   003/004 применяются идемпотентно и бэкофилл `rank_events` отработал.
2. `npm run dev:auth` + `npm run dev`, войти двумя вкладками (хост + гость),
   сыграть матч. **Проверить в БД**: `rank_events.hoster_user_id` и
   `session_id` заполнены (после фикса №1), `state_snapshots` содержит «до».
3. Гостем `/unlike <reason>` до достижения `blockAt` → WS хоста закрывается
   `4002`, комната исчезает из лобби, повторный `register_host` даёт `blocked`.
4. **Проверить откат**: rank задетых игроков вернулся на сумму без вклада
   баненного хостера; `states` восстановлены из самого раннего снапшота.
5. Проверить рейтинг в карточке лобби (`+N`/`0`/`-N`) и его обновление по
   `refreshInterval` (после фикса №2 — и снятие комнаты заблокированного
   хостера на «другом» мастере).
6. `npx eslint .` и `npm test` зелёные; добавить интеграционный тест из №1.
