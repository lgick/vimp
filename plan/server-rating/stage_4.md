# Этап 4. Аннулирование rank/skills при бане сервера ✅ выполнен

Цель: когда сервер (хостер) достигает `blockAt`, rank/skills, набранные на
этом сервере, аннулируются. Опирается на атрибуцию из этапа 1 и событие бана
из этапа 2.

## 4.1. Триггер

- В момент, когда `host_ratings.score <= blockAt` впервые (переход в
  `blocked=true`, этап 2), запустить аннулирование по `hoster_user_id`.
- Выполнять транзакционно на auth (единый источник профиля), не на мастере.

## 4.2. Откат rank (детерминированный)

- Пометить `rank_events.voided = true` для всех событий с этим
  `hoster_user_id` (по всем `game_id`, всем затронутым `user_id`).
- Пересчитать кэш `ratings.rank` = `SUM(delta) WHERE voided=false` для каждого
  задетого `(user_id, game_id)`.
- Идемпотентно: повторный бан того же хостера ничего не меняет (события уже
  `voided`).

## 4.3. Откат skills (решено: снапшот-восстановление)

Выбрано (MVP) — восстановление из снапшота:

- Для каждого `(user_id, game_id, session_id)` этого хостера взять
  `state_snapshots.state_before` и записать обратно в `states.state`.
- Если у игрока несколько сессий на баненном хостере — брать **самый ранний**
  снапшот (откат к состоянию до первого контакта с этим сервером).
- **Известное ограничение** (задокументировать): промежуточный честный
  прогресс на других серверах между сессиями может быть затёрт. Полное решение
  — обратимые дельты от игры (расширение SDK-контракта), вне MVP.
- Альтернативы, если снапшот-подход не подходит: (а) не откатывать skills,
  только rank; (б) обязать игру репортить дельты skills — тогда откат
  симметричен rank-леджеру, но требует нового поля в контракте плагина.

## 4.4. Файлы

- `packages/auth/src/UserRepository.js` — `voidHosterContributions(hosterUserId)`:
  транзакция `void rank_events` → `recomputeRank` → восстановление `states` из
  снапшотов.
- `packages/auth/src/main.js` — внутренний эндпоинт/вызов, дёргаемый при бане
  (аутентифицированный, только от мастера — не публичный).
- `packages/engine/src/master/*` — на переходе хостера в `blocked` вызвать
  аннулирование на auth.

## 4.5. Тесты

- После `void` rank задетых игроков падает ровно на сумму дельт баненного
  сервера; вклад других серверов не тронут.
- `states` возвращается к `state_before`; повторный вызов идемпотентен.
- Игрок без событий на баненном сервере не затронут.
- Мульти-сессия: берётся самый ранний снапшот.

## Готово, когда

Бан сервера детерминированно откатывает rank и (по выбранной стратегии) skills,
операция идемпотентна и транзакционна; `npx eslint .` и `npm test` зелёные.

## Реализация (отклонение от 4.4)

Триггер аннулирования сделан **внутри auth**, без отдельного внутреннего
эндпоинта и без вызова с мастера: `UserRepository._recomputeHostRating`
(вызывается из `voteHost`, `PUT /host-rating/:hosterUserId`) сравнивает
`blocked` до и после пересчёта и на первом переходе `false → true` сам вызывает
`voidHosterContributions(hosterUserId)`. Причина отклонения от файлового плана
4.4 — тот же самый запрос уже детерминирует переход в `blocked`; выносить это
на мастер потребовало бы нового внутреннего доверенного канала master→auth
(которого в кодовой базе пока нет ни для чего другого), ради вызова, который
и так синхронно происходит в теле того же HTTP-запроса на auth. `UserRepository.js`
остаётся единственным модулем, трогающим эти таблицы (см. `docs/en/auth.md`).

Аннулирование не обёрнуто в SQL `BEGIN`/`COMMIT` (этот класс нигде транзакции
не использует, в т.ч. `recomputeRank`/`upsertRank`) — вместо атомарности
используется идемпотентность каждого шага: `rank_events.voided` гасится один
раз, но пересчёт `ratings.rank`-кэша выполняется для **всех** когда-либо
задетых `(user, game)`, а не только тех, что изменил именно этот вызов —
поэтому повтор после сбоя на середине операции не пропускает пересчёт кэша.
Восстановление `states` берёт самый ранний снапшот заново при каждом вызове —
тоже no-op при повторе.

Тесты: `tests/auth/UserRepository.test.js` — переход в `blocked` запускает
аннулирование; повторная блокировка уже заблокированного хостера его не
повторяет; `voidHosterContributions` гасит только непогашенные события и
пересчитывает кэш для всех задетых пар; игрок без событий на баненном сервере
не затронут. Документация обновлена в `docs/en/auth.md` и `docs/ru/auth.md`.
`npx eslint .` чисто, `npm test` — 758/758 зелёных.
