# План: рейтинг серверов (`/like`·`/unlike`) + модель доверия игр + аннулирование rank/skills

Новое направление. Заменяет эфемерную соц-модерацию `/ban` на
идентичностный рейтинг хостеров и фиксирует модель доверия сторонних игр к
общему профилю пользователя (rank/skills).

## Контекст (что есть сейчас)

- **`/ban`** — `HostRegistry.report()` (`packages/engine/src/master/HostRegistry.js`):
  эфемерно, ключ репортёра — **IP**, порог `banThreshold=5` за окно
  `reportWindowMs=1 ч`, всё в памяти (`_bannedIps`), бан по IP, WS хоста
  закрывается кодом `4002`. Конфиг — `master.host.*` в
  `packages/engine/src/config/master.js`. Клиент шлёт `/ban <причина>` только
  как гость комнаты (`packages/engine/src/client/main.js`), причина обязательна.
- **Профиль**: auth-схема `ratings(user_id, game_id, rank)` — абсолютный rank
  через upsert; `states(user_id, game_id, state JSONB)` — скиллы. Записи **не
  привязаны к серверу**, поэтому откатить вклад конкретного сервера сейчас
  невозможно.
- **Rank-поток**: хост синхронизирует rank/state игрока через прокси мастера
  (`PlayerDataProxy`, `PUT /auth/rank`·`/state`) под Bearer самого игрока.
- **Лобби**: `GET /servers` (`HostRegistry._toPublic`) рейтинг не отдаёт.

## Зафиксированные решения

- **Пакеты (публичность)**: `@vimp/engine` (npm) и `vimp-engine-core`
  (crates.io) — **публичные**, это и есть SDK; `@vimp/auth` — **приватный
  сервис** (не пакет), секреты только в `.env`; плагины игр — на усмотрение
  автора (грузятся по URL), референс `@vimp/tanks` — публичный. См.
  [../README.md](../README.md).
- **Модель доверия игр к профилю**: писать rank/skills в общий профиль может
  **любая игра, присутствующая в каталоге мастера** (курируемый онбординг —
  `gameId` выдаёте вы, `config/master.js › games`). Каждая игра пишет **только
  в свой namespace** (`game_id`).
  - **rank** — общий формат для всех игр (единый integer-шаблон, рисуется на
    сайте мастера одинаково) → часть публичного SDK-контракта.
  - **skills** — приватный формат игры (произвольный JSONB `state`), движок в
    него не заглядывает; в SDK описан только механизм namespace, не поля.
  - Игра **никогда** не пишет ник/идентичность — они из JWT, не из игры.
- **Правила рейтинга сервера**: диапазон настраивается в движке (дефолт
  `[-10..+10]`), одинаково для всех игр; один голос на пользователя, мнение
  меняемо (`like`↔`unlike`); у верхней границы рейтинг не растёт дальше; на
  нижней границе (`blockAt`) сервер блокируется и хостеру запрещено создавать
  сервера; рейтинг виден в лобби.
- **Аннулирование**: rank/skills, набранные на сервере, достигшем бана,
  аннулируются.

## Решения по открытым вопросам (2026-07-26)

1. **Хранение репутации хостера и голосов** — **центрально в БД auth**
   (глобально для всех мастеров, персистентно; нужно и для аннулирования).
2. **Идентичность хостера** — **`userId` из JWT** при регистрации комнаты
   (не IP: иначе блокировка обходится сменой вкладки/IP).
3. **Откат skills** — **снапшот-восстановление** (`state_snapshots`, MVP).

Заделы на будущее (MVP не блокируют): отдельный per-game серверный ключ на
запись в профиль (сейчас доверяем мастеру — он валидирует `game_id` против
своего каталога) и обратимые дельты skills от игры вместо снапшотов.
