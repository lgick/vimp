### У1. Формат уникального ника гостя

Общее для обоих вариантов (решено, Р8): гостя в БД нет; номер гостя
`gid` берётся из Postgres `SEQUENCE guest_nick_seq` (`nextval` —
счётчик, не данные игрока) и переставляется обратимой перестановкой
(сеть Фейстеля с «прогулкой по циклу», cycle-walking) по домену формата,
поэтому ники строго уникальны и не идут подряд. Шаблон гостевого ника
**зарезервирован**: участник (passkey) не может выбрать такой ник при
смене, а гость, ставший участником, сохраняет свой (он уникален по
построению — последовательность его больше не выдаст).

- **A (рекомендуется): `Guest` + 9 символов `[0-9A-Z]`**, например
  `GuestK7Q2M9XA4` (14 символов — ровно `config.nick.maxLength`).
  Домен 36⁹ ≈ 1,0·10¹⁴ — не исчерпать ни ботами, ни временем; статус гостя
  виден по нику. Резерв: любой ник, начинающийся с `guest` без учёта
  регистра (`/^guest/i`).
- **B: «прилагательное + существительное + 4 цифры»**, например
  `BraveOtter0421` (≤ 14 символов: слова до 5 букв). Списки по 64 слова →
  64·64·10 000 ≈ 41 млн ников. Приятнее, но пространство исчерпаемо:
  нужен лимит выдачи по IP (этап 2 и так его вводит) и запасной формат по
  исчерпании (например `Player` + 8 символов). Резерв: точное совпадение
  с шаблоном «слово из списка + слово из списка + 4 цифры» без учёта
  регистра.

Затрагивает: `stage_1.md` → 1.4 (`lib/guestNick.js`), `stage_3.md` → 3.4
(запрет резервного шаблона при смене ника), доки `auth.md`.

### У2. Ник гостя между визитами

- **A (рекомендуется): хранится в браузере.** Гостевая сессия (`g_…`)
  лежит в `localStorage` (ключ `vimpSession`): тот же браузер видит тот
  же ник, пока хранилище не очищено; в БД ничего. Переход в другой
  браузер/профиль — другой гость.
- **B: новый ник на каждый визит.** Гостевая сессия — в `sessionStorage`
  (переживает перезагрузку вкладки, но не новую вкладку/запуск браузера).
  `sessionStorage`, а не просто память, обязателен: движок сам
  перезагружает вкладку (холодный промоушен преемника, переход по ссылке
  комнаты), и смена ника/`sub` при этом сломала бы
  `register_host { promotionToken }` (мастер сверяет `userId` кандидата).

Затрагивает: `stage_6.md` → 6.2 (`sessionStorageArea`) и 6.4 (хранилище
сессии в `LobbyAuthModel`).

### У3. Как часто гость проходит Turnstile перед созданием/входом на сервер

Механизм решён (этапы 2, 5, 6): после проверки Turnstile auth выдаёт
гостю сессию и JWT с claim `hvUntil` (секунды эпохи); мастер требует его
для `register_host` новой комнаты и нового `join_room`, хост — для входа в
матч. Вопрос только в сроке `config.turnstile.humanTtlMs`:

- **A (рекомендуется): 24 часа** (`86400000`). Дальше следующее
  создание/вход снова показывает виджет (в режиме managed обычно без
  клика). Идущий матч истечение не прерывает (переподключения, возврат
  после миграции, `TOKEN_REFRESH` — не «вход»).
- **B: перед каждым созданием/входом** — `humanTtlMs` ≈ 5 минут
  (`300000`: на сам вход с запасом), клиент запрашивает проверку перед
  каждым созданием и каждым переходом на сервер. Максимальная защита, но
  1–2 с задержки на каждое переключение сервера и быструю игру.
- **C: один раз на гостевую сессию** — `humanTtlMs = 0` трактуется как
  «бессрочно». Проще всего, но бот решает капчу один раз и дальше свободен.

Затрагивает: `stage_2.md` → 2.1, п. 4 (значение `humanTtlMs`),
`stage_6.md` → 6.5, п. 5 (когда показывать виджет).

## 0.2 Проверить внешние факты

Записать фактические значения в «Результат этапа 0».

1. **Версии `@simplewebauthn/server` и `@simplewebauthn/browser`**:
   `npm view @simplewebauthn/server version`,
   `npm view @simplewebauthn/browser version`. План написан под API
   v13 (`generateRegistrationOptions`, `verifyRegistrationResponse` →
   `registrationInfo.credential { id, publicKey, counter, transports }`,
   `generateAuthenticationOptions`, `verifyAuthenticationResponse({ credential })`;
   в браузере `startRegistration({ optionsJSON })`,
   `startAuthentication({ optionsJSON })`, `browserSupportsWebAuthn()`).
   Если мажорная версия другая — сверить сигнатуры по README пакета и
   поправить этапы 3 и 6 до кода.
2. **Тестовые ключи Cloudflare Turnstile** (документация Cloudflare,
   раздел «Testing»): ожидаются sitekey `1x00000000000000000000AA` (всегда
   проходит) и secret `1x0000000000000000000000000000000AA` (всегда
   проходит), а также ключи «всегда отказ» — для dev-умолчаний и тестов.
   Адрес проверки: `https://challenges.cloudflare.com/turnstile/v0/siteverify`
   (POST, `secret`, `response`, `remoteip`; ответ `{ success, hostname,
'error-codes' }`), скрипт виджета:
   `https://challenges.cloudflare.com/turnstile/v0/api.js?render=explicit`.
3. **CSP Turnstile**: какие источники нужны (ожидается `script-src` и
   `frame-src` `https://challenges.cloudflare.com`).
4. **Passkey на `https://localhost`**: rpId `localhost` для dev-контура
   (`https://localhost:3002`, mkcert) и виртуальный аутентификатор Chrome
   DevTools (WebAuthn panel) для ручной проверки.
