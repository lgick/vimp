## 1. 🔴 Пустой каталог игр насмерть ломает лобби

**Где**: `packages/engine/src/client/main.js:161-174`,
`packages/engine/src/client/lib/pickActiveGame.js:55`,
`packages/engine/src/client/main.js:1993`.

**Что происходит**. Модератор отклоняет или отключает последнюю игру
(`PATCH /admin/games/:id` со `status: 'disabled'`). Проход `GameSync` снимает
её с раздачи, `GET /games/manifest.json` отдаёт `[]`. Дальше на клиенте:

```js
activeGameManifest = pickActiveGame(gamesManifest, boot.gameId); // undefined
...
if (!activeGameManifest) {
  throw new Error('master has no games in its catalog');
}
} catch (e) {
  document.body.textContent = `Failed to load the game: ${e.message}`;
```

`document.body.textContent = …` **стирает всю разметку страницы** — вместе с
формой входа, `#lobby` и `#games-panel`. Дальше не работает ничего.

**Почему это проблема**. Это не «пустое лобби», это кирпич:

- сайт мёртв для всех, включая самого модератора;
- вернуть игру из интерфейса **нельзя**: панель модерации живёт в той самой
  разметке, которую только что стёрли, а поднимается она в `initLobby()`,
  до которого исполнение не доходит;
- единственный выход — `curl` в `PATCH /admin/games/:id` мимо интерфейса
  либо правка строки в БД руками;
- достаточно одного клика одного модератора, и никакого подтверждения на
  «вы отключаете последнюю игру платформы» нет;
- ровно тот же кирпич получится при штатном первом развёртывании платформы,
  пока в реестре нет ни одной одобренной игры: админ не сможет завести
  первую, потому что до формы заявки не доберётся.

Прошлое ревью (находка 10 плана `plugin-forward-compat`) уже проходило по
этому месту и добилось, чтобы **недоступная** игра оставалась в списке с
причиной, а не выкидывалась молча. Случай «список пуст» тогда остался
незакрытым, потому что каталог был статикой деплоя и пустым быть не мог.
С динамическим реестром он стал достижим из интерфейса.

**Как чинить**. Отсутствие игр — это состояние лобби, а не отказ загрузки.
Лобби обязано подниматься без активной игры: вход, бейдж пользователя,
«My games» и «Moderation» от игры не зависят вовсе, а зависят от неё только
форма создания комнаты и Leaderboard.

1. `client/main.js:164-166` — не бросать на пустом каталоге. Пустой массив
   отличается от «каталог непустой, но играбельного в нём нет»: второе
   `pickActiveGame` по-прежнему бросает своим сообщением, и это правильно.

```js
    // пустой каталог — состояние лобби, а не отказ загрузки: модератор
    // вправе отключить последнюю игру, и вернуть её он должен из той же
    // панели, а не через curl. Непустой каталог без играбельной строки —
    // по-прежнему ошибка (pickActiveGame бросает со своей причиной)
    if (activeGameManifest) {
      bindActiveGame(
        activeGameManifest,
        boot.clientPlugin ?? (await loadClientPlugin(activeGameManifest)),
      );
    }
```

2. `client/main.js:173` — заменить затирание `document.body` на текст в уже
   существующем контейнере ошибок лобби (`showLobbyError`) либо, если разметки
   ещё нет, на вставку `<div>` **перед** содержимым, а не вместо него. Стирать
   разметку страницы нельзя ни в одном сценарии: любая ошибка загрузки игры
   уносит вместе с собой и путь к её исправлению.

3. `client/main.js:1993` — `activeGameManifest?.id`: при пустом каталоге
   `selectActiveGame` вызывается из `join`/селектора первым же действием
   админа и упадёт на разыменовании `undefined`.

4. `initLobby()` (`client/main.js:2188-2189` и далее) — обойти
   game-зависимые шаги, когда активной игры нет:

```js
  populateGameSelect();

  if (activeGameManifest) {
    populateRoomForm(activeGameManifest);
    lobby.gameChanged(activeGameManifest.id, activeGameManifest.title);
  } else {
    // каталог платформы пуст: заявка и модерация — единственное, что
    // здесь можно делать, и именно они возвращают лобби к жизни
    showLobbyError('No games are published yet');
    hostBtn.disabled = true;
  }
```

   Выход из этого состояния уже написан и ничего нового не требует: админ
   жмёт «Test» → `games.publisher.on('staged')` → `registerGameManifest()` →
   `populateGameSelect()`, дальше `selectActiveGame(id)` привязывает плагин
   обычным путём. Одобрение игры даёт то же самое после перезагрузки вкладки.

5. Серверная страховка того же класса: `PATCH /admin/games/:id`, снимающий с
   раздачи последнюю игру, стоит сопроводить предупреждением в ответе
   (`{ game, warning: 'catalogEmpty' }`) и показать его в панели. Это не
   заменяет п. 1-4, но убирает удивление.

**Тесты**:

- `tests/client/pickActiveGame.test.js` — пустой массив возвращает
  `undefined` и **не** бросает (проверка уже есть — закрепить, что на неё
  опирается main);
- `tests/client/lobbyEmptyCatalog.test.js` (новый) — `initLobby` с пустым
  каталогом: `#lobby` виден, кнопка «Create server» выключена, `#games-panel`
  открывается, `document.body` не пуст;
- `tests/client/GamesCtrl.test.js` — `staged` при пустом каталоге доводит
  игру до селектора.

**Ручная проверка**: отключить в модерации все игры, перезагрузить вкладку,
убедиться, что виден вход и «Moderation», вернуть игру и убедиться, что
лобби ожило без правки БД.

## 2. 🟠 `npm pack --json` в npm 12 отдаёт объект — релиз игр падает

**Где**: `scripts/release/steps.js:469-484`, фикстура теста —
`tests/scripts/release/steps.test.js:28-30`.

**Что происходит**. Это ровно тот отказ, которым закончился прогон
`npm run release`:

```
[release] не разобрать вывод npm pack --json: Cannot read properties of undefined (reading 'files')
```

`checkTarball` разбирает вывод как массив:

```js
files = JSON.parse(stdout)[0].files.map(entry => entry.path);
```

В npm 12 (на машине — `npm 12.0.2`) форма ответа другая — объект, ключ
которого имя пакета:

```json
{ "@vimp-games/snakes": { "id": "…", "files": [ { "path": "LICENSE", … } ] } }
```

`JSON.parse(stdout)[0]` — `undefined`, `.files` — `TypeError`. Проверено
прямым запуском `npm pack --dry-run --json --ignore-scripts` в
`/Users/dmitry/Sites/my/vimp-snakes`.

**Почему тесты этого не поймали**. Фикстура сама воспроизводит устаревшую
форму:

```js
function packJson(files) {
  return JSON.stringify([{ files: files.map(file => ({ path: file })) }]);
}
```

Тест зелёный и при этом ложный: он подтверждает разбор формы, которой npm
больше не отдаёт. Это второй дефект — важнее первого, потому что он же
пропустит и следующую смену формата.

**Как чинить** — принять обе формы и не гадать по индексу:

```js
  let files;

  try {
    const parsed = JSON.parse(stdout);
    // npm ≤ 11 отдавал массив пакетов, npm ≥ 12 — объект «имя → пакет».
    // Пакет здесь ровно один (npm pack в каталоге игры), поэтому берём
    // первую запись любой из форм, а не индекс
    const entry = Array.isArray(parsed) ? parsed[0] : Object.values(parsed ?? {})[0];

    if (!entry || !Array.isArray(entry.files)) {
      throw new Error('в ответе нет списка files');
    }

    files = entry.files.map(item => item.path);
  } catch (error) {
    throw new Error(`не разобрать вывод npm pack --json: ${error.message}`);
  }
```

`!entry || !Array.isArray(entry.files)` обязателен: без него третья форма
ответа даст то же невнятное `Cannot read properties of undefined`, ради
которого этот блок и переписывается.

**Тесты** — `tests/scripts/release/steps.test.js`:

- `packJson` перевести на форму npm 12 (объект), добавить `packJsonLegacy`
  со старой формой; прогнать существующие четыре кейса по обеим формам
  (`describe.each`);
- новый кейс: `{}` (пустой объект) и `[]` — внятный отказ со словами
  `npm pack --json`, а не `TypeError`.

## 3. 🟠 Публикация игры всё ещё тянет за собой пуш в прод

**Где**: `scripts/release/plan.js:145-151`, `scripts/release.js:643`,
`scripts/release/steps.js:620-700` (`rollOutProduction`).

**Что происходит**. В плане релиза стоит строка

```
  прод (push в main)  да        —      опубликованы игры → нужен перепин
```

потому что

```js
    prod: {
      push: engine.publish || publishedGames.length > 0,
      reason: engine.publish ? 'опубликован движок'
        : publishedGames.length > 0 ? 'опубликованы игры → нужен перепин'
        : 'публиковать нечего',
```

Перепинивать больше нечего. После этапа 5 `master-game-registry` пинов игр в
репозитории движка не осталось вовсе:

- `package.json` корня — ни одной зависимости `@vimp-games/*` (проверено);
- `packages/create-vimp-game/src/versions.generated.json` — только
  `{"engine": …, "core": …}`;
- сам `rollOutProduction` уже это знает и печатает
  «игры больше не пинятся в package.json».

То есть при релизе одних только игр `writePinSnapshot` не меняет ни байта,
`commit()` честно говорит «коммитить нечего», `git push` не имеет что
пушить — и всё это после подтверждения «Пуш в main — это ДЕПЛОЙ прода».
Причина в плане при этом утверждает обратное: что перепин нужен.

**Почему это проблема**: не порча данных, а неверный план. Разработчик
читает «нужен перепин» и соглашается на «деплой прода» там, где деплоя нет;
в обратную сторону — привыкает подтверждать этот шаг не глядя, и настоящий
деплой движка проедет так же машинально. Плюс лишние `npm test` и
подтверждение в каждом релизе игры.

**Как чинить**. Разделить два разных смысла шага C: «пуш в main» (деплой
движка) и «проверка выпущенных игр» (`simGame(strict)` — она нужна и когда
пуша нет: подтверждает, что опубликованная версия игры работает с текущим
движком).

1. `plan.js:145-151`:

```js
    prod: {
      // игры едут в прод через реестр auth-сервиса, а не через образ:
      // публикация игры не меняет в этом репозитории ни файла, и пуш в main
      // был бы деплоем без изменений
      push: engine.publish,
      // но проверить выпущенную игру против текущего движка всё равно надо
      verifyGames: publishedGames.length > 0,
      reason: engine.publish
        ? 'опубликован движок'
        : publishedGames.length > 0
          ? 'игры едут через реестр — деплой не нужен, только проверка sim'
          : 'публиковать нечего',
```

2. `release.js:643` — запускать шаг при `decision.prod.push ||
   decision.prod.verifyGames`; в `rollOutProduction` при `push === false`
   пройти `simGame(…, {strict: true})` по опубликованным играм и выйти без
   `writePinSnapshot`, `commit` и подтверждения пуша.

3. Строку таблицы плана переименовать: «прод (push в main)» на «прод» с
   значением «нет (только sim)», чтобы «да/нет» отвечало на вопрос о деплое.

**Тесты** — `tests/scripts/release/plan.test.js` и `steps.test.js`:

- план с публикацией только игр: `prod.push === false`,
  `prod.verifyGames === true`, причина без слова «перепин»;
- план с публикацией движка: `prod.push === true` (регрессия);
- `rollOutProduction` при `push: false` не зовёт `git push` и не спрашивает
  подтверждения, но зовёт `simGame` по каждой игре.

**Документация**: `docs/en/publishing.md` и `docs/ru/publishing.md`, раздел
про шаг C — дописать, что релиз одних игр деплоя не делает.

## 4. 🟠 `moderatorNick` поехал автору игры

**Где**: `packages/auth/src/UserRepository.js:139-142` (`GAME_FIELDS`),
`:780-789` (`listGamesByAuthor`), маршрут `GET /games/mine` —
`packages/auth/src/main.js:350`; и `POST /games/:id/version` — `:434`.

**Что происходит**. Правка §6 расширила общий список колонок:

```js
const GAME_FIELDS = `g.*, a.nick AS author_nick, m.nick AS moderator_nick`;
```

`GAME_FIELDS` используют **все** выборки полной строки, включая
`listGamesByAuthor`. Раньше `moderator_nick` там не выбирался и `mapGame`
отдавал `moderatorNick: null`; теперь `GET /games/mine` и ответ
`POST /games/:id/version` отдают обычному разработчику ник модератора,
отклонившего его заявку.

**Почему это проблема**. Дело не в утечке секрета — ники и так публичны в
лобби, — а в том, что это **новая связка**: «эту заявку зарубил вот этот
человек». Модерация до сих пор была анонимной со стороны автора: ему
адресован `moderatorNote`, а не личность. Персональная адресация отказа —
это про травлю модераторов, и вводить её надо осознанно, а не побочным
эффектом рефакторинга SQL. Тем более что соседний комментарий в этом же
коммите прямо называет ник модератора внутренней перепиской:

> публичная выборка (`mapPublicGame`) джойнит только автора: ник модератора —
> внутренняя переписка модерации

То есть код сам себе противоречит: наружу через `GET /games` не пускает, а
автору через `GET /games/mine` отдаёт.

**Как чинить** — решение продуктовое, обе ветки дешёвые.

*Вариант A (рекомендую)* — автору ник модератора не показывать. Дописать
третью проекцию нельзя (их и так две), поэтому убрать поле на границе
маршрута, где смысл читается:

```js
// packages/auth/src/main.js
// автору адресовано замечание, а не личность модератора: персональная
// адресация отказа — отдельное продуктовое решение, а не побочный эффект
// общей проекции строки
const forAuthor = ({ moderatorNick, ...game }) => game;

app.get('/games/mine', requireAuth, async (req, res) => {
  res.json({ games: (await userRepo.listGamesByAuthor(req.user.id)).map(forAuthor) });
});
```

и тот же `forAuthor` — на ответ `POST /games/:id/version`, когда вызывающий
не админ (`isAdminUser` там уже вычисляется).

*Вариант B* — оставить как есть, но тогда это осознанная функция: снять
противоречащий комментарий у `PUBLIC_GAME_FIELDS`, дописать `moderatorNick`
в строку `GET /games/mine` в `docs/en/auth.md:259` и `docs/ru/auth.md:259`
(сейчас там перечислены только `status`, `pendingVersion`, `moderatorNote`) и
показать ник в панели «My games» — иначе поле едет по сети и не используется.

**Тест** — `tests/auth/mainGames.test.js` (или где проверяются маршруты
реестра): `GET /games/mine` отдаёт строку **без** `moderatorNick`, а
`GET /admin/games` — с ним.

## 5. 🟡 «Test» раздаваемой версии локально прилинкованной игры сносится тем же тиком

**Где**: `packages/engine/src/master/GameSync.js:117-124` и `:189-200`
(`_dropStaged`), `packages/engine/src/master/gameRoutes.js:204`.

**Что происходит**. `_dropStaged` снимает черновик, чью версию реестр уже
раздаёт. Для игры из реестра это верно. Для локально прилинкованной игры —
нет: раздаётся у неё сборка из `node_modules`, а `game.version` реестра
описывает совсем другой артефакт — тот, что лежит в npm.

Сценарий, который от этого ломается, — штатный dev-контур:

1. `tanks` прилинкован, в реестре одобрена версия `0.16.1`, `pendingVersion`
   пуст;
2. админ жмёт «Test» на `tanks`; `gameRoutes.stage` берёт
   `wanted = version ?? game.pendingVersion ?? game.version` → `0.16.1`;
3. пакет качается, попадает в каталог черновиком, в селекторе появляется
   `Tanks (test)`;
4. ближайший тик `GameSync` (≤ 60 с) видит локальную игру, зовёт
   `_dropStaged('tanks', '0.16.1')` — версии совпали, черновик снят;
5. следующий `_prune` уносит `.games/tanks/0.16.1/` с диска.

То есть **сравнить опубликованную в npm сборку с локальной прилинкованной
нельзя** — а это ровно то, ради чего «Test» в dev и нужен. Это остаток
находки §1: там закрыли черновик *заявленной* версии, здесь остался черновик
*раздаваемой*.

**Как чинить**. Признак «черновик больше не нужен» — не совпадение номера
npm-версии, а совпадение **артефакта**: раздаваемая запись и черновик — один
и тот же код. Хеш сборки для этого уже есть, и каталог уже сверяет ровно его
в `isStaged()` (`GameCatalog.js:233-258`) — там по той же причине: «одна и та
же сборка может быть опубликована под двумя npm-версиями».

```js
  // черновик снимается, только когда раздаваемая запись — ТОТ ЖЕ артефакт:
  // сверка по manifest.version (хеш сборки), а не по номеру npm-версии.
  // У локально прилинкованной игры раздаётся сборка из node_modules, и
  // совпадение номеров о ней ничего не говорит — сравнение этих двух сборок
  // и есть смысл «Теста» в dev
  _dropStaged(id) {
    const activeHash = this._catalog.getManifest(id)?.version;

    if (!activeHash) {
      return;
    }

    for (const staged of this._catalog.stagedManifests()) {
      if (staged.id === id && staged.manifest.version === activeHash) {
        this._catalog.remove(id, staged.version);
      }
    }
  }
```

`rebaseManifest` поле `version` не трогает (`rebaseManifest.js:41-49`), а
`_toDevManifest` подменяет только `entries` — то есть хеш сравним между
записью из `node_modules` и записью, скачанной из npm. Вызов остаётся там же,
в ветке локальной игры, и аргумент `version` из него уходит.

Что это даёт:

- разработчик опубликовал игру из того же прилинкованного репозитория —
  `dist/` тот же, хеш совпал, черновик снят автоматически (то, ради чего
  `_dropStaged` и писался);
- сборки разные — черновик остаётся, и «Test» делает то, что обещает;
- для игры ИЗ РЕЕСТРА поведение не меняется: там совпадение версии и так
  разрешается через `catalog.upsert({active: true})`, который перезаписывает
  ту же запись и делает её активной, — черновиком она после этого быть
  перестаёт по определению `stagedManifests()`.

**Тест** — `tests/master/GameSync.test.js`. Два существующих кейса
(«черновик локальной игры снимается, когда реестр раздаёт ту же версию» и
«…с другой версией остаётся») переписываются на хеш; стаб `makeCatalog()`
получает `getManifest`. Что проверять:

- совпал хеш сборки → `catalog.remove(id, stagedVersion)` вызван;
- номера npm-версий совпали, а хеши разные → `remove` **не** вызван (это и
  есть сломанный сегодня сценарий);
- активной записи нет вовсе (`getManifest` → `undefined`) → `remove` не
  вызван, ничего не бросается.

## 6. 🟡 `gameStatic.js` не описан в документации

**Где**: `docs/en/master.md:47-53` и `docs/ru/master.md:34-40` (таблица
модулей), `docs/en/master.md:185-206` (раздел про версионное URL-пространство)
и зеркало в `docs/ru/master.md`.

**Что происходит**. Коммит завёл новый модуль мастера
`packages/engine/src/master/gameStatic.js` и изменил наблюдаемый контракт
`/games/…`, но ни того, ни другого в документации нет:

- в таблице модулей `master.md` перечислены `GameStore.js`, `GameSync.js`,
  `gameRoutes.js`, `rebaseManifest.js` — `gameStatic.js` пропущен;
- раздел «Versioned URL space» по-прежнему говорит только, что сегмент,
  не похожий на версию, уходит статике; про то, что **промах по версионному
  пути теперь отвечает `404 JSON`**, а не проваливается в html-фолбэк, не
  сказано ни слова.

Это нарушение правила CLAUDE.md («any functional change updates both matching
pages in the same change») — то же, что находка 9 прошлого ревью. Контракт
404 при этом внешний: на него завязан `import()` клиентского бандла, и
именно его непонятность стоила полчаса отладки в §2 dev-fixes.

**Как чинить** — две правки в четырёх файлах (`en` + `ru`):

1. Строка таблицы модулей после `gameRoutes.js`:

> `packages/engine/src/master/gameStatic.js` — раздача `dist/` игр по
> `/games/<id>[/<version>]/…`: кэш инстансов `express.static` по директории
> версии (снятая с диска версия уносит свой маунт через `GameSync.onPruned`),
> 404 на промахе версионного пути и `next()` на неверсионном. Отдельный
> модуль, потому что `lobby.js` поднимает сервер и из тестов не импортируется.

2. Абзац в «Versioned URL space» / «Версионное URL-пространство»:

> Промах по `/games/<id>/<version>/…` — неизвестная игра, неизвестная версия
> или отсутствующий файл — отвечает `404 {"error": "unknownGame"}` либо
> `404 {"error": "notFound"}`. Провалиться в html-фолбэк такой путь не может
> по построению: он адресует хранилище пакетов и ничего больше, а `200
> text/html` на месте бандла превращает «файла нет» в невнятный отказ
> `import()`. Не-`GET`/`HEAD` запрос уходит дальше по цепочке: `serve-static`
> его не смотрит, и «файла нет» про него неизвестно. Неверсионный путь
> (`/games/<id>/…`) по-прежнему уходит `next()` — в dev это выход на
> Vite-исходники прилинкованной игры.

## 7. 🟡 Мелочи

**7.1 `clearForm` падает на отсутствующем поле.**
`packages/engine/src/client/components/view/Games.js:120-125`: `this._fields`
собирается через `document.getElementById(id)` и может содержать `null`, если
в `games.pug` переименуют элемент. `field.value = ''` тогда бросит внутри
обработчика события модели. Дёшево закрыть: `this._fields.forEach(field => {
if (field) { field.value = ''; } })` — либо, честнее, проверить полноту карты
один раз в конструкторе и упасть там с внятным сообщением.

**7.2 Черновики выведены из-под потолка `keep` без верхней границы.**
`packages/engine/src/master/GameSync.js:236` — `if (staged || keep.get(id).size
< this._keepVersions)`. Сегодня «один черновик на игру» держит роут `stage`
(`gameRoutes.js:218-222`), и это единственное, что ограничивает рост. Инвариант
стоит закрепить там, где он используется: комментарий в `_prune` уже ссылается
на «черновик», единственное число — стоит добавить, что источник ограничения —
`stage`, иначе следующая правка роута тихо снимет потолок с диска.

**7.3 Абзац в `publishing.md` не переразбит после правки.**
`docs/ru/publishing.md:484` (86 символов) и `docs/en/publishing.md:491`
(85 символов) выбиваются из своего же блока-цитаты, где остальные строки
уложены в 63-78: подписи стали длиннее («Обновить» → «Update version»), а
абзац переразбили только наполовину. Перевернуть оба абзаца целиком.

**7.4 Тест-фикстура `packJson`** — см. находку 2: устаревшая форма ответа в
фикстуре сделала зелёный тест ложным. Это отдельная привычка, а не разовая
опечатка: фикстуру внешнего инструмента стоит снимать с живого вывода и
подписывать версией инструмента, для которой она снята.

## Ответы на вопросы из постановки

### 1. ✅ выполнен — Опция `GAMES_MATRIX` больше не нужна? И почему не писать пакет в `SERVERS_MATRIX`?

**Реализовано** отдельным заходом (рабочее дерево, коммита нет). Итог
разошёлся с первым разбором в этом файле — ниже он исправлен.

**`GAMES_MATRIX` удалена целиком.** Из деплоя её убрал ещё этап 5
(`.github/workflows/deploy.yml` её не знает), а теперь снято и чтение в
движке: `config/env.js`, `master/localGames.js`, `master/lobby.js`,
`config/master.js`. Обе роли, которыми переменную оправдывали, отпали:

- «статический каталог для self-hosted мастера без реестра» — такого
  сценария нет: лобби-мастер без auth-сервиса не работает вовсе (вход,
  `JwksProxy`, `PlayerDataProxy`, `GameRegistryProxy`), а реестр приезжает
  вместе с тем же auth-сервисом. Игры живут в его Postgres, заводятся
  интерфейсом; пустая БД — пустое лобби, и это законное состояние;
- «выключатель автообнаружения в dev» — он и был дефектом: `applyLocalGames`
  при заданной переменной молча не трогал каталог, давая «правлю игру, а
  едет другая». Вдобавок игра из `GAMES_MATRIX` не попадала в
  `localGameIds`, и `GameSync` всё равно перекрывал её записью реестра —
  переменная не делала даже того, что обещала.

`master:games` остался массивом конфига: его наполняет автообнаружение в dev
и читает dedicated-сервер.

**`dedicatedGame` теперь принимает имя пакета** — ровно как в вопросе.
Поддержаны обе формы: `"tanks"`, `"@vimp-games/tanks"` и любая из них с пином
`@<version>`.

**Поправка к первому разбору.** Утверждение «`@vimp-games/tanks` без пина
молча станет id целиком» верно фактически, но вывод из него был неверен:
`parseGameRef` устроен именно так намеренно (`lastIndexOf('@')` с guard'ом
`at <= 0`), и scoped-имя он разбирает правильно. Разбор менять не пришлось —
ломался **резолв**: `ref.id` искался только по `game.id`/`row.id`,
промахивался и уходил в `catalog.upsert({id: '@vimp-games/tanks'})`, то есть
имя пакета со слешем становилось сегментом URL раздачи. Отказа при этом не
было — был тихо битый каталог. Это чинится тем же изменением: id всегда
берётся из разрешённого пакета или строки реестра.

Возражения 2 и 3 первого разбора (id — ключ реестра и сегмент URL; игра может
сменить пакет, не меняя id) остаются в силе и как раз поэтому обе формы
разрешаются **в id**, а не подставляются в каталог как есть.

Порядок разрешения (`resolveLocalRef` в `dedicated/main.js`): `master:games`
по id → `master:games` по пакету → манифест пакета в `node_modules` (любой
скоуп, реестр не нужен) → реестр по `id` **или** `packageName`.

Итого в матрице: `{"ip": …, "domain": "tanks.lgick.dev", "dedicatedGame":
"@vimp-games/tanks"}`. Документация правлена в обеих ветках
(`configuration.md`, `dedicated.md`, `deployment.md`, `master.md`), журнал —
`### ⚠️ Breaking` + `### Migration` + `### Added` в `[Unreleased]`
`packages/engine/CHANGELOG.md` (minor, `0.25.0 → 0.26.0`).

### 2. Если модератор уберёт все игры, сайт отдаёт «Failed to load the game»

Подтверждено и разобрано — [находка 1](#1). Дефект серьёзнее, чем выглядит:
страница не просто пустеет, а **стирает свою разметку**, поэтому вернуть игру
из панели модерации нельзя — модератор запирает сам себя.

### 3. `npm run release` падает на разборе `npm pack --json`

Подтверждено и воспроизведено — [находка 2](#2): npm 12 сменил форму ответа
с массива на объект «имя пакета → пакет». Фикстура теста воспроизводит старую
форму, поэтому падение и не поймалось.

Второй половине вопроса — «раньше после публикации игр требовалось обновлять
прод, теперь не требуется» — посвящена [находка 3](#3): скрипт с этим ещё не
согласился и по-прежнему просит пуш в main с причиной «нужен перепин», хотя
перепинивать нечего.
