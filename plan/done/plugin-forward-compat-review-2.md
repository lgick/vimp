### 1. `requires` продублирован в трёх местах, и ни одна проверка их не сверяет — СРЕДНЯЯ — ✅ выполнен

`packages/create-vimp-game/templates/default/src/{host,client}/index.js`,
`vimp-snakes/scripts/build-game-manifest.js:158`,
`packages/engine/src/lib/loadGamePackage.js:assertPluginMatchesManifest`

Правка находки 3 прошлого ревью объявила `requires` необязательным полем
**обеих половин плагина** и добавила `requires: []` в шаблон. Но список
возможностей теперь живёт в трёх независимых местах одного пакета игры:
`build-game-manifest.js` (→ `dist/manifest.json`), `HostPlugin.requires`,
`ClientPlugin.requires`. Расхождение между ними не ловит ничто.

И оно уже произошло — в **опубликованной** игре:

```
node_modules/@vimp-games/snakes/dist/manifest.json → requires: ["accolades"]
vimp-snakes/src/host/index.js                       → поля нет
vimp-snakes/src/client/index.js                     → поля нет
```

То есть практическое следствие, ради которого находку 3 и заводили,
осталось невылеченным дословно: `snakes`, поднятая через standalone SDK
(`npm run dev` в репозитории игры) на движке без порта 18, по-прежнему
получает `requires: []`, вердикт `{ok: true}` и тихо недоиграет вместо
честного отказа. Движок починен, шаблон починен — игра нет.

Прецедент проверки в движке уже есть и стоит ровно там, где нужно:
`assertPluginMatchesManifest` сверяет `engineApi` манифеста с обеими
половинами и падает с текстом «stale dist/». `requires` — поле того же
класса и той же природы (собирается той же сборкой), но проверки не
получило.

**Решение**

1. `src/lib/loadGamePackage.js` — расширить `assertPluginMatchesManifest`:
   множество `manifest.requires` обязано совпадать с объединением
   `host.requires ∪ client.requires`. Текст отказа — тот же «stale dist/»:
   это рассинхрон сборки внутри пакета, а не отказ по возрасту (И4 не
   нарушается — половина без поля читается как `[]`, и игра, у которой
   пусто везде, проходит как раньше).
2. Правило контракта B2 — то же сравнение статически, чтобы разработчик
   игры узнавал о расхождении на `vimp-contract`, а не на первом
   solo-прогоне. B2 уже читает `ctx.manifest.requires`, половины доступны
   ему через `ctx.hostPlugin`/`ctx.clientPlugin` (их читает C10).
3. `vimp-snakes` — добавить `requires: ['accolades']` в обе половины рядом
   с `engineApi`, с тем же комментарием, что уже стоит в
   `build-game-manifest.js`. Это `Fixed`/`Changed` в журнале игры, не
   в движковом.
4. Тесты: `tests/lib/loadGamePackage.test.js` — манифест с `requires`
   и половина без него → отказ; `tests/devtools/contract/rules.test.js` —
   то же для B2.

### 2. Строка в `plugin.requires` снова итерируется посимвольно — СРЕДНЯЯ — ✅ выполнен

`packages/engine/src/standalone/index.js:72-77`

```js
requireCompatible({
  id: hostPlugin.id,
  requires: requires ?? [
    ...(hostPlugin.requires ?? []),
    ...(clientPlugin.requires ?? []),
  ],
});
```

Это ровно тот дефект, который находка 2 прошлого прохода вылечила в
`checkPluginCompatibility` и в правиле B2 («строка проитерируется
посимвольно»), — и он вернулся здесь же, в правке находки 3. Спред строки
даёт массив символов, каждый символ — валидная строка, поэтому проверка
формы внутри `checkPluginCompatibility` его пропускает. Воспроизведено на
живом модуле:

```
hostPlugin.requires = 'accolades'
→ ok:false, missing: ['a','c','c','o','l','a','d','e','s'],
  text: '… does not have: a, c, c, o, l, a, d, e, s — update the engine'
```

Разработчик встраивания, написавший `requires: 'accolades'` вместо массива
(естественная опечатка для поля, которого в его игре раньше не было),
получает вместо внятного «должен быть массив» бессмысленный список букв.
Объект (`requires: {}`) даёт `TypeError: not iterable` прямо из
`startStandaloneGame` — то есть краш, а не вердикт.

**Решение**: не спредить недоверенное значение. Нормализовать одной
функцией рядом с `checkPluginCompatibility` (её же и переиспользовать):

```js
// в lib/gamePlugin.js, рядом с checkPluginCompatibility
export function mergeRequires(...sources) {
  for (const src of sources) {
    if (src !== undefined && src !== null && !Array.isArray(src)) {
      return src; // вернуть КАК ЕСТЬ: форму осудит checkPluginCompatibility
    }
  }

  return sources.flatMap(src => src ?? []);
}
```

и звать `requires: requires ?? mergeRequires(hostPlugin.requires,
clientPlugin.requires)`. Тогда битая форма доезжает до единственной точки,
которая умеет о ней говорить, и отвечает вердиктом `bad-manifest`, а не
буквами и не `TypeError`.

Тест — `tests/standalone/startStandaloneGame.test.js`: половина с
`requires: 'accolades'` и с `requires: {}` даёт отказ с текстом про массив.

### 3. Алиас опкода резолвится не в ту сторону — СРЕДНЯЯ (недостижима сегодня) — ✅ выполнен

`packages/engine/src/lib/coreAbi.js:dispatchCoreOp`,
`packages/engine/src/config/abiOps.js`

```js
const resolved = abiOps.resolve(op);

if (!abi.ops.includes(resolved)) {
  return NOT_HANDLED;
}
```

Реестр `createRegistry` спроектирован под одно направление: **имя пишет
игра, движок резолвит его вперёд, в активное**. Так работают `formControls`
(игра написала `segmented` — движок строит `radio`), `clientServices`,
`capabilities`. Для опкодов направление обратное: имя пишет **движок**, а
понимать его должно **уже опубликованное ядро**, которое старше движка.

Отсюда: пусть `debug.json` однажды выведен алиасом на `debug.dump`.
`resolve('debug.json')` вернёт `debug.dump`; ядро, собранное сегодня,
объявляет в `abi_describe` только `debug.json`, — `includes` не совпадёт, и
движок решит, что ядро опкода не знает. Возможность молча теряется ровно на
тех ядрах, ради которых весь план и писался. Для `debug.json` есть запасной
путь (замороженный `debug_json`), поэтому цена сегодня нулевая; для
опкода-команды, у которого запасного пути по определению нет, — это тихая
потеря функциональности на старой игре.

Реестр заведён именно ради того, чтобы алиасы появились (так сказано в
шапке `abiOps.js`), так что путь достижим ровно в тот день, когда механизм
впервые применят.

**Решение** (одно из двух, но выбрать сознательно):

1. Пробовать **всю цепочку**, от активного имени к выведенным: у реестра
   уже есть `chain(value)`, дающий `[{value:'debug.json'}, {value:'debug.dump'}]`.
   ```js
   const names = abiOps.chain(op).map(entry => entry.value).reverse();
   const known = names.find(name => abi.ops.includes(name));

   if (known === undefined) {
     return NOT_HANDLED;
   }

   const out = core.dispatch(known, payload);
   ```
   Активное имя пробуется первым, выведенное — как запасной путь для старого
   ядра. Это и есть И1 применительно к оси wasm.
2. Либо признать, что алиасов у опкодов не бывает, и закрыть путь
   механически: `createRegistry` вызывать с флагом «алиасы запрещены», а в
   `abiOps.js` записать почему (новая форма опкода = новое имя, старое имя
   продолжает обрабатываться ядром). Тогда `resolve` из `dispatchCoreOp`
   убрать — сейчас он создаёт видимость поддержки, которой нет.

Тест — `tests/lib/coreAbi.test.js` с временным алиасом в реестре: ядро,
объявившее ТОЛЬКО выведенное имя, обслуживается (вариант 1) либо реестр
падает на загрузке (вариант 2).

### 4. `dispatchCoreOp` доверяет ответу `dispatch`, хотя весь модуль — про недоверие — НИЗКАЯ — ✅ выполнен

`packages/engine/src/lib/coreAbi.js`

`readCoreAbi` нормализует всё: нет метода, не-JSON, `ops` не массив, элементы
не строки. Соседняя функция в том же файле берёт результат ядра как есть:

```js
const out = core.dispatch(resolved, payload);

if (out.length === 0) { … }
```

Ядро, у которого `abi_describe` есть, а `dispatch` нет (ручное раскрытие
макроса в игре, обрезанная сборка, мок в тесте игры), даёт
`TypeError: core.dispatch is not a function`; ядро, вернувшее `undefined`
или строку, — `TypeError` на `.length` либо `bytes` в виде строки дальше по
коду. Точка отказа — конструктор `GameCoreAdapter` или обработчик
`PS_CONFIG_DATA`, то есть ровно те два места, которые находка 7 прошлого
прохода и закрывала от «получатель падает от того, что отправитель другой».

**Решение**: та же дисциплина, что у `readCoreAbi` — feature-detect и
проверка формы ответа:

```js
if (typeof core?.dispatch !== 'function') {
  return NOT_HANDLED;
}

const out = core.dispatch(resolved, payload);

if (!(out instanceof Uint8Array) || out.length === 0) {
  return NOT_HANDLED;
}
```

Тест — `tests/lib/coreAbi.test.js`: ядро без `dispatch`, ядро с
`dispatch → undefined`, ядро с `dispatch → 'строка'`.

### 5. Числовое поле хост проверяет диапазоном, но не `regExp` — НИЗКАЯ — ✅ выполнен

`packages/engine/src/lib/validators.js:numericError`,
`packages/engine/src/client/lib/formBuilder.js:validateField`

Клиент у числового поля проверяет **и** диапазон, **и** `regExp` — причём
собственный комментарий объясняет, зачем оба: «ловит то, что диапазон
пропускает (дробное, ведущий ноль)». Хост в ветке `isNumericControl`
проверяет только `min`/`max` и уходит по `continue`.

Значит поле `{control: 'number', min: 1, max: 8, regExp: '^([1-8])$'}` от
клиента, обошедшего форму, принимает `3.5` и `1e0` — форма их отбивает.
Это не дыра (диапазон соблюдён), но это ровно то расхождение
«клиент разрешает не то, что хост», которое модуль объявляет своим
инвариантом.

**Решение**: в `numericError` после проверки диапазона применять `regExp` к
строковому представлению значения в единице отображения — тем же
`matchesPattern`, что и текстовая ветка. Тест — `tests/lib/validators.test.js`:
`3.5` при `min:1,max:8,regExp:'^([1-8])$'` отвергается так же, как на клиенте.

### 6. `source`-поле в `authSchema` хост не проверяет вовсе — НИЗКАЯ — ✅ выполнен

`packages/engine/src/lib/validators.js:isDeclaredOption` (условие
`!options.source`), `src/client/components/view/Auth.js:83`

Auth-форма строится с **пустым** `ctx` (`buildForm(descriptors, container, {}, …)`),
поэтому `source`-поле у игрока резолвится в пустой список и получает
`'no options available'` — заполнить его нельзя. Хост же такое поле
пропускает целиком: `!options.source` снимает проверку членства, а никакой
другой у select/radio нет.

Итог: честный игрок войти не может, клиент с поднятым сокетом отправляет в
поле произвольную строку. Это буквальная инверсия инварианта модуля
(«клиент, обошедший форму, не должен получать больше прав, чем клиент, её
заполнивший»), просто с другой стороны, чем находка 1 прошлого прохода.

**Решение**: `source` в `authSchema` — дефект схемы, а не режим работы.
Правило C10 обязано его отвергать (`authSchema` строится без `ctx.sources`,
и никакого источника вариантов у неё быть не может), а `validateAuth` —
отвечать `'not an option'` вместо пропуска. Тесты — `rules.test.js` и
`validators.test.js`.

### 7. Неизвестное имя `control` на хосте почти не проверяется — НИЗКАЯ — ✅ выполнен

`packages/engine/src/lib/validators.js`

`resolveDescriptor` для неизвестного имени возвращает дескриптор как есть
(«последнее скажет билдер»). На хосте билдера нет: `isTextControl` false,
`OPTION_CONTROLS` не совпал — остаётся только `MAX_FIELD_LENGTH` и игровой
валидатор. Поле с `control: 'megaslider'` (игра из будущего, опечатка в
схеме) уезжает в игру недовалидированным.

У честного клиента такое поле не строится вовсе (`buildForm` его
пропускает с `console.error`), значит ключ в сабмит не попадает и хост
отвечает `Property is missing` — то есть поведение уже расходится в пользу
обошедшего форму.

**Решение**: `validateAuth` отвергает поле, чей `control` не резолвится
реестром (`formControls.has === false`), с ошибкой `'unknown control'` — тем
же приговором, который выносит билдер. C10 ловит это раньше и остаётся
основным контуром, `validateAuth` — последним. Тест —
`tests/lib/validators.test.js`.

### 8. Крейт опубликован версией без записи в журнале — НИЗКАЯ (процесс) — ✅ выполнен

`packages/engine/core/Cargo.toml:3` (`version = "0.9.1"`),
`packages/engine/core/CHANGELOG.md`

Тег `vimp-engine-core@0.9.1` существует, версия в `Cargo.toml` — `0.9.1`,
а последняя секция журнала — `## [0.9.0]`. Секции `[0.9.1]` нет.

Правило `CLAUDE.md`: «**подзаголовок задаёт уровень релиза** — единственное
место, где он записан». Опубликованная версия, которой в журнале нет,
нарушает его буквально: по журналу нельзя ответить, что уехало в 0.9.1
(фактически — перестановка doc-комментария из находки 10, изменение
поведения нулевое). Игры при этом обязаны поднять пин руками
(предупреждение в шапке того же файла), и разработчику игры негде прочитать,
ради чего.

**Решение**: добавить `## [0.9.1]` с `### Changed` и одной строкой
(«doc-комментарий `serialize_state` вернулся к своей функции; поведение не
менялось»), либо — если правило допускает релиз без записей — записать это
исключение в `docs/en/publishing.md`, чтобы `npm run release` и человек
читали одно и то же. Первое проще и честнее.

### 9. Мелочи стиля и однородности — НИЗКАЯ — ✅ выполнен

- **`catch (err)` с неиспользуемой переменной.** Находка 14 прошлого прохода
  предлагала включить `caughtErrors: 'all'` + `caughtErrorsIgnorePattern:
  '^_'`. В конфиг это не попало; вместо этого `bin/vimp-surface.js:46`
  переписан на `catch {`. В `master/GameCatalog.js` таких `catch (err)`
  осталось четыре (строки ~44, ~65, ~112, ~130) — то есть в одном коммите
  два стиля на одну ситуацию. Либо включить правило и вычистить, либо
  вернуть `catch (err)` в vimp-surface: важно, чтобы стиль был один.
- **`GameCoreAdapter.js:1-3`** — оба новых импорта вставлены **над** шапкой
  файла, и блок «Адаптер Rust-ядра (GameCore) под интерфейс…» теперь
  читается как комментарий к классу, а не как заголовок модуля. Во всех
  остальных модулях движка (`coreAbi.js`, `registry.js`, `formUnit.js`)
  порядок обратный. Переставить.
- **`src/lib/coreAbi.js`** — `export default readCoreAbi;` стоит **в
  середине** файла, между `readCoreAbi` и `dispatchCoreOp`. Дефолтный
  экспорт посреди модуля читается как конец файла; перенести вниз (или
  снять — именованных экспортов достаточно, оба места вызова импортируют
  по имени).
- **Rust: литерал `"debug.json"` в пяти местах** — `abi::ENGINE_GAME_OPS`,
  `abi::ENGINE_CLIENT_OPS`, `game.rs:dispatch` (match), `client/game.rs:dispatch`
  (match), плюс JS-реестр. JS-половина в этом же плане специально ушла от
  литералов к именованной константе (`ABI_OP_DEBUG_JSON`) — «имя опкода
  читается ТОЛЬКО отсюда», — а Rust остался на литералах. Разъезд списка и
  `match` даёт ядро, которое объявляет опкод и не обрабатывает его (движок
  увидит «не обработан» и уйдёт на запасной путь — молча). Завести
  `pub const OP_DEBUG_JSON: &str = "debug.json";` в `abi.rs` и использовать
  во всех четырёх местах.

## Браузерное тестирование (`npm run dev`, master :3002)

Прогнано вручную в Chrome, оба матча — на живом мастере с обеими
установленными играми.

| Что проверялось | Результат |
| --- | --- |
| Каталог `/games/manifest.json` | обе игры; у `snakes` — `requires: ["accolades"]`, поля `compat` нет (движок возможность даёт) |
| Лобби, переключение игры в селекторе | форма перестраивается, у tanks появляются `roundTime`/`mapTime`/`friendlyFire`/`Map` |
| Живая валидация room-формы (этап 3 + `formUnit`) | `maxPlayers = 99` → «MAX PLAYERS: must be ≤ 32»; `roundTime = 5` → «must be ≥ 10»; `roundTime = abc` → «must be a number»; исправление гасит строку по своему полю |
| Единица `unit: 's'` | поле показывает `120`, таймер матча стартует с 2:00 — конвертация display↔stored цела на обеих половинах |
| Скрытие поля с единственным вариантом | `Map` у snakes (одна карта `arena`) строки не даёт, у tanks — селект из трёх |
