# План: динамический хост (миграция хоста) + отказ от `/like`·`/unlike` + комнаты без имени + прямые ссылки

Новое направление. Комната перестаёт принадлежать вкладке создателя: роль
хоста (Worker с WASM-ядром и мета-слоем) переходит к другому подключённому
игроку — планово (кнопка, перегрузка, лаг, скрытая вкладка, голосование) или
аварийно (вкладка закрыта, интернет оборвался). Комната живёт, пока в ней
есть хоть один игрок.

> **Как исполнять.** Перед этапом читать только этот файл и файл этапа.
> Каждый этап самодостаточен: в нём перечислены файлы, шаги, тесты, доки и
> критерии готовности. Этап помечается «✅ выполнен» в своём заголовке и в
> таблице ниже. Коммиты не делать — всё остаётся в рабочем дереве
> (правило разработчика). После последнего этапа весь каталог переносится
> `git mv` в `plan/done/host-migration/`.

## Контекст: что есть сейчас (проверено по коду 2026-10-01)

Пути ниже — от корня репозитория `/Users/dmitry/Sites/my/vimp`.

- **Топология — звезда.** Авторитетный матч крутится в Web Worker вкладки
  создателя (`packages/engine/src/host/host.worker.js` → `HostGame.js`), а
  `RTCPeerConnection` живут в главном потоке этой вкладки
  (`client/network/HostController.js`, `HostConnectionManager.js`). Гости —
  WebRTC-офферы (`client/network/WebRtcManager.js`), сам хост-игрок ходит
  через `LoopbackTransport` с socketId `'local'` (`config/lobby.js:344`).
- **Worker handoff** (`HostController.swapWorker`, docs/en/host.md →
  «Worker handoff») меняет Worker **внутри одной вкладки и только на границе
  раунда** (`RoundManager.initiateNewRound`), ядро не дампится, переносится
  JS-мета `HostGame._collectHandoff` (`HANDOFF_VERSION = 3`, HostGame.js:24,
  756-788): участники (с gameId), счёт Stat, карта + остаток времени, `seq`.
  Клиенты рукопожатие **не повторяют** — `PortMachine.restore` поднимает
  автомат сразу в игровом состоянии. Повторный `CONFIG_DATA` клиент
  обработать не умеет (создаст второй `clientCore`, повторный `app.init`).
- **Дамп ядра** `EngineSim::serialize_state/deserialize_state`
  (`packages/engine/core/src/game.rs:476-540`, ABI `abi.rs:314-325`,
  заморожен) — JSON-байты: мир Rapier, карта, PRNG, аккумулятор,
  `GameSim::serialize`. Предусловие: аккумуляторы снапшота опустошены
  (`pack_body`). Из JS **никем не вызывается**. Обе игры и шаблон
  скаффолдера реализуют `serialize`; у tanks есть тесты «дамп → идентичная
  симуляция». Размер дампа не измерялся.
- **Мета посреди раунда не сериализуется**: таймер раунда, отложенные
  рестарт/смена карты, голосования (замыкания `resultFunc`), панель,
  статусы участников, `PlayerDataSync`, override карты, JS-состояние модулей
  плагина (snakes: `ArenaScaler`, `StatBridge`).
- **Известный баг**: после Worker handoff `PlayerDataSync` теряет токены
  игроков — rank/state до конца сессии не пишутся (restoreHuman не получает
  токен, `PlayerDataSync.load` не вызывается).
- **Мастер** (`master/HostRegistry.js`, `SignalingServer.js`): `hostId` —
  `uuidv4` на каждую регистрацию (меняется при переподключении сигналинга
  хоста), состава комнаты мастер не знает (`currentPlayers` сообщает хост),
  закрытие WS хоста сразу удаляет комнату и никого не уведомляет; 1 комната
  на IP.
- **Клиент** (`client/main.js`): любой `close` транспорта → `handleDisconnect`
  → `location.reload` через 3 с; у `Publisher` нет `off()`; таймаутов WebRTC
  нет; `beforeunload` нет; выхода из матча кроме закрытия вкладки нет.
- **Рейтинг `/like`·`/unlike`** (`plan/done/server-rating/`) — мастер
  (`HostRatingProxy`, `_vote`, `refreshRatings`, код `4002`), auth
  (`host_ratings`, `host_votes`, `voidHosterContributions`,
  `state_snapshots`, атрибуция `hoster_user_id`), клиент (перехват в чате,
  бейдж в лобби).
- **Имя сервера** — поле `#lobby-name`, `register_host.name`, поиск
  `gameId/name`. Роутинга по URL нет вовсе: `#auth`/`#lobby` — id DOM-узлов;
  OAuth-возврат и `history.replaceState` (main.js:2504) теряют hash.

## Цели

1. **Миграция хоста** без закрытия комнаты: плановая — продолжение с того же
   тика; аварийная — откат к последней контрольной точке (≤ ~0.5–1 с
   игрового времени). Пауза переключения 1–3 с под оверлеем «Switching
   host…», мир на паузе, пока игроки переподключаются.
2. **Отказ от социальной системы** `/like`·`/unlike` целиком (мастер, auth,
   БД, клиент, доки). Её роль (защита от плохого хоста) берут на себя
   автотриггеры и голосование «Change host».
3. **Комнаты без имени**: мастер выдаёт короткий стабильный `roomId`.
4. **Прямые ссылки**: `#/<gameId>/<roomId>` — вход в комнату,
   `#/<gameId>` — быстрая игра; ссылка переживает OAuth-логин и смену хоста.

## Зафиксированные решения (ответы разработчика, 2026-10-01)

- **Модель — «тёплый резерв P2P».** Мастер назначает преемника (бету); хост
  шлёт ему полную контрольную точку (дамп ядра + мета) ~2 раза/с по
  отдельному DataChannel `standby`. Резервные соединения клиентов к бете
  заранее **не** держим (пауза 1–3 с допустима).
- **Триггеры плановой передачи**: кнопки «Leave server» и «Hand over host»;
  авто — перегрузка хоста (просадка тикрейта), сетевой лаг хоста
  (с гистерезисом и cooldown), скрытая вкладка хоста; голосование
  «Change host» чат-командой `/changehost` (замена `/like`; в меню
  голосований пункта нет); `beforeunload` у текущего хоста как защита
  от случайного закрытия. Некритичные авто-триггеры откладываются до
  границы раунда (с потолком ожидания).
- **Ссылки — hash**: `#/<gameId>/<roomId>` и `#/<gameId>`.
- **Три вида URL** (уточнено при исполнении этапа 3): без hash — лобби (все
  игры); `#/<gameId>` — быстрая игра (оптимальная комната игры, иначе
  создание); `#/<gameId>/<roomId>` — прямой вход. Не залогинен — окно
  авторизации поверх (своего URL нет), после входа — тот же URL.
- **Правила выхода из комнаты**: кик (простой, латентность, пинги) — без
  перезагрузки, адрес → главная, причина в `#tech-informer`, клик/F5 → лобби;
  закрытие комнаты (уход хоста, `room_closed`, `unknownRoom`, неудачная
  миграция) — `reloadTo(#/<gameId>)`; «Leave server» — `reloadTo('')`
  (лобби); отказы политики — как раньше, без перезагрузки. Мёртвая или полная
  прямая ссылка — быстрая игра той же игры. `sessionStorage` для этого не
  используется.
- **План — по этапам** в этом каталоге.

### Отклонено / вне плана

- **Hot standby (две параллельные симуляции)** и **«триада 2 из 3»** —
  невозможны без lockstep: ввод применяется по факту прихода
  (`HostGame.updateKeys`, без привязки к тику), `on_ai_tick(dt)` ботов
  зависит от реального `dt` (`core/src/game.rs:287`) — миры разойдутся за
  секунды.
- **Контрольные точки на мастере** — мастер остаётся без игровых данных.
- **Резервные WebRTC-соединения клиентов к бете заранее** — возможное
  будущее улучшение (сократит паузу до ~0.3 с), в план не входит.
- **Бинарный дамп ядра (bincode)** — только если этап 0 покажет, что
  JSON+gzip не укладывается в бюджет; тогда это отдельное решение с
  разработчиком (затрагивает крейт).
- **Dedicated-сервер и standalone SDK** миграцию не получают (там хост один
  по определению); их поведение не должно измениться.

## Целевая архитектура (кратко)

```
           мастер (сигналинг, реестр комнат, арбитр миграции)
           Room { roomId, epoch, hostMemberId, successorMemberId,
                  members{memberId→{userId, caps, rtt}}, status }
             ▲ join_room/host_unreachable/...       ▲ register_host/update_host/...
             │                                      │
  клиент C ──┼── WebRTC meta+state ──► ХОСТ A (Worker: ядро+мета, epoch N)
  клиент B ──┘ (бета) ◄── DataChannel `standby`: контрольные точки ~2/с
                │
                └─ прогретый Worker (плагин загружен, wasm скомпилирован)

  авария/плановая передача: мастер → B `promote{epoch N+1}` → B поднимает
  Worker из контрольной точки, регистрируется → мастер → всем
  `host_changed{N+1}` → клиенты: новый WebRTC к B + RESUME (порт) →
  мир снимается с паузы
```

### Глоссарий

| Термин            | Что это                                                                                                                                                                                                                                                         |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `roomId`          | Стабильный публичный id комнаты (8 символов crockford-base32 в нижнем регистре), в ссылке и в лобби; переживает смену хоста                                                                                                                                     |
| `epoch`           | Номер «правления» хоста в комнате (с 1), +1 при каждой смене хоста; все сообщения миграции его несут, устаревшие отбрасываются                                                                                                                                  |
| `memberId`        | Случайный UUID вкладки (`crypto.randomUUID()` при загрузке страницы), ключ участника комнаты на мастере; переживает реконнект сигналинга                                                                                                                        |
| `roomSecret`      | Бывший `hostSecret`: `HMAC(VIMP_ROOM_SECRET_KEY, roomId:epoch:hostUserId)` — доказывает мастеру, что ты хост этой эпохи (записи rank/state, `reclaim_host` после рестарта мастера — защита от угона комнаты по видимому `roomId`); меняется со сменой эпохи сам |
| `promotionToken`  | Одноразовый токен мастера, который преемник предъявляет в `register_host`, чтобы занять комнату                                                                                                                                                                 |
| `resumeKey`       | Случайный секрет участника, выданный хостом при входе в матч; предъявляется новому хосту при возобновлении; едет в контрольной точке                                                                                                                            |
| контрольная точка | `{ meta (HANDOFF_VERSION 4), core (байты serialize_state) }`, gzip; периодическая или финальная                                                                                                                                                                 |
| бета / преемник   | Участник, назначенный мастером получать контрольные точки и принять хост                                                                                                                                                                                        |

### Инварианты, которые нельзя нарушить

- `ENGINE_API_VERSION` остаётся **4**; плагинная поверхность только
  дополняется (`packages/engine/contract/surface.json`, `npm run
surface:update`); из `surface.json` **ничего не удалять** — если шаг
  этого требует, остановиться и обсудить с разработчиком.
- Номера портов (`config/wsports.js`) и коды закрытия
  (`config/closeCodes.js`) append-only: выведенный код/порт остаётся с
  пометкой `// retired`, номер не переиспользуется.
- ABI ядра заморожен (`FROZEN_CORE_ABI`): используем существующие
  `serialize_state`/`deserialize_state`, новых экспортов ядра не вводим.
- `host/meta/` остаётся Worker-safe (только изоморфные API).
- Протокол главный поток ↔ Worker: **новый Worker обязан понимать сообщения
  старого главного потока** (страница, загруженная до деплоя, поднимает
  Worker по свежему манифесту). Старые типы сообщений не удалять, только
  добавлять.
- Новый Worker принимает handoff-состояние **v3 и v4** (смена кода в
  открытой комнате передаёт v3 от старого Worker'а новому).
- Игра, не включившая `gameConfig.migration.midRound`, мигрирует «мягко»:
  мета переносится, раунд начинается заново (как нынешний handoff). Это
  поведение по умолчанию для всех уже опубликованных игр.
- Dedicated (`src/dedicated/`) и standalone (`src/standalone/`) работают как
  раньше: без миграции, без меню комнаты и без перехвата `/changehost`
  (режим — из `boot.js`). Меню голосований движок не меняет ни в одном
  режиме.

## Общие правила для каждого этапа

1. **Тесты в том же изменении** (CLAUDE.md → Testing): Vitest в `tests/`,
   зеркально `packages/engine/src/`; фикс начинается с теста,
   воспроизводящего баг. Rust — `npm run core:test` (только если тронуто
   ядро; по плану ABI не меняется, единственный возможный фикс внутри
   крейта — поведение `ClientCore.reset()` в этапе 4, если проверка
   покажет, что он не сбрасывает историю предиктора; тогда — запись
   `### Fixed` в `packages/engine/core/CHANGELOG.md`).
2. **Конец каждого этапа — зелёный прогон**:
   `npx prettier --write <изменённые файлы>`, `npx eslint .`,
   `npm test -- --silent` (при необходимости `npx vitest run <путь>
--reporter=dot`).
3. **Доки в том же изменении**: `docs/en/<page>.md` и зеркально
   `docs/ru/<page>.md` (таблица «область → страница» в `CLAUDE.md`);
   изменения контракта плагина — ещё и в `docs/ai/`.
4. **CHANGELOG** `packages/engine/CHANGELOG.md` под `## [Unreleased]`,
   подзаголовок выбирать осознанно: новое — `### Added`, удалённое —
   `### Removed`, исправление — `### Fixed`; `### ⚠️ Breaking` +
   `### Migration` — только если что-то, что раньше загружалось (плагин,
   конфиг), теперь отвергается. Тесты/рефакторинг/доки — не записи.
5. **Release impact** в отчёте этапа: какой артефакт тронут (npm
   `vimp-engine` / crate / `create-vimp-game`), какой бамп следует из
   подзаголовка, нужно ли что-то в репозиториях игр, какие проверки прошли.
   `version` не править, ничего не публиковать, не коммитить.
6. Конфиги: числовые пороги — в `config/lobby.js` (клиент) /
   `config/master.js` (мастер) / `config/hostDefaults.js` (Worker), с
   описанием в `docs/{en,ru}/configuration.md`.
7. UI-строки — на английском (как весь UI движка).
