# Кодревью 014d0f8 («form bug»): декларативные проверки на хосте + C10 ✅ выполнен

> Все находки (S1-S3, М1-М6) закрыты в рабочем дереве; М1 сделан первым
> вариантом (гейт по контролу), М2 — доками, М4 снят правкой S3.

Разбор коммита `014d0f8` — `validateAuth` применяет `maxlength`/`regExp`
дескриптора, `C10` ловит нерезолвнутое имя валидатора. Каждое утверждение
ниже проверено запуском кода, а не чтением комментариев.

## Что сделано хорошо

- Дыра закрыта в правильном месте: `validateAuth` — единственная точка, через
  которую проходит и клиентский путь (`main.js:441`), и авторитетный
  (`PortMachine.js:218`).
- Якорение `regExp` переиспользует `anchorPattern` (`src/lib/formPattern.js`)
  — клиент и хост физически не могут разойтись в трактовке паттерна.
- Осознанные исключения (`required`, некомпилируемый паттерн) не просто
  сделаны, а объяснены в коде, в `CHANGELOG` и в обеих версиях
  `plugin-api.md`; `docs/ru` — точное зеркало `docs/en`.
- Порядок проверок совпадает с формой: длина → формат → игровой валидатор,
  одна ошибка на поле (`continue`).
- `C10` не даёт ложного срабатывания на движковом имени (`isValidName`
  гостевого ника) — это ровно тот случай, который сломал бы гостевой контур.
- `npx eslint` чисто, точечные наборы (`tests/lib/validators.test.js`,
  `tests/devtools/contract/rules.test.js`) — 70 тестов зелёные.

## S1. Паттерн игры исполняется на хосте против строки без потолка длины

**Критерии:** Безопасность, Производительность, Масштабируемость.

### Проблема

До коммита `regExp` из схемы игры выполнялся только в браузере игрока
(`formBuilder.fieldPattern`) — то есть в его собственной вкладке. Теперь тот
же паттерн исполняется на **хосте**: в P2P-контуре это Worker с авторитетным
матчем (его заморозка — заморозка комнаты для всех), в `dedicated` — весь
Node-процесс игрового сервера.

При этом длина значения не ограничена ничем, если в дескрипторе нет
`maxlength`. Это не побочный эффект, а зафиксированное поведение —
`tests/lib/validators.test.js:111-115` прямо утверждает, что строка в 10 000
символов проходит. Размер кадра тоже никто не режет: `PortMachine.message()`
делает `JSON.parse(data)` без проверки длины, ограничителя на входе нет
(`grep maxPayload|maxMessageLength` по `src/host`, `src/master` — пусто).

Катастрофический бэктрекинг превращает это в заморозку матча. Замер
(`node --input-type=module`, паттерн `(a+)+b`):

| длина значения | время в `validateAuth` |
| --- | --- |
| 22 символа | 216 мс |
| 26 символов | 366 мс |
| 30 символов | 5812 мс |

Тридцать пять символов — уже минуты заблокированного event loop. Кадр
`PC_AUTH_RESPONSE` шлёт любой подключившийся клиент, ещё до создания
участника.

Оговорка по-честному: паттерн приходит из схемы игры, а не от атакующего, —
это дефект плагина, а не чужой ввод. Но до коммита такой дефект стоил игроку
подвисшей вкладки, а после — стоит комнате всего матча, и запускается это
одним сообщением.

### Решение

Потолок длины поля, когда `maxlength` не объявлен: он и ограничивает
бэктрекинг, и закрывает саму дыру «поле без `maxlength` принимает строку
любой длины».

`packages/engine/src/lib/validators.js`:

```js
// потолок длины поля формы, когда maxlength в дескрипторе не объявлен.
// regExp игры теперь исполняется на хосте против строки, которую прислал
// клиент, и катастрофический паттерн вроде "(a+)+b" превращает 35 символов
// в минуты заблокированного event loop — а хост это либо Worker с
// авторитетным матчем (замирает комната), либо процесс dedicated целиком.
// 256 — с запасом на любое поле auth-формы (ник, имя модели): значения
// длиннее не бывает у формы и не нужно тому, кто её обошёл
const MAX_FIELD_LENGTH = 256;
```

и в цикле, вместо текущей ветки `maxlength` (проверка длины выносится из-под
`if (value !== '')` — пустой строке она не мешает, а порядок «длина раньше
паттерна» обязателен, иначе потолок не спасает):

```js
    const limit = options?.maxlength ?? MAX_FIELD_LENGTH;

    if (value.length > limit) {
      errors.push({ name, error: 'too long' });
      continue;
    }

    if (value !== '' && options?.regExp && !matchesPattern(options.regExp, value)) {
      errors.push({ name, error: 'invalid format' });
      continue;
    }
```

**Тесты:** заменить `tests/lib/validators.test.js:111-115` («поле без
maxlength/regExp проходит любой строкой») на два кейса — строка в пределах
потолка проходит, строка длиннее `MAX_FIELD_LENGTH` даёт `too long`; и кейс
со злым паттерном `(a+)+b` + 300 символов, который обязан вернуться за
единицы миллисекунд (`expect(Date.now() - t).toBeLessThan(100)`).

**Журнал:** отдельным пунктом в тот же `### Changed` — поле без `maxlength`
теперь ограничено потолком в 256 символов, и почему.

## S2. Заявленный паритет не достигнут: членство в списке вариантов хост не проверяет

**Критерии:** Безопасность, Работоспособность.

### Проблема

Коммит формулирует цель так: «клиент, обошедший форму, не должен получать
больше прав, чем клиент, её заполнивший». Но самое жёсткое ограничение формы
— не `maxlength` и не `regExp`, а **список вариантов**: `<select>` и
`<input type=radio>` физически не могут отдать значение вне своих `options`.
На хосте это не проверяется вообще — ни до коммита, ни после.

Проверено:

```js
validateAuth({ side: 'что угодно' },
  [{ name: 'side', options: { control: 'select', options: ['red', 'blue'] } }]);
// -> undefined
```

Обе поставляемые игры спасает только то, что каждая объявила свой
`isValidModel` (`model in models`) — то есть от совпадения, а не от контракта.
Игра с полем-`select` без валидатора (команда, цвет, режим) примет от
обошедшего форму клиента любую строку, и та доедет до `HumanParticipant` и
разъедется по остальным клиентам комнаты. Это ровно тот класс дыр, ради
которого коммит и делался, — и он остался открытым.

`source`-поля проверять нельзя и не нужно: auth-форма строится с пустым
`ctx` (`Auth.js:83` — `buildForm(descriptors, container, {}, …)`), так что
`source` в `authSchema` и на клиенте резолвится в пустой список
(`no options available`). Проверяем только объявленный inline-список.

### Решение

Разбор вариантов дескриптора сейчас живёт в `client/lib/formBuilder.js`
(`normalizeOptions`, `forcedValue`) — хосту импортировать оттуда нельзя
(слой клиента). Прецедент уже есть: ровно для такого случая в прошлой правке
заведён `src/lib/formPattern.js`. Тем же приёмом вынести разбор вариантов в
`packages/engine/src/lib/formOptions.js`:

```js
// Разбор списка вариантов дескриптора — общий для формы (client/lib/
// formBuilder.js) и для авторитетной проверки (lib/validators.js): вариант
// пишут либо строкой, либо { value, label }.
export function normalizeOptions(list) {
  return (list || []).map(opt =>
    opt !== null && typeof opt === 'object' ? opt : { value: opt, label: String(opt) },
  );
}
```

`formBuilder.js` переходит на импорт (свою копию удалить), а `validators.js`
получает проверку членства:

```js
import { normalizeOptions } from './formOptions.js';

// контролы со списком вариантов: браузер другого значения и не отдаст —
// <option>.value и <input type=radio>.value это ровно объявленный список.
// Хост обязан требовать того же, иначе поле-select без игрового валидатора
// принимает от обошедшего форму клиента любую строку
const OPTION_CONTROLS = ['select', 'radio'];

// source-варианты хост не резолвит (их и форма не резолвит: auth-форма
// строится с пустым ctx) — проверяем только объявленный список
const isDeclaredOption = (options, value) =>
  normalizeOptions(options.options).some(opt => String(opt.value) === value);
```

в цикле — до `regExp`, сразу после проверки длины:

```js
    if (
      OPTION_CONTROLS.includes(options?.control) &&
      !options.source &&
      (options.options?.length ?? 0) > 0 &&
      !isDeclaredOption(options, value)
    ) {
      errors.push({ name, error: 'not an option' });
      continue;
    }
```

`String(opt.value)` — то же приведение, что делает `resolveForcedValue`
(`formBuilder.js:61`): `options: [1, 2]` в DOM становятся строками, и хост
обязан сравнивать с ними, а не с числами.

**Тесты** (`tests/lib/validators.test.js`): значение вне списка → `not an
option`; значение из списка → `undefined`; список из объектов
(`{ value, label }`) → сравнение по `value`; числовые варианты
(`options: [1, 2]`, значение `'1'`) → проходит; поле с `source` → проходит
(хост списка не знает). Плюс в `tests/client/lib/formBuilder.test.js` —
что переезд `normalizeOptions` ничего не сломал (существующие кейсы
достаточны, отдельный не нужен).

**Доки и журнал:** дописать абзац «Validation split» в
`docs/en|ru/plugin-api.md` и строку в `docs/ai/10-pitfalls.md` — хост
проверяет и членство в списке; `### Changed` в `packages/engine/CHANGELOG.md`.

## S3. Два определения «валидатор резолвится» разъехались

**Критерии:** Работоспособность, Отсутствие дублирования, Поддерживаемость.

### Проблема

Коммит ввёл понятие «имя валидатора резолвится» и записал его в двух местах
по-разному:

- `validators.js:88` — `if (validatorFn && !validatorFn(value))`: зовётся всё
  **истинное**;
- `c10-auth-schema.js:60` — `typeof validators[validatorName] !== 'function'
  && !engineValidatorNames.includes(validatorName)`: требуется **функция**,
  но движковое имя засчитывается без проверки типа.

Отсюда обе стороны ошибки:

1. Игра, объявившая `validators: { isValidModel: 'm1' }` (строка вместо
   функции — опечатка ровно того же класса, что коммит и ловит), проходит
   `validateAuth` не молча, а **броском**. Проверено:

   ```
   TypeError: validatorFn is not a function
   ```

   `PortMachine.message()` вызывает `state.methods[msg[0]](msg[1])` без
   `try/catch` (`PortMachine.js:141`) — исключение уходит наверх из
   обработчика сообщения Worker'а.

2. Игра, перекрывшая движковое имя не-функцией (`validators: { isValidName:
   null }`), **проходит `C10` зелёным** — `engineValidatorNames.includes()`
   срабатывает раньше типа — и падает на хосте по пункту 1. То есть правило
   обещает ровно то, чего не проверяет.

### Решение

Одно определение на движок, которым пользуются оба: `validateAuth` — чтобы
звать, `C10` — чтобы проверять. Заодно исчезает надобность в экспорте
`engineValidatorNames` (см. М4).

`packages/engine/src/lib/validators.js`:

```js
/**
 * Резолвит имя валидатора из дескриптора: движковые правила, перекрытые
 * игровыми. Одно определение на движок — им пользуется и validateAuth
 * (чтобы звать), и правило C10 (чтобы проверять); две копии этого правила
 * уже разъезжались на типе значения.
 * @param {string} name - Имя из options.validator.
 * @param {Object} [validators] - authSchema.validators игры.
 * @returns {Function|undefined} Функция или undefined, если имя не резолвится.
 */
export const resolveValidator = (name, validators = {}) => {
  const fn = { ...validationRules, ...validators }[name];

  return typeof fn === 'function' ? fn : undefined;
};
```

В `validateAuth` (строки 80-91) — вместо `rules[options.validator]`:

```js
    if (options?.validator) {
      const validatorFn = resolveValidator(options.validator, validators);

      // не-функция и незнакомое имя ведут себя одинаково — поле проходит.
      // Для клиента это норма (игровые валидаторы к нему не едут), для
      // хоста — дефект схемы, о котором говорит C10 и console.error в
      // PortMachine (М3): звать что попало нельзя, TypeError отсюда
      // выходит прямо в обработчик сообщения
      if (validatorFn && !validatorFn(value)) {
        errors.push({ name, error: 'not valid' });
      }
    }
```

Локальную `rules` из `validateAuth` удалить.

В `c10-auth-schema.js` — импорт `resolveValidator` вместо
`engineValidatorNames`, условие сжимается до:

```js
      if (
        validatorName !== undefined &&
        !resolveValidator(validatorName, validators)
      ) {
```

**Тесты:** `validators.test.js` — валидатор-не-функция не бросает и поле
проходит; `rules.test.js` — `C10` ловит движковое имя, перекрытое
не-функцией.

## М1. Паритет с формой асимметричен по типу контрола

**Критерии:** Работоспособность, Документированность.

`validateField` применяет `maxlength` и `regExp` только к `control: 'text'`
(`formBuilder.js:108-125` — обе ветки под `isText`). `validateAuth` применяет
их к любому контролу. Проверено:

```js
validateAuth({ side: 'RED' },
  [{ name: 'side', options: { control: 'select', regExp: '[a-z]+' } }]);
// -> [{ name: 'side', error: 'invalid format' }]
```

Форма такое пропускает, хост отбивает — и игроку нечем это исправить, вариант
в списке ровно такой. Направление «хост строже» безопасно, но тупик для
игрока хуже, чем несделанная проверка.

**Решение** (одно из двух, по вкусу):

- либо гейт по контролу, как на клиенте — `const isText = options?.control ===
  'text' || options?.control === undefined;` и обе декларативные ветки под
  ним (потолок длины из S1 при этом остаётся безусловным — он про DoS, а не
  про паритет);
- либо оставить как есть и назвать асимметрию явно в комментарии и в
  «Validation split»: `maxlength`/`regExp` на нетекстовом контроле — дефект
  схемы, и хост отказывает.

Первое честнее по отношению к формулировке «те же декларативные правила».
Проверку членства из S2 это не отменяет — она как раз для нетекстовых.

## М2. `min`/`max` — третья декларативная пара, о которой не сказано ничего

**Критерий:** Документированность.

Форма проверяет `min`/`max` (`formBuilder.js:101-107`), хост — нет, и ни
комментарий в `validators.js`, ни «Validation split», ни `CHANGELOG` этого не
упоминают, хотя перечисляют `required` как единственное исключение.

Сегодня это безвредно по нетривиальной причине: числовое поле отдаёт из
`getValue()` **число**, а `validateAuth` отбивает нестроковое значение
`Property must be a string` — то есть числовое поле в `authSchema` не работает
вовсе, ни через форму, ни в обход. Но узнать это можно только сопоставив три
файла.

**Решение:** строка в комментарии `validateAuth` и в «Validation split» обеих
локалей: числовых полей в `authSchema` не бывает (значение обязано быть
строкой), поэтому `min`/`max` там не применяются. Плюс, по желанию, четвёртая
проверка в `C10`: `numeric: true` или `unit` в `authSchema.params` — ошибка
схемы, поле никогда не пройдёт авторизацию.

## М3. `C10` — опциональный тул, а дыра — рантаймовая

**Критерий:** Поддерживаемость.

Правило ловит опечатку, только если разработчик игры запускает
`vimp-contract`. Кто не запускает — по-прежнему получает поле, которое не
проверяет никто, без единой строки в консоли.

Внутрь `validateAuth` предупреждение не поставить: у клиента игровых
валидаторов нет по устройству, и он бы спамил. Но у хоста есть точка, где
известны и схема, и валидаторы, и она исполняется один раз за матч —
конструктор `PortMachine` (`PortMachine.js:47`, сразу после сборки
`this._authParams`):

```js
    // C10 говорит это статически, но контракт-чекер запускают не все:
    // нерезолвнутое имя означает, что поле не проверяет никто
    for (const { name, options } of this._authParams) {
      if (
        options?.validator &&
        !resolveValidator(options.validator, authSchema.validators)
      ) {
        console.error(
          `PortMachine: authSchema param "${name}" names validator ` +
            `"${options.validator}", which authSchema.validators does not ` +
            'provide — the field is checked by nobody',
        );
      }
    }
```

**Тест:** `tests/host/PortMachine.test.js` — схема с опечаткой в имени пишет
`console.error` (spy), корректная — молчит.

## М4. `engineValidatorNames` — новый публичный экспорт, которого нет в журнале

**Критерии:** Документированность, Стандартизация.

`packages/engine/package.json` отдаёт `"./lib/*": "./src/lib/*"`, то есть
`vimp-engine/lib/validators.js` — публичная точка входа, и
`engineValidatorNames` стал публичным API. По `CLAUDE.md` новый публичный
экспорт — это `### Added`, а не `Changed`; в журнале он не упомянут вовсе.
Уровень релиза от этого не меняется (в `[Unreleased]` уже есть `### Added` →
minor), так что чинить нечего, кроме самой записи.

Плюс мелочь: экспортируется изменяемый массив — любой потребитель может
`push`-нуть в него.

**Решение:** правка S3 убирает экспорт совсем — резолвер закрывает
потребность, и вопрос heading'а снимается вместе с ним. Если S3 не делать —
завести строку в `### Added` и заморозить массив (`Object.freeze`).

## М5. Два цикла подряд по одному массиву

**Критерий:** Отсутствие дублирования.

`c10-auth-schema.js:41-48` и `52-69` — два `for (const field of params)`
подряд. Слить в один с двумя проверками внутри; порядок нарушений при этом
сохранится по полям, а не по видам ошибок, что читается даже лучше.

## М6. Пробелы в тестах

**Критерий:** Тестируемость.

Не покрыто ни одним кейсом:

- `maxlength` коротит игровой валидатор (`continue`) — то есть при слишком
  длинном значении валидатор не зовётся;
- нерезолвнутое имя в `C10` при **отсутствующем** `authSchema.validators`
  (сегодня оба кейса передают объект);
- гостевой контур — единственное место, где новая проверка `maxlength`
  реально срабатывает сегодня (`createGuestIdentity` объявляет
  `maxlength: 15` на нике): ник длиннее теперь отбивается `too long`, а не
  `not valid`, и это стоит зафиксировать тестом, потому что это единственное
  наблюдаемое изменение поведения в поставляемом коде;
- случаи из S1-S3 и М1 (перечислены в своих разделах).

## Проверено и **не** является проблемой

- **Токен не попадает под новые проверки.** `validateAuth` идёт по
  `authParams`, а `token` в схеме отсутствует по устройству
  (`identity.js:46`) — потолок длины JWT не заденет.
- **Обрезка пробелов.** Форма отдаёт `getValue()` уже обрезанным
  (`formBuilder.js:144`), хост не обрезает — но легального пути, где хосту
  придёт необрезанная строка от формы, нет, а обошедшему клиенту `' Bob '`
  отобьёт `isValidName`.
- **Пустое значение и `required`.** Пропуск обоснован: solo-путь
  (`boot.autoAuth` → `defaultsFrom`) шлёт дефолты схемы, среди которых бывает
  `''`. Гостевой ник при этом всё равно отбивается — `isValidName('')` ложь.
- **Уровень релиза `### Changed`.** Прецедент в журнале уже есть: тем же
  heading'ом логировалось ужесточение `B5` («also checks that each `regExp`
  compiles»). Отбивается здесь значение поля, а не плагин и не конфиг, —
  `⚠️ Breaking` не требуется.
- **Совместимость с поставляемыми играми.** У tanks и snakes в `authSchema`
  ровно одно поле (`model`, `control: 'select'`, только `validator`) — новые
  ветки на них не срабатывают вовсе, `C10` зелёный у обеих.
- **Перекомпиляция паттерна на каждый вызов** (в отличие от кэша
  `formBuilder.patterns`) — `validateAuth` зовётся раз на вход игрока,
  экономить нечего.

## Порядок работ

1. S1 (потолок длины) — единственная находка с рантайм-последствиями для
   комнаты; делается в одном файле.
2. S3 (единый резолвер) — снимает и М4.
3. S2 (членство в списке) — самая объёмная: новый `src/lib/formOptions.js` +
   переезд `normalizeOptions` из `formBuilder.js`.
4. М1, М2, М3, М5, М6 — по месту.
5. Доки (`docs/en|ru/plugin-api.md`, `docs/ai/10-pitfalls.md`) и
   `packages/engine/CHANGELOG.md` (`### Changed`, уровень секции не меняется).
