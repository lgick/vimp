# Этап 2. Причина A: шаг тел как у Rapier (порт TGS) ✅ выполнен

Индекс и общий контекст — `plan/README.md`. Правила и запреты оттуда действуют здесь. Этап начинается только
после этапа 1: эталон Rapier (`rapier_head_on`) и правка `obb_manifold` уже в дереве.

## Причина

### Причина A: решатель реплики устроен не так, как TGS-решатель Rapier

Уточнено на шаге 0 по исходникам `rapier2d` 0.34 (`dynamics/solver/velocity_solver.rs::solve_constraints`,
`island_solver.rs`, `contact_constraint/contact_with_coulomb_friction.rs::{generate, update, solve}`,
`contact_constraint_element.rs`, `geometry/contact_pair.rs::is_bouncy`, `narrow_phase.rs` ≈1035–1070).

**Как шаг делает Rapier** (параметры хоста — по умолчанию, меняется только `dt`):
1. Ограничения строятся ОДИН раз на позе начала шага. Для точки запоминаются нормаль `n`, точка (середина `p1`, `p2`),
   локальные точки в обоих телах, зазор `dist0` (у Rapier `dist > 0` — зазор, то есть `dist0 = −depth`),
   проекционная масса и `normal_vel = is_bouncy · e · v_n0`. Здесь `v_n0` — нормальная скорость сближения точки на
   начало шага. `is_bouncy` = (точка новая и `e > 0`) или (точка старая и `e ≥ 1`); «новая» — суммарный импульс
   точки на ПРОШЛОМ шаге равен 0. У танка e = 0.05, поэтому старая точка не отскакивает никогда.
2. Шаг делится на `num_solver_iterations = 4` подшага, `h = dt/4`. На каждом подшаге:
   1. **update.** Зазор пересчитывается по текущим позам: `dist = dist0 + (p1 − p2)·n`, где `p1`, `p2` — локальные
      точки, перенесённые текущими позами тел. `rhs_wo_bias = normal_vel + max(dist, 0)/h`,
      `rhs_bias = clamp((dist + allowed_err)·erp_inv_dt(h), −max_corrective, 0)`, `rhs = rhs_wo_bias + rhs_bias`.
      Накопленный импульс подшага уходит в `impulse_accumulator`. Касательная `rhs` получает смещение
      `(p1 − p2)·t / h`.
   2. **warmstart.** Импульс прошлого подшага (на первом подшаге — прошлого ШАГА) прикладывается заново,
      `warmstart_coefficient = 1`.
   3. **Проход со смещением (1 итерация PGS).** Сначала нормали: пару точек одного манифольда в 2D решает
      блочный 2×2 MLCP-решатель (`solve_pair`, `BLOCK_SOLVER_ENABLED = cfg!(dim2)`), одиночную точку — обычный клампинг.
      Везде мягкость `cfm_factor(h)`: `new = cfm · max(old − r·dvel, 0)`. Потом трение всех точек, конус —
      `friction · normal.impulse` текущего подшага.
   4. **Интеграция позиций** скоростью на `h`, поворот линеаризован (`integrate_linearized`: cos/sin + нормировка).
   5. **Проход без смещения (1 итерация).** `cfm = 1`, `rhs = rhs_wo_bias`: нормали (тем же блочным решателем),
      затем трение.
3. После подшагов: позиция — итог подшагов; скорость демпфируется ОДИН раз на полный `dt`
   (`writeback_bodies(base_params)`), позиции демпфирование не касается. В кэш точки пишутся `warmstart_impulse`
   (импульс последнего подшага) и `impulse` (сумма за шаг, по ней следующий шаг решает `is_new`).

**Чем отличается реплика** (`apply_contact_impulse`):
- один «подшаг» на весь `dt`, итерации без интеграции между ними;
- нет прохода без смещения. Поэтому у закрывшегося зазора остаётся скорость «зазор/dt», а не то, что даёт Rapier;
- нормаль и трение решаются поточечно, без блочного решателя пары. Первая точка манифольда разворачивает корпус,
  трение превращает разворот в боковой снос `vx`;
- нет памяти между шагами (`is_new`, warmstart);
- проникновение разводит `separate_bodies` жёстко раз за шаг, а не мягкая пружина на каждом подшаге.

**Замер шага 0** (танк 8×6 из раздела 1, `v = 140`, путь за шаг 1.167, стена прямо перед лбом, меняется зазор):

| зазор / путь за шаг | `vx` на шаге удара | `vx` на следующем шаге |
| --- | --- | --- |
| 0.04 … 0.69 | −6.83 (отскок −e·v, затем демпфирование) | −6.67 |
| 0.73 | −3.65 | −3.56 |
| 0.77 | +4.88 | 0 |
| 0.86 | +51.7 | −0.02 |
| 0.99 | +122.0 | 0 |

Лоб встаёт к грани во всех случаях, проникновение ≤ 0.041. Граница ≈0.73 — это «зазор закрывается на последнем
подшаге»: там `max(dist, 0)/h` ещё разрешает сближение, отскок приходит только в проход без смещения того же
подшага, а на следующем шаге точка уже не новая. Простое правило «закрывшийся контакт → −e·v_n0» (прежняя
редакция 3.2) совпадает с Rapier только ниже границы: примерно каждый четвёртый удар дал бы рывок до ≈130 ед/с.
Поэтому решатель повторяет подшаги Rapier, а не приближает их формулой.

### Что уже проверено прототипом (прототип откачен, в деревьях его нет)

Прототип был собран прямо в `predictor.rs` игры:
- в каждой итерации сначала нормали всех точек, потом трение;
- проход без смещения — только для контактов с `acc.normal > 0` после прохода со смещением;
- позиция интегрируется скоростью прохода со смещением, итоговая скорость берётся из прохода без смещения, затем
  демпфирование.

Результаты:
- лобовой удар в длинную стену — `vy` совпал с хостом бит в бит (−6.28 → −6.11 → −5.95 на следующих шагах), `ω` = 0,
  остаток `vx` 0.30, ошибка позиции ≈0.05 (порог сценариев — 3);
- `cargo test --workspace` игры зелёный, `terraces_backside.json` зелёный;
- `jump` и `downtown_bridge` покраснели — это причина B, её прототип не исправлял.

- **Ограничение прототипа (выяснено на шаге 0).** Прототип совпадал с хостом только в режиме, где зазор
  закрывается раньше последнего подшага Rapier (см. «Причина A», таблица). Код ниже — справка по устройству
  прохода без смещения, в новом решении он заменён подшагами.

Код прототипа (для справки, не копировать дословно):

```rust
// в resolve_world, после сбора contacts: Vec<(a, b, Contact, Surface, ContactImpulses)>
let v0: Vec<f32> = contacts.iter().map(|(a, b, c, ..)| rel_normal_velocity(&sim[*a], &sim[*b], c)).collect();

for _ in 0..SOLVER_ITERATIONS {
    // 1) нормали всех точек (со смещением bias = −depth/dt при depth < 0, отскок — от избытка, как сейчас)
    // 2) трение всех точек (кулоновский конус от НАКОПЛЕННОГО нормального импульса)
}

let biased = sim.clone();                       // скорости для интеграции позиции
let active: Vec<bool> = contacts.iter().map(|c| c.4.normal > 0.0).collect();

for _ in 0..SOLVER_ITERATIONS {
    for k in 0..contacts.len() {
        if !active[k] { continue; }
        // vn = относительная нормальная скорость БЕЗ смещения
        // target = e * min(v0[k], 0)        (отскок от исходной скорости сближения)
        // total = max(acc.normal − (vn + target) / eff_n, 0); jn = total − acc.normal; acc.normal = total
        // применить jn к обоим телам (как в apply_contact_impulse)
    }
}
// итог: позиция += biased.v · dt; скорость = sim.v (без смещения); затем демпфирование
```

`rel_normal_velocity` — то же, что приватная `rigid_body::normal_velocity`: `(v_b + ω_b × r_b − v_a − ω_a × r_a) · n`.

## Решение

### Шаг тел как у Rapier (новый API, `### Added`)

Существующие `apply_contact_impulse`, `separate_bodies` и `integrate` не менять, иначе молча поменяется физика
других игр. В их doc-комментарии дописать, что для паритета с хостом нужен `step_bodies`. Добавить в
`packages/engine/core/src/client/rigid_body.rs`:

```rust
/// Число подшагов решателя хоста (`IntegrationParameters::num_solver_iterations` Rapier по умолчанию).
pub const SOLVER_SUBSTEPS: usize = 4;

/// Стабильный между шагами идентификатор точки контакта: по нему решатель находит память прошлого шага
/// (`is_new`, warmstart). Собирает вызывающий из устойчивых имён пары и номера точки манифольда.
// поля скрыты: `a`, `b` по 32 бита и номер точки в `u64` не помещаются
// (решение пользователя, шаг 1.2)
#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash, PartialOrd, Ord)]
pub struct ContactKey { a: u32, b: u32, point: u8 }

impl ContactKey {
    /// Ключ точки `point` (0 или 1) пары `a`—`b`; `a`, `b` — устойчивые имена тел (id игры, индекс блока).
    pub fn new(a: u32, b: u32, point: u8) -> Self;
}

/// Строка контакта шага: тела по индексам среза, точка манифольда на позе начала шага, материал, ключ.
#[derive(Clone, Copy, Debug)]
pub struct ContactRow {
    pub a: usize,
    pub b: usize,
    pub contact: Contact,
    pub surface: Surface,
    pub key: ContactKey,
}

impl ContactRow {
    /// Строки манифольда пары `a`—`b` для `step_bodies`: точки `Manifold::solver_points()` подряд (порядок пары
    /// для блочного решателя), ключи — `key_base` с номером точки 0/1. Вызывающий не может перепутать точки
    /// старого и нового решателя или разорвать пару.
    pub fn from_manifold(a: usize, b: usize, manifold: &Manifold, surface: Surface, key_base: ContactKey)
        -> impl Iterator<Item = ContactRow>;
}

/// Память контактов между шагами — то, что Rapier хранит в `ContactData` точки: импульс последнего подшага
/// (warmstart, нормаль и касательная) и сумма за шаг (по ней решается `is_new`). Вызывающий держит один кэш
/// на симуляцию, живёт между шагами без аллокаций. `Clone` дешёвый (два коротких `Vec`): предиктор хранит
/// копию на каждый шаг в истории снимков и откатывает её вместе с состоянием.
#[derive(Clone, Debug, Default)]
pub struct ContactCache { /* приватно */ }

impl ContactCache {
    pub fn new() -> Self;
    /// Забыть всё: телепорт, респаун, откат к снапшоту без сохранённого кэша.
    pub fn clear(&mut self);
}

/// Шаг тел с контактами, как у Rapier: `SOLVER_SUBSTEPS` подшагов (update → warmstart → проход со смещением →
/// интеграция позиций на h → проход без смещения), затем одно демпфирование скорости на полный `dt`.
/// На выходе у `bodies` — позиции и скорости после шага (заменяет `separate_bodies` + итерации
/// `apply_contact_impulse` + `integrate`). Статика не меняется. Строки двух точек одной пары решаются
/// блочным решателем пары, как у Rapier в 2D. Кэш читается (память прошлого шага) и перезаписывается
/// точками этого шага; точки, которых в `rows` нет, из кэша уходят.
pub fn step_bodies(bodies: &mut [Body], rows: &[ContactRow], cache: &mut ContactCache, dt: f32);
```

В `packages/engine/core/src/client/collision.rs` (решение пользователя после шага 1.2, вариант «а»):

```rust
impl Manifold {
    /// Точки для `step_bodies`: середины между поверхностями тел, как `SolverContact::point` у parry. Старый
    /// решатель (`apply_contact_impulse`) ждёт `as_slice()` — перепутать их значит тихо разъехаться с хостом.
    pub fn solver_points(&self) -> impl Iterator<Item = Contact>;
}
```

- `Manifold` получает скрытый признак падающего тела (поля и так приватные — аддитивно). `obb_manifold`,
  `as_slice()`, `deepest()` и старый решатель не меняются бит в бит.
- Середина: точка на падающем теле `a` → `p − depth/2·n`, на падающем `b` → `p + depth/2·n`. У спекулятивного
  контакта (`depth < 0`) середина лежит в зазоре, как у parry. Откат к смешанной точке (перекрытая пара без
  точек клиппинга) — точка на `a`.
- Зачем: `obb_manifold` отдаёт точку на поверхности падающего тела, parry — середину; разница depth/2 вдоль
  нормали меняет плечо трения. Замер: косой удар (корпус под 0.3 рад) на шаге удара vx 2.86 против 2.28, ω −4.13
  против −3.96, вторичный удар на шаг раньше; с серединой — совпадение до ~1e-5 на 30 шагах.

Детали реализации (всё — порт исходников Rapier, в doc-комментариях ссылки на файлы Rapier):
- **Построение ограничения** — раз на шаг, по позе начала шага: нормаль `n`; точка `contact.cx/cy`; локальные
  точки в обоих телах; `dist0 = −depth`; проекционная масса нормали и касательной; `v_n0`; `normal_vel =
  is_bouncy · e · v_n0`; `is_bouncy` по сумме импульса из кэша (0 или ключа нет → точка новая); warmstart-импульсы
  из кэша (ключа нет → 0).
- **Пара точек.** Строки с одинаковыми `(a, b)` и соседними индексами в `rows` (две точки одного манифольда) —
  блок 2×2: `r_mat`, обращение, при вырожденности — «лишняя» точка обнуляется, как в `generate` Rapier;
  `solve_mlcp_two_constraints` — дословно по логике Rapier (4 кандидата, выбор по неотрицательности).
  Порядок строк задаёт вызывающий: две точки манифольда подряд.
- **Мягкость и коррекция:** `erp_inv_dt(h)`, `cfm_factor(h)` (из `natural_frequency 30`, `damping_ratio 5` —
  уже есть в `CONTACT_NATURAL_FREQUENCY`, `CONTACT_DAMPING_RATIO`), `ALLOWED_LINEAR_ERROR`,
  `MAX_CORRECTIVE_VELOCITY`. `separate_bodies` внутри не зовётся: проникновение снимает `rhs_bias` на подшагах.
- **Трение** в обоих проходах, конус — от импульса нормали ТЕКУЩЕГО подшага; касательное смещение
  `(p1 − p2)·t / h` в проходе со смещением.
- **Интеграция на подшаге:** `x += v·h`, поворот линеаризован как у Rapier (`cos' = cos − ω·h·sin`,
  `sin' = sin + ω·h·cos`, нормировка) → `angle` через `atan2` и `normalize_angle`.
- **Демпфирование** один раз после подшагов, формула `integrate`: `v *= 1/(1 + dt·damping)`.
- **Кэш** хранит на ключ `{ warmstart_normal, warmstart_tangent, total_normal }`. Реализация без аллокаций в
  установившемся режиме: два `Vec`, отсортированных по ключу, меняются местами на каждом шаге (строк
  единицы, `HashMap` не нужен).
- **Пустой `rows`:** те же подшаги без ограничений. Итог отличается от `integrate` только линеаризацией поворота
  (у Rapier она есть и без контактов), это проверяет тест против Rapier.
- **Устойчивые имена тел для ключа** (`ContactKey::new(a, b, point)`) — обязанность вызывающего, индексы в
  срезе `bodies` для этого не годятся: в игре партнёр-стена получает новый индекс в `sim` на каждом шаге
  (`static_body(hit.block_x, hit.block_y)`). Схема имён для игры (шаг 5.2): блок стены — уровень +
  индекс блока в `levels.static_blocks(level)`; страж рампы — индекс в `self.guards` со своим префиксом;
  предсказанное тело — его id в подсистеме; свой танк — константа. Имя упаковывается в `u32` с префиксом рода
  тела в старших битах. `BlockContact` индекса блока не несёт (только `block_x`, `block_y`), а новое поле в
  публичной структуре с открытыми полями сломало бы код, который строит её литералом; поэтому индекс блока
  игра получает сама — сбором по блокам уровня с перечислением (`enumerate` над `static_blocks(level)` и
  `obb_manifold` на каждый, как делает `collect_block_contacts_into`) или поиском по центру. Способ — на шаге 5.2,
  API движка не меняется.
- **Фильтр `keep_solver_contact`** Rapier (точка в решатель идёт, если `dist < prediction` или
  `dist + v_n·dt < prediction`) — вызывающий уже отсекает по `prediction`; в doc-комментарии указать, что `rows`
  обязан собираться с тем же `prediction`, что `soft_ccd_prediction` хоста.

Экспорт — через `pub mod client` (`client/mod.rs`): проверить, что новые имена доступны как
`vimp_engine_core::client::rigid_body::{step_bodies, ContactRow, ContactKey, ContactCache, SOLVER_SUBSTEPS}`.

## Шаги

Каждый шаг — тест, затем код. После каждого шага — `cargo test --quiet` в `packages/engine/core`
(или `npm run core:test`).

### Шаг 1. Причина A ✅ выполнен

1. Тесты в `rigid_body.rs`, до реализации (падают, потому что функций ещё нет). Реплика получает тот же старт,
   что Rapier в эталоне этапа 1 (шаг 0), контакты — `collision::obb_manifold(tank, wall, 6.0)` на позе начала шага, ключи —
   `ContactKey::new(0, 1, i)`, кэш живёт через шаги:
   - `step_bodies_matches_rapier_across_gap_regimes` — **критерий приёмки**: все режимы таблицы эталона (этап 1, шаг 0), `vx` на
     шаге удара и на следующем совпадают с Rapier с допуском 0.1, проникновение — как у Rapier ±0.01
     (у него до 0.041), `vy` и `ω` — как у Rapier ±1e-2 (абсолютный). Прежнее «|vy|, |ω| ≤ 1e-3» было ошибкой
     плана: сам Rapier даёт vy ≈ 3e-3 — у почти симметричной пары ветку блочного решателя выбирает округление f32,
     бит в бит её не повторить (причина — в комментарии теста);
   - `a_contact_that_pushed_last_step_does_not_bounce`: второй шаг режима 0.77 — `|vx| < 0.1` (отскок был бы ≈ −6.8);
   - `rotated_hull_at_the_wall_matches_rapier` — **критерий приёмки**: корпус под 0.3 рад входит в стену, все 30
     шагов (включая вторичный удар) `vx`, `vy`, `ω` как у Rapier ±0.1;
   - `solver_points_*` (в `collision.rs`): середина при перекрытии и при зазоре, для падающего `a` и для падающего
     `b`; `as_slice()` прежний;
   - `ContactRow::from_manifold`: две точки подряд, ключи `key_base` с номером 0/1, точки — `solver_points()`;
   - `a_gap_not_closed_this_step_is_untouched`: зазор больше пути за шаг → итог = `integrate` без контакта;
   - `two_point_manifold_does_not_slide_sideways`: лобовой удар двумя точками — `|vx|`, `|ω|` на порядок меньше,
     чем у последовательного `apply_contact_impulse` с `SOLVER_ITERATIONS = 4`;
   - `resting_contact_stays_at_rest`: тело лежит у стены (глубина ≈0) с нулевой скоростью 60 шагов — не дрожит и
     не уходит (warmstart + мягкость);
   - `penetration_is_removed_like_rapier`: стартовое перекрытие 0.5 — глубина через 1, 5, 20 шагов совпадает с
     Rapier (тот же помощник с `wall_face` < 4) с допуском 0.01;
   - `no_contacts_matches_rapier`: пустой `rows`, тело с `v` и `ω` — поза и скорости через 10 шагов совпадают с
     Rapier (линеаризация поворота);

## Риски

1. **Точность порта TGS.** Решение — повторить подшаги Rapier, а не приблизить их; критерий — таблица шага 0
   с допуском 0.1. Остаются расхождения порядка ошибок f32 (у Rapier SIMD-путь и `enhanced-determinism`). Если
   какой-то режим не сходится после честного порта — остановиться с замерами, допуск не ослаблять.
2. **Ключи точек.** Parry сопоставляет точки манифольда между шагами по id признаков (вершина/грань); реплика —
   по номеру точки после клиппинга. Если порядок точек `obb_manifold` меняется между шагами (корпус
   проворачивается), warmstart попадёт не в ту точку. Проверить тестом на повороте корпуса у стены; при
   расхождении — доложить (вариант: ключ из id вершины падающей грани).
3. **Откат/реконсиляция в игре.** Кэш — новое состояние предиктора; решено: копия в истории снимков на каждый
   шаг, откат вместе с уровнем (шаг 5.2). Остаток: память хоста на тот же шаг реплике неизвестна, её память —
   лучшее приближение.
4. **Другие игры на движке** (`vimp-snakes`, шаблон `create-vimp-game`). `apply_contact_impulse`,
   `separate_bodies`, `integrate` не меняются, поэтому их физика прежняя. Правка `obb_manifold` меняет их
   поведение в угловом случае — в сторону хоста. Упомянуть это в отчёте. Проверить
   `grep -rn "obb_manifold\|apply_contact_impulse" packages/create-vimp-game` на шаблон.
5. **Ящики карты и чужие танки.** Они тоже в `sim` и в `step_bodies` получат ту же физику. Если сценарии с
   ящиками (`crate*`, `bridge*`) покраснеют — доложить, не чинить молча.
6. **Стоимость.** 4 подшага × 2 прохода вместо 4 итераций: примерно вдвое больше работы решателя на шаг
   предсказания. Строк единицы, но реплей реконсиляции гоняет десятки шагов за кадр — замерить в игре на шаге 5.
