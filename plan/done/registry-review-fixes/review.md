## F1. `deploy.yml`: `toJSON(matrix.settings)` пишет многострочный JSON 🔴

**Где.** `.github/workflows/deploy.yml:240`:

```yaml
VIMP_DEDICATED_ROOM: ${{ toJSON(matrix.settings) }}
```

**Что не так.** Функция `toJSON` GitHub Actions форматирует объекты и
массивы *с отступами и переводами строк* (компактно печатаются только
скаляры и `null`). Для `settings: { maxPlayers: 8 }` переменная получает

```
{
  "maxPlayers": 8
}
```

Дальше в скрипте `echo "VIMP_DEDICATED_ROOM=$VIMP_DEDICATED_ROOM"` пишет
это в `.env.prod` — три строки вместо одной. `env_file` docker compose
читает файл построчно: строка `  "maxPlayers": 8` — не `KEY=VALUE`, и
compose падает на разборе (либо, в старых версиях, молча игнорирует).
Итог: **любой dedicated-бокс, у которого в `SERVERS_MATRIX` задано
`settings`, не поднимется после деплоя** — ровно тот сценарий, ради
которого этап 5 и делался.

Проверка `[ "$VIMP_DEDICATED_ROOM" != "null" ]` от этого не спасает: она
ловит только отсутствие поля.

**Почему не поймали.** Тест `tests/config/env.test.js` проверяет
`readDedicatedRoom` — движковую сторону, которая получает уже готовую
строку. Строку формирует workflow, а его не покрывает ничто.

**Решение** — этап 1 (`stage_1.md`): схлопывать JSON в одну строку на
раннере через `jq -c` (он есть на `ubuntu-latest`) до передачи в
ssh-action, плюс защита на сервере от значения с переводом строки.

## F2. Двойной `lookup` на каждое нажатие «Load» 🟠

**Где.** `packages/engine/src/client/components/view/Games.js:113-115`:

```js
this._lookupBtn.onclick = () => this._emitLookup();
packageField.onblur = () => this._emitLookup();
```

**Что не так.** Порядок событий в браузере при клике по кнопке:
`mousedown` → `blur` поля → `mouseup` → `click`. То есть нажатие «Load»
при сфокусированном поле пакета публикует `lookup` **дважды**. Каждый
`lookup` — это `GET /games/lookup`, а на стороне мастера:

1. скачивание тарболла игры из npm (`store.inspectPackage`);
2. распаковка и структурная проверка;
3. `store.publishedVersions` — ещё один поход в реестр;
4. `fetchPackageMeta` — третий.

Плюс обе попытки тратят по единице общего лимитера
(`gameSubmitLimiter`, 5 запросов в минуту на пользователя,
`master/lobby.js:121`), который делится с `submit` и `requestVersion`.
Один цикл «ввёл пакет → Load → Submit» съедает 3 из 5; вторая попытка
(опечатался в имени) упирается в `tooManyRequests`.

**Решение** — этап 5, п. 5.1: запоминать последний разобранный
`packageName@version`, гасить повтор и держать флаг «запрос в полёте».

## F3. `submit` скачивает тот же тарболл второй раз 🟠

**Где.** `master/gameRoutes.js:169` (`store.inspectPackage`) и `:187`
(`packageMeta`).

**Что не так.** Штатный путь формы — сначала `lookup` (скачивание +
распаковка + проверка + пакумент), затем `submit`, который делает ровно
то же самое ещё раз. Заявка обходится платформе в два скачивания
тарболла (до `maxTarballBytes` каждый) и два похода в npm вместо одного.

Отказаться от проверки в `submit` нельзя — это единственная защита от
прямого вызова роута в обход формы. Правильный размен — короткоживущий
кэш вердикта по ключу `packageName@version`, который наполняет `lookup`
и потребляет `submit`.

**Решение** — этап 5, п. 5.2.

## F5. Игру невозможно удалить 🟠

**Где.** Весь путь реестра. В `packages/auth/src/main.js` есть
`POST /games`, `POST /games/:id/version`, `GET|PATCH /admin/games/:id` —
и ни одного `DELETE`. В `UserRepository` нет метода удаления,
в `GameRegistryProxy` — вызова, в клиенте — кнопки.

Единственное, что доступно админу, — `status: 'disabled'`: игра
пропадает из каталога, но остаётся в очереди модерации, продолжает
занимать `id` и `lower(package_name)` (уникальный индекс
`games_package_lower_idx`) и считается в потолке `maxPerUser = 20`
заявок автора. Ошибочно заведённую заявку убрать нечем.

**Решение** — этап 2: `DELETE` во всех трёх слоях + кнопки в обеих
карточках.

## F6. Порядок проверок в `PATCH /admin/games/:id` 🟡

**Где.** `packages/auth/src/main.js:509-523`.

`resolveAuthor` (а внутри — `SELECT … FROM users`) выполняется **до**
`userRepo.getGame(req.params.id)`. Для запроса к несуществующей игре с
неизвестным ником ответ будет `404 unknownUser` вместо `404 unknownGame`
— сообщение уводит админа не туда. Плюс лишний запрос в БД на заведомо
провальном пути.

**Решение** — этап 5, п. 5.3: сначала `getGame`, потом `resolveAuthor`.

## F7. `fetchPackument` и `fetchPackageMeta` — один и тот же код 🟡

**Где.** `master/npmRegistry.js:34-96` и `:100-160`.

Различаются заголовком `accept`, поведением на 404 и разбором тела.
Совпадают: построение URL, `try/catch` вокруг `fetchImpl`, три текста
ошибок, проверка `res.ok`, разбор JSON. Тексты ошибок дублируются
дословно — разъедутся при первой же правке формулировки.

**Решение** — этап 5, п. 5.4: приватный `requestPackument(url, accept,
{fetchImpl, timeout, packageName})`, возвращающий `null` на 404; обе
экспортированные функции строятся над ним.

Этап 2 добавил маршрут `GET /games/lookup` (`master/lobby.js:611`), а

намеренно продублированы — общей зависимости между пакетами нет) и

## F12. `VIMP_ADMIN_NICKS`: захват свободного ника 🔵

**Как это работает сейчас.** `packages/auth/src/main.js:148-155`:

```js
async function issueIdentityToken(user) {
  const isEnvAdmin = config.admin.nicks.includes(user.nick.toLowerCase());
  const role = await userRepo.syncRole(user.id, isEnvAdmin);
  return jwtLib.signIdentityToken({ sub: user.id, nick: user.nick, role });
}
```

`syncRole` (`UserRepository.js:750`) ставит `admin` тому, кто в списке,
и снимает роль у всех остальных `admin`. Ник глобально уникален без
учёта регистра (`002_nick_case_insensitive.sql`), `setNick`
(`UserRepository.js:216`) работает только при `nick IS NULL`, то есть
**переименования нет**, а сравнение со списком приведено к нижнему
регистру с обеих сторон.

**Вывод по прямому вопросу заказчика: зайти под ником уже
зарегистрированного админа нельзя.** Ник занят строкой в `users`,
второй пользователь его не получит ни в другом регистре, ни через
другого OAuth-провайдера, и роль он получить не может.

**Что действительно уязвимо — «свободный ник».** Роль привязана к
*строке ника*, а не к личности. Если ник из `VIMP_ADMIN_NICKS` ещё не
занят в БД — новый деплой, новая БД, добавили в список ник человека,
который ещё не входил, опечатались в списке — то **первый, кто
зарегистрируется под этим ником, станет админом**. OAuth-вход открыт
всем, `POST /nick` — тоже, а гонка выигрывается одним запросом. То же
самое произойдёт, если админ когда-нибудь будет удалён из `users`
(сейчас удаляются только анонимные строки, но `deleteIfAnonymous`
существует).

Смежное, менее острое: `role` в токене — подсказка интерфейсу, но
мастер принимает решения именно по ней (`master/adminAuth.js:61`), см.
F13.

Dev-вход (`devLogin.js`) даёт произвольный ник и, значит, админа кому
угодно — но маршрут регистрируется только при `NODE_ENV !== 'production'`
(`main.js`), в проде его физически нет. Это в порядке.

**Решение** — этап 4: пин по личности провайдера (`provider:uid`) как
приоритетный источник админских прав + предупреждение при старте о
незанятых админских никах.

## F13. Роль в токене мастера живёт до 4 часов 🔵

`master/adminAuth.js:9-20` подробно объясняет, почему клейма `role`
достаточно: любая запись уходит в auth, где роль перечитывается из БД,
а единственный «пишущий» роут мастера (`POST /admin/games/:id/stage`)
начинается с `GET /admin/games` в auth и разжалованному вернёт 403.
Рассуждение верное. Но оно держится на *порядке действий внутри
`stage`*, который ничем не закреплён: переставь походы местами при
рефакторинге — и разжалованный админ сможет 4 часа занимать диск
мастера скачанными пакетами.

**Решение** — этап 4, п. 4.4: тест, фиксирующий, что `stage` не трогает
`GameStore`, если `registry.listAll` ответил 403.

## Что проверено и признано корректным

- `loadGamePackage` (`client: 'lazy'`): форма результата одна при обоих
  режимах, `loadClientPlugin()` кеширует промис, `assertPluginMatchesManifest`
  вызывается и на ленивом пути. Единственный потребитель `clientPlugin`
  в Node — `devtools/pluginLoader.js`, и он просит `client: true`.
- `GameStore._stagePackage`: id из недоверенного манифеста проходит
  `GAME_ID_PATTERN` и `RESERVED_GAME_IDS`, отказ — вердиктом, не броском
  (контракт модуля сохранён). `.staging` в корне не может столкнуться с
  каталогом игры: `GAME_ID_PATTERN` не допускает точку.
- `ensurePackage`: гонка двух загрузок одной версии разрешается через
  `has()` после отказа `rename` — корректно и идемпотентно.
- `normalizeRepoUrl`: все формы `repository` из npm приведены к
  `http(s)`; userinfo (`https://evil@github.com/...`) вырезается;
  всё, что не `http(s)`, становится `null` — `javascript:` в `href` не
  доедет ни до БД, ни до представления.
- `dedicated/main.js`: ужесточение условия до
  `ref.includes('/') && PACKAGE_NAME_PATTERN.test(ref)` — правильное
  отступление от буквы плана, иначе id `tanks` качался бы из npm как
  чужой безскоупный пакет.
- Миграция `011_drop_superadmin.sql` и порядок выката (auth → мастера)
  описаны верно; `syncRole` действительно делает `VIMP_ADMIN_NICKS`
  единственным источником роли.
- `.github/deployment/lib/common.sh`: вынесение общих функций устранило
  реальный риск расхождения валидации origin и генерации Nginx-конфига
  между двумя сценариями; `scp -r` в документации исправлен верно
  (без него `lib/` не уехала бы на сервер).
