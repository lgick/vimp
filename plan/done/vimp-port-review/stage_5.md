# Этап 5. Журнал плагина: `[Unreleased]` на шесть опубликованных версий ✅ выполнен

**Репозиторий**: `vimp-tanks`, рабочая директория
`/Users/dmitry/Sites/my/vimp-tanks`.
**Объём**: S. **Зависит от этапов 1–4** — их записи тоже попадут в
`[Unreleased]` и должны быть разложены вместе со всеми.

Кода этап не касается вообще.

## Проблема

```bash
cd /Users/dmitry/Sites/my/vimp-tanks
grep -n "^## \[" CHANGELOG.md
# 8:## [Unreleased]
# 89:## [0.6.0] - 2026-08-09
node -p "require('./package.json').version"   # 0.10.0
git log --oneline --grep="^chore: release"    # 0.8.0, 0.8.1, 0.9.0, 0.10.0 и ранее
```

После `## [Unreleased]` сразу идёт `## [0.6.0]`, при том что опубликованы
0.7.0, 0.7.1, 0.8.0, 0.8.1, 0.9.0 и 0.10.0. То есть весь накопленный за
перенос материал (в том числе протокольный блок про кадр v4/v5) лежит в
«неопубликованном», хотя он давно у пользователей. Потребитель пакета не может
понять, в каком релизе появилась поддержка `optionalFrom` и `angvel`.

Дефект **унаследованный**: та же картина была до начала переноса — проверить
`git show 8817036~1:CHANGELOG.md | grep -n "^## \["`. Но именно эта задача
положила туда протокольный блок, поэтому чинить уместно здесь.

Вторая, связанная проблема — устаревшее требование внутри записи:

> …(frame v4/v5, requires `vimp-engine` 0.12 / `vimp-engine-core` 0.6)

Актуальные пины: `vimp-engine` `^0.14.0` (`package.json`, devDependencies) и
`vimp-engine-core` `0.8.0` (`core/Cargo.toml`).

## Правки

### 5.1 — разложить записи по фактическим релизам

Сопоставить содержимое `[Unreleased]` с релизными коммитами:

```bash
git log --oneline --format="%h %ad %s" --date=short | grep "release"
```

Известные точки: `7a37dd5` (0.8.0), `8fd25d3` (0.8.1), `ff1a9fc` (0.9.0),
`7e5c2cf` (0.10.0, 2026-08-21); 0.7.0 и 0.7.1 — раньше, найти тем же
запросом. Для каждой версии завести заголовок `## [X.Y.Z] - YYYY-MM-DD` с
датой релизного коммита и перенести под него записи, которые в него вошли
(ориентир — какие коммиты попали в диапазон между релизами:
`git log --oneline <prev-tag>..<tag>`).

Записи, которые появятся на этапах 1–4 этого плана, остаются в
`[Unreleased]` — они действительно не опубликованы.

Если восстановить принадлежность записи к версии по истории не удаётся —
не выдумывать: положить её в ближайший релиз, который её точно содержит, и
не дробить формулировку.

### 5.2 — обновить требование к версиям движка

В записи про кадр v4/v5 заменить «requires `vimp-engine` 0.12 /
`vimp-engine-core` 0.6» на актуальные `^0.14.0` / `0.8.0` — либо, что точнее,
на «минимально требуемые» версии, если 0.12/0.6 действительно минимум, а
0.14/0.8 — просто текущий пин. Проверить по journal'ам движка, в каком миноре
появились `optionalFrom` (`packages/engine/CHANGELOG.md`, 0.12.0) и
`ClientState::game()` / `setId` в `set_map`
(`packages/engine/core/CHANGELOG.md`), и написать честный минимум.

### 5.3 — разобраться, почему шаг датирования не отработал

В `vimp` релизный скрипт (`npm run release`) датирует `[Unreleased]` — там
журнал разложен по версиям. В `vimp-tanks` этого не происходит, а собственного
релизного скрипта в `scripts/` нет (`ls scripts/` — только build/check/audio).
Выяснить, чем релизится плагин (по релизным коммитам: они меняют только
`package.json`, `core/Cargo.toml` и lock-файлы), и либо подключить тот же
шаг датирования, либо зафиксировать в `CLAUDE.md` плагина, что журнал
датируется вручную перед релизом.

Правку релизного процесса **не выполнять молча**: если она выходит за
редактирование журнала, вынести отдельным пунктом и согласовать.
