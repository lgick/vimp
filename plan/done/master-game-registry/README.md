# Динамический каталог игр на мастер-сервере (Этап 1 продукта)

Направление: движок перестаёт знать об играх. Игры живут в реестре БД
auth-сервиса, мастер скачивает одобренные пакеты из npm registry, раздаёт их
с диска и обновляет каталог на лету — без пересборки образа и без рестарта.
Разработчик подаёт заявку из лобби, админ модерирует её там же.

## Контекст

Сегодня список игр зашит в двух местах: игровые пакеты объявлены
зависимостями корневого `package.json` (`@vimp-games/tanks`,
`@vimp-games/snakes`), а каталог — переменной `GAMES_MATRIX` в GitHub Actions
Variables. `GameCatalog` строится **один раз при старте** мастера из
`master:games` и резолвит пакеты в `node_modules`
(`packages/engine/src/master/GameCatalog.js:55`); `Dockerfile:38-52,84-88`
переносит `dist/` всех `@vimp-games/*` в образ.

Следствие: добавить игру = отредактировать `package.json`, пересобрать образ
движка и передеплоить все мастера. Игра стороннего разработчика туда попасть
не может вовсе — нет ни заявки, ни модерации, ни ролей. В `users` нет колонки
роли, на мастере нет ни одного админского роута и ни одного admin-элемента
интерфейса (`docs/en/master.md:413` фиксирует: «there's no admin UI»).

## Принятые решения (не пересматривать при исполнении)

1. **Реестр игр** — таблицы в Postgres **auth-сервиса**. Мастер БД не
   получает и ходит REST'ом, как уже ходит за rank/state/jwks
   (`JwksProxy`, `PlayerDataProxy`, `HostRatingProxy`).
2. **Бандлы** — локальный диск VPS, раздаёт мастер. CDN (unpkg) — будущий
   Этап 2 продукта.
3. **Скачивает и валидирует пакет мастер**; auth хранит только метаданные и
   статусы и остаётся источником авторизации (роль перечитывается из БД).
4. **URL-пространство игр версионное**: `/games/<id>/<version>/…`. Мастер
   переписывает `assetsBase`/`entries` в отдаваемом манифесте — тем же
   приёмом, которым уже переписывает их в dev на `/@fs/`
   (`GameCatalog.js:150-164`). Это то, что позволяет админу играть в новую
   версию, пока игроки играют в одобренную.
5. **Распаковка** — зависимость `tar@^7` (та же библиотека, что использует
   npm) + собственный `fetch` пакумента и проверка `integrity`.
6. **Переход существующих игр** — seed в SQL-миграции
   (`ON CONFLICT DO NOTHING`), лобби не пустеет ни на минуту.

## Важная поправка к исходной постановке

В исходном описании «авто-бот на мастере» гоняет `vimp-contract` и `vimp-sim`
на новой версии. Так делать **нельзя**:

- `checkContract()` (`packages/engine/src/devtools/contract/loadContext.js:85`)
  **импортирует обе половины плагина как живые модули**, а `vimp-sim`
  исполняет wasm-ядро игры. Для опубликованного пакета это исполнение
  недоверенного кода в процессе мастера.
- В тарболле лежит только `dist/` (`files: ["dist"]`), поэтому большинство из
  34 правил контракта (`package.json`, `vite.config.js`, `core/Cargo.toml`,
  `src/**`) всё равно вернут `skip`.

Поэтому на мастере — **структурная валидация без исполнения кода** (новый
`gamePackageCheck.js`, эталон проверок — `devtools/contract/rules/a6-manifest.js`).
Полный `vimp-contract` и `vimp-sim` остаются инструментами разработчика и его
CI. Прогон в песочнице — будущий Этап 2 продукта.

## Вне объёма

Фоновый сканер новых версий, уровни доверия `Trusted`, автоаппрув патчей,
Cloudflare/CDN, роль `moderator`, назначаемая из интерфейса. Схема БД и REST
рассчитаны на них — переписывать сделанное здесь не придётся.

## Влияние на релиз (CLAUDE.md → Release impact)

Публикуемый артефакт — npm `vimp-engine`, уровень **minor**
(`### ⚠️ Breaking` в `0.x`). Новая рантайм-зависимость `tar`. Крейт
`vimp-engine-core` не трогается, `ENGINE_API_VERSION` остаётся 4, из
`packages/engine/contract/surface.json` ничего не удаляется. `packages/auth`
не публикуется. Репозитории игр следовать не обязаны.

## Общие правила исполнения

- Каждый этап заканчивается зелёными `npx eslint .` и `npm test -- --silent`.
- Любое функциональное изменение сопровождается тестом в том же изменении
  (тесты живут в `tests/`, зеркалят `packages/engine/src/`, не колокейтятся).
- Документация правится в обеих ветках (`docs/en/` — канон, `docs/ru/` —
  зеркало) в том же изменении. Сводная таблица «что куда» — в
  [stage_5.md](stage_5.md).
- Коммиты не делать: изменения остаются в рабочем дереве для ручной проверки.
