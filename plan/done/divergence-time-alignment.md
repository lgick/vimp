## 1. Термины и устройство (что нужно знать)

**Детектор рассинхрона предикта** — отладочная проверка: насколько клиентское предсказание своего танка расходится с
авторитетным состоянием сервера. Включается только секцией `divergence` конфига клиентского ядра (в проде её нет).

Цепочка:

1. Клиентское ядро (Rust, крейт `vimp-engine-core`, `packages/engine/core/`), `ClientState::push_frame`
   (`packages/engine/core/src/client/game.rs`, ≈ строки 240–290) получает бинарный кадр сервера. Если в кадре есть
   player-блок (авторитетное состояние своего актора `[f32; PLAYER_STATE_LEN]`, раскладка — игровая), то:
   - `observe_divergence(&player, frame.server_time, offset, local_now)` (≈ строки 464–495) снимает
     `self.game.predicted_state()` — **текущее** состояние реплики игры — и отдаёт `DivergenceTracker::observe`;
   - затем `self.game.on_server_state(...)` — реконсиляция: игра затирает предикт авторитетным состоянием и
     переигрывает историю ввода от момента кадра до «сейчас».
2. `DivergenceTracker` (`packages/engine/core/src/client/divergence.rs`) покомпонентно считает `predicted − authoritative`,
   копит `samples`/`violations`/`maxDelta`, записи с превышением порогов кладёт в кольцевой буфер; наружу —
   `ClientCore.take_divergence()` (JSON).
3. Headless-раннер (JS, `packages/engine/src/devtools/`): `ScenarioRunner.js` крутит матч по сценарию,
   `VirtualClient.js` — клиент без PixiJS, `invariants.js` → инвариант 9 `predictionDrift` (FAIL, если есть записи с
   превышением порогов сценария `divergence.thresholds`), `report.js` — отчёт. Запуск из игры:
   `npm run sim:scenarios` (= `node node_modules/vimp-engine/bin/vimp-sim.js ...`; у игры `vimp-engine` подключён
   через `npm link` на `packages/engine`, поэтому JS-правки движка видны игре сразу, без релиза).

**Время.** Клиентское локальное время `local_now` (мс). Кадр несёт `server_time`; `offset` оценивает интерполятор,
момент кадра в локальном времени — `server_time − offset`. Предиктор игры шагает фиксированным шагом
(`timeStep` = 1/120 с ≈ 8.333 мс) внутри `GameClientDef::update(local_now)`, которую движок зовёт из
`ClientState::sample(local_now)` (рендер-тик, ≈ строки 307–335 `game.rs`). Состояние реплики относится к моменту
последнего сделанного шага (`local_now` последнего `sample` минус остаток аккумулятора), а **не** к моменту кадра.

## 2. Проблема

`observe_divergence` сравнивает предсказание на момент **последнего рендер-тика** с авторитетным состоянием на момент
**кадра**. Разница моментов Δt даёт ложное расхождение `≈ v · Δt` по позиции (и скачок скорости, если в этот
промежуток был удар о стену).

В headless-раннере Δt — ровно один шаг, по построению цикла `ScenarioRunner.js` (≈ строки 204–230):

```js
for (let tick = 0; tick <= scenario.ticks; tick += 1) {
  // ... ops сценария
  if (tick > 0) {
    await virtualClock.advance(stepMs);   // хост шагает; его кадры сразу уходят клиентам:
                                          // routeFrame → client.pushFrame(bytes, virtualClock.monotonic())
  }
  for (const client of clients.values()) {
    client.render(virtualClock.monotonic());   // → core.sample(now) → game.update(now): предикт догоняет now
  }
}
```

Кадр момента `T` вталкивается (`push_frame`) **до** `render(T)`, когда реплика ещё стоит на `T − stepMs`. Латентность
headless-прогона нулевая (`routeFrame`, `ScenarioRunner.js` ≈ 263–300: «латентность headless-прогона равна нулю»),
поэтому `server_time − offset = T`.

Документация движка сейчас называет это ожидаемым: `docs/en/debugging.md` (и `docs/ru/debugging.md`), раздел
«Prediction divergence detector», пункт «one fixed step of lag» — советует ставить пороги не ниже
`speed × timeStep`. Для игр с быстрыми объектами это превращает порог позиции в функцию максимальной скорости и
маскирует настоящие расхождения на обычных скоростях. Задача — убрать этот сдвиг, а не жить с ним.

### Доказательства (игра `vimp-tanks`, сценарий `tests/scenarios/downtown_surfaces.json`, пороги
`[3, 3, 0.06, 25, 25, 1.5, 0.15, 0.06]` для `[x, y, angle, vx, vy, angvel, …]`)

| Клиент | Что делает | max \|Δ\| позиции | Объяснение |
| --- | --- | --- | --- |
| p1, p5 | едут прямо 260 ед./с | Δy 2.13–2.20 | 260 / 120 = 2.17 — ровно шаг |
| p3 | после плиты-бустера ~490 ед./с | Δx 4.04–4.09 на каждом кадре → FAIL | 490 / 120 = 4.08 — ровно шаг |
| p3 | удар о перила | Δvx 45 (предикт 38.7, кадр −6.7) → FAIL | хост за этот шаг уже отскочил |

Строка отчёта: `sock-p3: serverTime 1700000005866.6667, offset 1700000000000, source 'state': #0 Δ-4.088 > 3
(predicted 244.3394, authoritative 248.4274), replayed 0 input(s) in [5833.33, 5833.33]` (окно `replayed` — от
**предыдущей** реконсиляции: `observe_divergence` вызывается до `on_server_state`).

При этом паритет-тесты игры, где хост и реплика шагают синхронно, на тех же скоростях укладываются в пороги 3/25 —
физика реплики совпадает с хостом; «расхождение» создаёт только момент сравнения. До изменения игры бустер давал
≤ 340 ед./с (340/120 = 2.83 < 3), и сдвиг был не виден.

## 3. Цель и критерии готовности

1. В headless-прогоне предикт сравнивается с кадром на **тот же** момент: у прямолинейно едущего танка Δ позиции ≈ 0
   (< 0.05) независимо от скорости.
2. Пороги сценариев не ослабляются; `"divergence": null` не используется как обход.
3. Существующие тесты движка зелёные (`npx eslint .`, `npm test`, `npm run core:test`), новые тесты фиксируют порядок.
4. Документация (en + ru + `docs/ai/13-debugging.md`) больше не называет шаг отставания ожидаемым для headless.
5. В игре (шаг 8) `downtown_surfaces.json` зелёный без изменения порогов, либо остаток разобран и доложен.

## 4. Варианты (выбор — на шаге 1, с согласия пользователя)

**A. Порядок доставки кадров в headless-раннере (рекомендуется).** `routeFrame` не вталкивает `sendShot` сразу, а
кладёт байты в очередь клиента; в цикле тика после `client.render(now)` очередь сливается через
`client.pushFrame(bytes, now)`. Тогда к моменту `push_frame(T)` реплика уже на `T` (аккумулятор ≈ 0, т. к. шаг
рендера раннера = шагу предиктора), и сравнение точное.
- Правка только в JS (`packages/engine/src/devtools/`), крейт не меняется → релиз крейта не нужен, игре не нужен
  апгрейд `vimp-engine-core`.
- Побочный эффект: кадр попадает в интерполятор на один рендер-тик позже (обрабатывается следующим `sample`). Для
  браузера это реалистично (кадры приходят между рендерами). Проверить, что не ломаются тесты раннера
  (`tests/devtools/ScenarioRunner.test.js`: число кадров, `drift.samples === frameCounts.sendShot - 1`, детерминизм
  `shotHashes`), и последний тик прогона: кадры, пришедшие на последнем `advance`, тоже должны быть доставлены (слить
  очередь и после цикла, либо явно задокументировать).
- Прочие методы `routeFrame` (`sendPing`, `sendFirstShot`, `sendClear`, `sendMap`, …) — не трогать, если нет причины;
  относительный порядок `sendClear`/`sendMap` и отложенных `sendShot` сохранить (кадр старой карты не должен прийти
  после `sendClear`/`sendMap`). Самое простое — очередь сливается и **перед** обработкой любого не-`sendShot`
  сообщения этому клиенту, с тем же `now`.
- Браузер не меняется: там остаётся отставание до одного рендер-кадра (задокументировать как ограничение браузерной
  половины).

**B. Диагностика момента в записи (дополнение к A, по желанию пользователя).** Необязательный метод контракта
`GameClientDef::predicted_state_time() -> Option<f64>` (локальное время шага, к которому относится
`predicted_state()`; дефолт `None`) и поле записи `predictedTime` + `lagMs = (server_time − offset) − predictedTime`.
Ничего не компенсирует, но делает сдвиг видимым в отчёте. Меняет крейт и контракт → `### Added` в
`packages/engine/core/CHANGELOG.md`, запись в `packages/engine/contract/surface.json` (добавление, не удаление),
`docs/*/plugin-api.md`, `docs/ai/`. Игре потребуется реализовать метод, чтобы получить поле.

**C. Отвергнутые.**
- Экстраполяция `predicted + v·Δt` — неверна на контактах и поворотах.
- Вызов `game.update(local_now)` внутри `push_frame` перед сравнением — детектор начнёт менять измеряемое (лишние шаги,
  эффекты, история уровня у игры).
- История предсказанных состояний в игре (`predicted_state_at(t)`) — дорого и не решает случай, когда кадр новее
  последнего шага реплики (ровно случай headless).

Рекомендация: **A**; B — только если пользователь захочет видеть сдвиг в отчётах браузера.
