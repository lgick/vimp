## F1 🔵 Недоверенная контрольная точка переписывает конфигурацию Worker'а преемника

**Где:** `client/network/Promotion.js:305` и `:331-337`,
`client/network/HostPrewarm.js:111-114`,
`lib/createHostRuntime.js:166-185` (`ROOM_SETTING_KEYS` включает
`isDevMode`), `lib/applyRoomOverrides.js:59-60`,
`lib/createHostRuntime.js:188-192` (`import(room.game.hostEntryUrl)`).

**Что не так.** Контрольная точка приходит бете от другого игрока — хоста,
которому нельзя доверять. `Promotion._start` берёт
`meta.room.settings` **целиком** (`{ ...meta.room.settings }`) и
разворачивает его в `room` Worker'а поверх собственных полей беты:

```js
const room = { ...prepared.room, ...settings, hostSocketId, roomId, epoch };
```

В прогретом пути (`warm.prepared`) `prepared.room` — другой объект, и
любые ключи точки перекрывают его: `game` (а значит `hostEntryUrl` и
`wasmUrl` — Worker делает `import(room.game.hostEntryUrl)`), `isDevMode`
(dev-команды игры, например `/nr` в tanks, рекордер, CONSOLE всем игрокам),
`maps`, `seed`, `mapsVersion`. Честный хост тоже кладёт в точку
`isDevMode` (его включает `pickRoomSettings`).

Отдельно: версия игры для подготовки комнаты берётся из точки
(`meta.room.game`), и мастер её не подтверждает — хост может заставить бету
поднять другую версию той же игры, лежащую на мастере (например,
застейдженную).

**Сценарий.** Хост с изменённым клиентом шлёт бете точку с
`room.settings = { isDevMode: true, game: { hostEntryUrl: '/games/<другая>/…/host.js', … } }`.
После промоушена бета поднимает чужой бандл (в проде CSP
`script-src 'self'` ограничивает его своим origin, в dev — любой URL) или
работает в dev-режиме, где любой игрок перезапускает раунд.

**Причина.** На мастере для холодного пути настройки санируются
(`sanitizeRoomSettings`), а для пути через точку — нет.

## F2 🔴 Плановая передача всегда теряет финальную точку

**Где:** `master/MigrationCoordinator.js:629-638` (широковещательный
`host_migrating` в `beginHandoff` исключает только хоста),
`client/main.js:4087-4098` (обработчик `host_migrating`),
`client/network/SessionSupervisor.js:274-299` (`migrate()` →
`_dropTransport()` → `WebRtcManager.destroy()` → `pc.close()`),
`client/network/StandbySender.js:104-127, 155-177` (`refresh()` при
закрытии пира беты сбрасывает `_pendingFinal`).

**Что не так.** Канал `standby` открыт поверх **того же**
`RTCPeerConnection`, что игровой транспорт беты к хосту. Мастер шлёт бете
`promote {mode: 'planned'}` и сразу следом `host_migrating`. Супервизор
беты на `host_migrating` закрывает транспорт — а с ним pc и канал
`standby`. Финальная точка идёт по цепочке «мастер → хост → Worker →
gzip → DataChannel → бета» и почти никогда не успевает раньше
`host_migrating`, который бета получает напрямую от мастера. Хост, увидев
закрытие пира беты, ещё и выбрасывает ждущую отправки финальную точку.

**Итог.** `Promotion._pickCheckpoint` ждёт финальную `finalWaitMs` (3 с)
впустую и поднимает матч из последней периодической точки. Плановая
передача — это пауза +3 с и откат ~0,5 с для всех, то есть ровно то, чего
она должна была избежать («продолжение с того же тика»). Тестами не
ловится: `main.js` не покрыт, а модульные тесты Promotion/StandbyReceiver
кладут точку в приёмник напрямую.

## F3 🟠 Разморозка после сорвавшейся передачи «перезаводит» хост-игрока

**Где:** `host/HostGame.js:1523-1537` (`unfreeze` →
`_sendResumeEntry` всем `getNetworkedReady()`),
`client/main.js:849-867` (обработчик FIRST_SHOT_DATA шлёт
FIRST_SHOT_READY, если `supervisor.resuming` ложен),
`host/HostGame.js:681-715` (`firstShotReady` без проверки готовности).

**Что не так.** Пакет полной синхронизации после `unfreeze` уходит всем
подключённым готовым участникам, в том числе хост-игроку на loopback (гости
к этому моменту уже бросили транспорт по `host_migrating`). Пакет содержит
FIRST_SHOT. Клиент хост-игрока не в режиме возобновления, поэтому отвечает
FIRST_SHOT_READY, и хост повторно выполняет `firstShotReady`: всем уходит
`USER_JOINED` («<хост> joined the game»), хост-игроку — `initialVote`
(окно выбора команды в tanks), а в игре с `noSpectators` (snakes)
`admitPlayer` заново ставит уже играющего на точку респауна.

**Когда.** Каждая сорвавшаяся плановая передача: финальная точка
снимается на заморозке всегда, значит `_drainedWhileFrozen` всегда
истинен.

## F4 🔴 Оффер гостя во время миграции даёт `unknownRoom`, и гость уходит из живой комнаты

**Где:** `master/SignalingServer.js:950-979` (`_onWebRtcOffer`),
`master/MigrationCoordinator.js:186` (`_unbindHost` в `hostLost`),
`client/main.js:1905, 2174-2180, 4204-4211` (`awaitingAnswer`,
`handleSignalingError`).

**Что не так.** Как только мастер перевёл комнату в `migrating`, сессия
хоста отвязана, и `_onWebRtcOffer` отвечает на любой оффер
`error {code: 'unknownRoom'}` (код `migrating` с повтором — только для
`handing_off`). Клиент на `unknownRoom` при `awaitingAnswer === true`
вызывает `leaveRoomWith('Room no longer exists…')`. `awaitingAnswer`
ставится на каждую попытку транспорта и снимается только на `open`; на
`host_migrating` транспорт бросается, а флаг остаётся `true`.

**Сценарий (типичный).** Хост закрыл вкладку. Гость замечает обрыв
DataChannel почти одновременно с мастером, супервизор сразу делает первую
попытку переподключения (оффер с `resume`). Мастер уже отвязал хоста —
ответ `unknownRoom`. Даже если гость успел получить `host_migrating`,
флаг `awaitingAnswer` всё ещё `true` → гость уходит в быструю игру, хотя
через 1–3 с комната получила бы нового хоста. То же для комнаты `online`
с отсоединённым хостом (обрыв WS хоста без кандидатов): гость, у которого
моргнула сеть, уходит из комнаты, где P2P-матч жив.

**Причина.** Ошибки мастера не привязаны к запросу (нет поля «на что это
ответ»), а клиент решает по глобальному флагу.

## F5 🔵 Членство в комнате самозаявляемое: «фантомы» искажают счётчик, голосование, кворум и выбор преемника

**Где:** `master/SignalingServer.js:884-934` (`_onJoinRoom` — нужен только
валидный токен), `master/RoomRegistry.js:608-618` (`currentPlayers`),
`master/HostVoteManager.js:120-125, 176-201` (`eligible` и голоса — по
`memberId`), `master/MigrationCoordinator.js:854-892, 941-961` (отчёты
`host_unreachable` и кворум — по `memberId`), `master/successor.js`.

**Что не так.** `join_room` принимает любого с валидным токеном и любым
UUID `memberId`, без доказательства, что он вообще подключён к хосту. Один
аккаунт может открыть N сигнальных сессий и войти в чужую комнату N
«фантомами». Все счётчики мастера считают по `memberId`:

- `currentPlayers` растёт → комната выглядит полной: быстрая игра её
  обходит, прямая ссылка уводит в быструю игру (`decideRouteAction`
  сравнивает `currentPlayers >= maxPlayers`);
- голосование `/changehost`: N голосов от одного пользователя → снятие
  любого хоста (+ запрет ему на 10 минут) и принудительная миграция;
- кворум `host_unreachable`: N отчётов → принудительная миграция раз в
  `forcedMigrationCooldownMs` (30 с) — откат мира у всех;
- преемник: фантом с `caps.canHost` и хорошим RTT до мастера становится
  бетой (канал `standby` ему не открыть — пира нет), а в аварии —
  холодным кандидатом: 25 с ожидания на каждого. Зловредный фантом может и
  принять промоушен — занять чужую комнату.

## F6 🟠 Комната на двоих: один отчёт гостя снимает хоста

**Где:** `master/MigrationCoordinator.js:956`
(`quorum = Math.max(1, Math.ceil(guests / 2))`).

При одном госте кворум — 1. Гость, у которого не сходится P2P (его NAT),
отчитывается, хост отвечает на пробу, мастер принудительно отдаёт роль
гостю. Тот же путь в обратную сторону, скорее всего, тоже не сойдётся:
бывший хост отчитается, и через 30 с роль уйдёт обратно — «пинг-понг» с
откатами. Заодно любой гость комнаты на двоих забирает роль хоста когда
захочет.

## F7 🟠 «Призрачное» членство после выхода без перезагрузки

**Где:** `client/main.js:1573-1660` (`handleDisconnect` не шлёт
`leave_room`), `master/SignalingServer.js:521-569, 810-814`
(`register_host`/`_bindHost` не снимают прежнее членство сессии).

После кика (лобби-режим уводит на главную **без** перезагрузки, вкладка и
её сигнальная сессия живы) мастер продолжает считать вкладку участником
комнаты: она в `currentPlayers`, в голосовании и кандидат в беты. На
`promote` такая вкладка молчит (`handlePromote` выходит по
`!currentRoomId`) — мастер ждёт её `coldPromotionTimeoutMs` (25 с), прежде
чем взять следующего. То же, если вкладка без перезагрузки создаёт свою
комнату.

## F8 🟠 Свежесть точки беты меряется по приходу статуса, а не по возрасту точки

**Где:** `master/SignalingServer.js:496-516` (`receivedAt: this._now()` на
каждый `standby_status`), `client/main.js:2031-2042`
(`reportStandbyStatus` раз в 5 с шлёт последнюю точку, какой бы старой она
ни была), `master/MigrationCoordinator.js:291-300, 654-669`,
`client/network/StandbySender.js:144-149` (закрытие канала `standby` при
живом пире выключает точки до смены состава пиров),
`client/network/Promotion.js:281-289` (возраст точки не проверяется).

Если поток точек встал (канал `standby` закрылся сам, хост пропускает точки
из-за забитого канала, Worker не снимает точки), бета всё равно раз в 5 с
сообщает старую точку, и мастер считает её свежей. Авария → режим
`checkpoint` из точки минутной давности → откат мира на минуты вместо
холодного старта.

## F9 🟠 После рестарта мастера гости могут остаться вне комнаты навсегда

**Где:** `client/main.js:4069-4082` (на `welcome` один `join_room`, и
только при `!awaitingAnswer`), `master/SignalingServer.js:896-901`.

Деплой рестартует мастер (push в `main`). Реестр пуст, пока хост не вернёт
комнату `reclaim_host`. Гость, чей сигналинг переподключился раньше хоста,
получает на `join_room` ответ `unknownRoom`, и повтора нет. Он продолжает
играть по P2P, но для мастера его нет: не считается в лобби, не кандидат в
беты, не голосует. Если хост потом уйдёт, мастер увидит комнату без людей
и закроет её — гости вылетят в быструю игру. Гость, который в момент
`welcome` переподключал WebRTC (`awaitingAnswer`), не шлёт `join_room`
вовсе.

## F10 🟠 Истечение identity-токена (4 ч) ломает сценарии миграции

**Где:** `client/main.js:4214-4220` (`invalidToken` → `logout()` +
`leaveRoomWith`), `client/main.js:1957-1967` (`memberCaps`),
`client/main.js:2830-2903` (`handlePromote`),
`client/components/model/LobbyAuth.js` (продления нет),
`packages/auth/src/config/auth.js:63` (`expiresIn: '4h'`),
`lib/jwt.js:71` (проверка `exp`).

Токен из `localStorage` живёт 4 часа с момента входа и не продлевается.
Новые потоки предъявляют его посреди матча: `join_room` после
реконнекта сигналинга, `reclaim_host`, `register_host` преемника,
`RESUME_REQUEST`. С истёкшим токеном:

- гость при моргании сети получает `invalidToken` на `join_room` → выход
  из аккаунта и выброс из **работающего** P2P-матча;
- бета с истёкшим токеном получает отказ на `register_host`, уходит из
  комнаты, мастер ждёт `promotionTimeoutMs` (10 с) до следующего
  кандидата;
- хост при реконнекте сигналинга не может вернуть комнату и сам её
  закрывает.

## F11 🟠 Ожидающая эстафета Worker'ов блокирует любую плановую передачу

**Где:** `client/main.js:2710-2728` (`startPlannedHandoff` отказывает при
`workerSwapInProgress`), `client/main.js:3148-3198, 2536-2546`
(`refreshHostWorker` на каждый `host_registered` с новой версией),
`host/meta/core/RoundManager.js:321-328, 345-356`,
`../vimp-snakes/src/config/game.js:99-100, 134` (`endlessRound`,
`mapTime` 1 ч).

После любого деплоя мастер рестартует, хост возвращает комнату, видит
новый `codeVersion` и запускает эстафету Worker'ов — она ждёт границы
раунда (в snakes — смены карты, до часа). Всё это время
`startPlannedHandoff` возвращает `false`: «Hand over host» молча не
работает, «Leave server» уходит аварийным путём (откат у всех),
автотриггеры (скрытая вкладка, перегрузка) не срабатывают, голосование
кончается принудительной миграцией.

## F12 🟡 Тайминги клиента и мастера рассогласованы и ничем не проверяются

**Где:** `config/lobby.js:248-255` (`session.migrationWaitMs` 40 с),
`config/master.js` (`promotionTimeoutMs` 10 с,
`coldPromotionTimeoutMs` 25 с), `master/MigrationCoordinator.js:239-276`
(`_promoteNext`), `client/network/SessionSupervisor.js:274-299`
(`migrate()` при уже идущей миграции ничего не продлевает).

- Цепочка «бета с точкой + два холодных кандидата» = 10 + 25 + 25 = 60 с
  > 40 с: гости уходят в быструю игру, пока мастер ещё ищет хоста.
- Связки «`handoffDeadlineMs` > `handoffTimeoutMs`», «`checkpointMaxAgeMs`
  ≥ 2 × `standbyStatusIntervalMs`», «`migrationWaitMs` ≥ сумма дедлайнов
  промоушена» записаны только в комментариях.
- `hostDefaults.resumeWaitMs` (3000) равен `session.hostSilenceMs` (3000):
  гость, вернувшийся в восстановленный матч первым, до его старта молчит
  почти столько же, сколько сторожок тишины считает смертью транспорта.

## F13 🟡 «Leave server» последнего человека теряет несинхронизированные очки

**Где:** `client/main.js:2818-2826` (`leaveServer` →
`teardownHostRole` → `HostController.destroy` → `worker.terminate()`),
`host/HostGame.js:829-860` (`destroy()` с `flushAll` есть, но в браузере
не вызывается).

Хост, один в комнате, уходит кнопкой — Worker убивается без
`flushAll`: накопленные rank/state всех участников с прошлой
синхронизации (интервал до `minFlushInterval`, 5 мин) пропадают. Это
явное действие пользователя, и корректно завершить матч здесь можно.

## F14 🟡 Красные тесты tanks — следствие этой задачи, а не «давний разрыв»

**Где:** `../vimp-tanks/tests/host/HostGame.test.js:275` и далее (6 тестов
«эстафета Worker'ов (5.2)»).

В отчёте этапа 7c и в памяти записано, что тесты падают «независимо» от

станет красным, как только tanks перейдёт на новую версию движка.

## F18 🟡 `memberId` в оффере не привязан к сессии

**Где:** `master/SignalingServer.js:950-979`,
`client/network/HostConnectionManager.js:210-230`.

Мастер пересылает хосту `memberId` из оффера после проверки только
формата. Гость может назваться `memberId` другого участника (например,
беты), и `peerConnectionOf(memberId)` у хоста вернёт его пир — канал
`standby` уйдёт не туда. Узнать чужой `memberId` сейчас трудно, но
проверка дешёвая: у сессии-участника он уже известен мастеру.

## F20 🟡 Прогрев не сохраняет скомпилированный wasm

**Где:** `lib/createHostRuntime.js:126-163` (`preloadHostRuntime`).

`WebAssembly.Module` из прогрева выбрасывается, на промоушене wasm
компилируется заново (выигрыш прогрева — только HTTP-кэш). Необязательно:
плюс ~50–200 мс к паузе промоушена.

---

## На решение разработчика (в план не включено)

- **D1. Тексты движковых кодов в каждой игре (DRY).** Каждый новый код
  движка (`s:7…11`, `v:6…15`) требует правки обеих игр, шаблона и фикстуры;
  игра без релиза показывает пустоту. Возможный вариант, не нарушающий
  решения «только кодами»: движок держит английские тексты по умолчанию
  для своих кодов, игра их перекрывает. Решение разработчика (память,
  этап 7c) — тексты в играх; без его согласия не трогать.
- **D2. Миграция сразу при обрыве WS хоста.** Короткий обрыв сигналинга
  (Wi-Fi, прокси) у живого хоста почти всегда проигрывает гонку прогретой
  бете: комната переезжает с откатом, хотя P2P цел. Решение 7.0 («хост не
  приоритетен») принято осознанно; вариант — короткая выдержка
  (~1,5 с), если не пришёл `host_leaving`.
- **D3. Продление identity-токена.** Этап 7 этого плана смягчает F10, но
  полностью проблему снимает только тихое продление токена в auth.

## Что сделано хорошо

Протоколы расширяются только добавлением (порты, коды закрытия, сообщения
Worker'а, алиасы `hostId`/`hostSecret`/`mapName`); секреты сравниваются за
постоянное время (`roomSecret`, `resumeKey`, `promotionToken` с проверкой
формата); распаковка чужой точки ограничена 8 МБ; эпохи отсекают поздние
сообщения; идемпотентность записи очков через `writeSeq` продумана вместе
с откатом; тесты на новые модули подробные (3405 зелёных); документация
en/ru и CHANGELOG ведутся в том же изменении.
