# Этап 4 — Wasm-ABI: заморозка, `abi_describe`, `dispatch`

**Почему этот этап особенный.** Всё остальное в плагинном контракте — данные,
которые движок может переписать адаптером на лету. Ядро игры —
скомпилированный бинарник; таблица экспортов фиксируется в момент
`wasm-pack build`. Если `GameCoreAdapter.js` позовёт метод, которого в
годовалом `.wasm` нет, никакой адаптер его не синтезирует. Это единственная
точка, где шим бессилен, и она определяет потолок всей затеи.

Подробный разбор трёх способов сломать игру через ABI (A: новый метод,
B: смена сигнатуры, C: удаление) — в [`original-statement.md`](original-statement.md).
Лечим A и B.

**Результат этапа:** таблица экспортов ядра перестаёт расти; движок узнаёт
возможности загруженного ядра до первого вызова; любая будущая возможность
приезжает опкодом, а не символом.

**Затрагивает крейт `vimp-engine-core` (0.8.4) → minor.** После этапа
обязателен `npm run core:test`.

## 4.1 Заморозка сигнатур

Правило, записываемое в шапку `packages/engine/core/src/abi.rs`:

```
// ЗАМОРОЖЕНО (И3). Имя, арность и типы каждого pub fn ниже неизменны
// НАВСЕГДА. Glue-код wasm-bindgen лежит в dist уже опубликованных игр:
// добавленный аргумент он молча выбросит, и старая игра будет тихо врать
// вместо того чтобы упасть. Нужна другая форма — заведи опкод dispatch
// (см. 4.3), а не правь сигнатуру.
// Страж: tests/devtools/surface.test.js, раздел abi.
```

Замораживаемый набор — сегодняшний, ~26 методов игрового макроса
(`abi.rs:18-256`) и ~15 клиентского (`abi.rs:274+`). Метод из макроса можно
**удалить** (случай C, безобиден: старая игра его всё ещё экспортирует,
движок перестаёт звать) — но не переименовать и не изменить.

Горячий путь остаётся прямыми экспортами и не трогается совсем: `step`,
`apply_input`, `apply_aim`, `pack_body`, `pack_frame`, `body_has_events`,
`frame_ptr`, `frame_bytes`; на клиенте — `push_frame`, `sample`, `hot_ptr`,
`hot_values`. Они вызываются каждый тик, часть — zero-copy через память WASM
(`abi.rs:212`); гнать их через сериализованный конверт означало бы реальную
просадку без выигрыша в гарантии.

Расти будет только холодная половина — жизненный цикл, запросы, отладка,
handoff, конфигурация. Исторически движок добавлял именно туда: `map_info`,
`players_data`, `take_events`, `debug_json`, `serialize_state`,
`deserialize_state`, `remove_players_and_shots`.

## 4.2 `abi_describe()`

Оба макроса начинают генерировать один дополнительный метод:

```rust
pub fn abi_describe(&self) -> String
```

Возвращает JSON:

```json
{
  "abi": 1,
  "core": "0.9.0",
  "ops": ["state.replaySeek", "snapshot.deltaV2"]
}
```

- `abi` — версия самого формата самоописания (не контракта плагина);
- `core` — версия крейта `vimp-engine-core`, с которым собрано ядро; берётся
  из `env!("CARGO_PKG_VERSION")` **крейта движка**, а не игры (внутри макроса
  это `$crate`-контекст — проверить, что раскрытие даёт версию движкового
  крейта; при необходимости зашить константу `pub const CORE_VERSION` в
  `vimp-engine-core` и подставлять её);
- `ops` — список опкодов, которые умеет это раскрытие макроса плюс те, что
  объявила сама игра (см. 4.3).

**JS-сторона.** `packages/engine/src/host/GameCoreAdapter.js` получает
приватный `_describe`, читаемый один раз в конструкторе:

```js
// Метода нет — ядро собрано до появления самоописания. Это не ошибка:
// поколение 0, ни одного опциального опкода (И2).
this._abi = typeof core.abi_describe === 'function'
  ? JSON.parse(core.abi_describe())
  : { abi: 0, core: null, ops: [] };
```

Зачем, если есть `?.`: сегодня движок узнаёт о возможностях ядра **в момент
вызова**, посреди матча — так сделано в `GameCoreAdapter.js:96`
(`this._core.apply_aim?.(…)`) и `:218` (`typeof this._core.debug_json !==
'function'`). Для необязательного вызова этого хватает, но не хватает для
решений, принимаемых заранее: какую ветку упаковки снапшота выбрать,
показывать ли поле в форме создания комнаты, что сообщить лобби.
Самоописание переносит знание на момент загрузки.

Зеркальный `_abi` заводится и в клиентском контуре — `src/client/` там, где
создаётся `ClientCore` (`clientCoreConfig.js` / `client/main.js`).

## 4.3 `dispatch`

Один новый экспорт в обоих макросах:

```rust
pub fn dispatch(&mut self, op: &str, payload: &[u8]) -> Vec<u8>
```

Соглашение:

- пустой возврат (`Vec::new()`) = «опкод не обработан»; движок идёт по
  запасному пути. Это отличается от «обработан, ответа нет» — для второго
  случая возвращается однобайтовый маркер `[0x00]`;
- `payload` и ответ — сырые байты; кодировка на усмотрение опкода (JSON,
  бинарь) и фиксируется в реестре опкодов;
- опкод — строка вида `<область>.<действие>` (`state.replaySeek`,
  `snapshot.deltaV2`), регистрируется в
  `packages/engine/src/config/abiOps.js` (append-only реестр из этапа 3, та
  же форма).

**Расширение со стороны игры.** Трейт `GameSim<G>` (`core/src/sim.rs`)
получает метод **с реализацией по умолчанию** — это обязательное требование
И5, иначе крейты игр перестанут компилироваться:

```rust
/// Игровые опкоды dispatch. Реализация по умолчанию — «не обработано»:
/// игра, которой это не нужно, не пишет ни строки.
fn dispatch_op(&mut self, _op: &str, _payload: &[u8]) -> Option<Vec<u8>> {
    None
}

/// Имена опкодов, которые обрабатывает эта игра — уезжают в abi_describe.
fn dispatch_ops(&self) -> &'static [&'static str] { &[] }
```

Макрос в `dispatch` сначала пытается обработать движковые опкоды (делегация
в `EngineSim<G>`), затем зовёт `dispatch_op` игры, затем возвращает пустоту.

**Ключевое свойство, ради которого всё затевается.** Макрос раскрывается в
крейте игры. Значит, как только игра пересобирается с любым будущим
движком, она получает все опкоды, которые макрос к тому моменту умеет, —
без единой правки своего исходника. Движок раздаёт возможности через макрос,
а таблица экспортов остаётся константной. Расширение вместо изменения
работает буквально.

## 4.4 JS-обёртка вызова

`GameCoreAdapter.js` получает единый метод:

```js
// Единственный разрешённый способ позвать необязательную возможность ядра.
// Прямой вызов нового метода на this._core запрещён (И2): у старой игры
// его нет.
_op(op, payload) {
  if (!this._abi.ops.includes(op)) {
    return null;               // ядро не умеет — вызывающий решает, что делать
  }

  const out = this._core.dispatch(op, payload);

  return out.length === 0 ? null : out;
}
```

ESLint-правило (`eslint.config.js`, `no-restricted-syntax`): обращение к
`this._core.<имя>` разрешено только для имён из замороженного списка;
всё остальное — через `_op`. Сообщение правила ссылается на И1/И2 и на этот
файл плана.

## 4.5 Слепок

Разделы `abi.game`, `abi.client` (из этапа 1) дополняются `abiOps` — списком
зарегистрированных опкодов. Опкоды append-only на тех же правилах: удаление
опкода — удаление возможности, которую могла использовать игра.

Отдельный тест: `abi_describe` и `dispatch` присутствуют в обоих макросах
(защита от того, что кто-то уберёт сам механизм расширения).

## 4.6 Первый настоящий опкод

Чтобы механизм был проверен, а не только объявлен, этап переводит **один
существующий необязательный вызов** на опкод, оставив прямой метод на месте
(И1 — метод не удаляется):

Кандидат — `debug_json` (`abi.rs:240`, feature-detect уже стоит в
`GameCoreAdapter.js:218`). Заводится опкод `debug.json`; адаптер сначала
пробует `_op('debug.json')`, при `null` откатывается на
`this._core.debug_json?.()`. Обе ветки покрываются тестом: ядро с опкодом,
ядро без опкода но с методом, ядро без обоих.

Это даёт живой образец для всех будущих расширений и проверяет цепочку
целиком.

## Changelog

`export_client_core_abi!` now also emit `abi_describe()` and `dispatch(op,

core capabilities arrive as `dispatch` opcodes, not as new exports».
