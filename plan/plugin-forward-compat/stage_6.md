# Этап 6 — Пересборка игр и закрепление правил

Затрагивает **чужие репозитории**: `~/Sites/my/vimp-tanks` и
`~/Sites/my/vimp-snakes`. Правила `CLAUDE.md` (документация, changelog,
тесты, отсутствие автокоммитов) действуют там так же.

**Важно.** Этот этап — не условие работоспособности. После этапов 1–5 обе
игры продолжают работать в старых сборках без единой правки; это проверено
на `gen-api3` в этапе 5. Этап 6 нужен, чтобы игры **получили** новые
возможности и стали образцом для тех ста, которые придут.

## 6.1 Что реально меняется в репозитории игры ⏳ (ждёт публикации крейта и `vimp-engine`)

Почти ничего. `dispatch` и `abi_describe` приезжают из макроса
(`vimp_engine_core::export_game_core_abi!(GameCore)` —
`vimp-tanks/core/src/lib.rs:53`, `vimp-snakes/core/src/lib.rs:61`), строка не
меняется. Игровые `#[wasm_bindgen]`-методы (`set_model`, `sync_panel`,
`try_fire`, `cycle_weapon`) не трогаются — движок их не знает и не зовёт.

Работа сводится к:

1. `cargo update -p vimp-engine-core` до новой версии крейта; при
   необходимости правка `Cargo.toml`.
2. `npm i vimp-engine@<новая>`.
3. `npm run core:build` + `npm run build` — пересборка ядра и пакета.
4. `npm test`, `npm run core:test`, `npx eslint .`.
5. `npx vimp-contract --game .` — зелёный по новому `b2`.

`manifest.requires` **не добавляется**, пока игра не начнёт пользоваться
чем-то опциональным. Для `vimp-snakes` кандидат — `accolades` (игра его
использует): объявить `requires: ['accolades']` в
`scripts/build-game-manifest.js`. Для `vimp-tanks` — проверить, использует ли;
если нет, поле не появляется.

## 6.2 Опциональная реализация `dispatch_op`

Только если у игры есть что ответить. На момент написания плана — нет; обе
игры оставляют реализацию по умолчанию (`None`). Пункт существует, чтобы
исполнитель не искал, что тут делать: **делать нечего, и это правильно**.

## 6.3 Шаблон `create-vimp-game` ✅ выполнен

`packages/create-vimp-game/templates/default/` — то, с чего начнут будущие
сто игр. Правки:

- `scripts/build-game-manifest.js` — писать `requires: []` явно с
  комментарием, объясняющим, когда туда что-то добавляют (сейчас файл
  импортирует `ENGINE_API_VERSION` из `vimp-engine/config/opcodes.js`, строка
  5 — импорт остаётся, число по-прежнему штампуется в манифест как метка
  поколения);
- `src/host/index.js`, `src/client/index.js` — комментарий рядом с
  `engineApi: ENGINE_API_VERSION`, что это метка, а не гейт, и что игра не
  устареет от роста версии движка;
- `tests/config/contract.test.js` — сверить с новым `b2`.

`packages/create-vimp-game/CHANGELOG.md` — `### Changed`.

## 6.4 Правило релиза в `CLAUDE.md` движка ✅ выполнен

Секция «Changelogs» дополняется правилом, закрывающим цикл:

```
**`ENGINE_API_VERSION` заморожен на 4 и не бампается.** Возможность,
добавляемая движком, регистрируется в `src/lib/capabilities.js` и, если
игра обязана её потребовать, объявляется в `GameManifest.requires`.
`⚠️ Breaking` в плагинном контракте допустим только когда движок обязан
отвергнуть ранее принимавшийся ввод (например security-фикс) — и требует
удаления строки из `contract/surface.json` тем же коммитом.
```

Секция «Release impact» дополняется строкой: правка
`packages/engine/contract/surface.json` в сторону удаления — всегда повод
для явного обсуждения.

Ограничение `CLAUDE.md`: файл строго английский и не более 1000 токенов
(идеально 300–600). Сейчас он уже близок к верхней границе — добавляя эти
правила, что-то придётся ужать. Приоритет у нового правила: оно и есть
«бескомпромиссное правило vimp engine» из постановки.

## 6.5 Документация игр ⏳ (ждёт публикации)

В обоих репозиториях игр, `docs/{en,ru}/`:

- `getting-started.md` — про то, что игра не обязана следовать за версией
  движка;
- `architecture.md` — упоминание `dispatch`/`abi_describe`, если игра начнёт
  ими пользоваться (сейчас — нет, значит правки нет).

Правило `docs/en` ↔ `docs/ru` действует в репозиториях игр так же.

## 6.6 Публикация

Порядок обязателен, иначе игра соберётся против неопубликованного крейта:

1. `vimp-engine-core` (крейт) — публикует разработчик.
2. `vimp-engine` (npm) — `npm run release`.
3. `create-vimp-game` (npm).
4. `vimp-tanks`, `vimp-snakes` — после того как крейт и `vimp-engine`
   доступны.

Версии не правятся руками и ничего не публикуется агентом — этим занимается
разработчик (`docs/en/publishing.md`, правило `CLAUDE.md`).

## Проверка этапа

- В каждом репозитории игры: `npx eslint .`, `npm test`, `npm run core:test`,
  `npx vimp-contract --game .` — зелёные.
- `npm run sim -- --game <dist игры>` из репозитория движка — матч проходит.
- Браузерный smoke: `npm run dev` в движке с обеими играми в `node_modules`,
  обе видны в лобби, комнаты создаются, матчи идут.
- Контрольный опыт этапа 5 повторяется **после** пересборки: старая сборка
  под `engineApi: 3` всё ещё запускается рядом с новой. Обе игры в лобби
  одновременно, разных поколений.
- `npm run create:game <dir>` + `npm run test:scaffold` — свежесозданная игра
  собирается и проходит контракт.

## Финальный отчёт

При отчёте о работе назвать (правило «Release impact» в `CLAUDE.md`):

- артефакты: крейт `vimp-engine-core` (minor), npm `vimp-engine` (minor),
  npm `create-vimp-game` (patch/minor), плюс пакеты обеих игр;
- уровень бампа — считывается с подзаголовков `[Unreleased]` в трёх
  журналах;
- репозитории игр обязаны последовать **по желанию**, не по необходимости —
  и это главный проверяемый результат всего плана;
- какие предпубликационные проверки прогонялись.
