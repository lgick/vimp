# Журнал клиентских ошибок (client-reports)

Направление: каждая неперехваченная ошибка браузерного клиента (и явные
предупреждения движка и игровых плагинов) попадает в **один центральный
журнал** — таблицу Postgres auth-сервиса, сгруппированную по отпечатку, с
расшифрованными стеками и статусами «open / fixed / ignored». Смотреть и
закрывать ошибки — во вкладке «Errors» админской панели лобби.

План самодостаточен: исполнителю не нужен контекст беседы, в которой он
составлен. Перед каждым этапом прочитать этот файл целиком и файл этапа.

## Контекст

На проде (dedicated-сервер, круглосуточный матч) клиент падал посреди игры:

```
Uncaught TypeError: Cannot read properties of null (reading 'x')
  at Tr (client-BvkP3FTH.js:84:46108)
  at oa._applyModel (client-BvkP3FTH.js:210:14757)
  at oa._updateView … at oa.onRender …
```

Узнали об этом только потому, что игрок прислал консоль. В движке нет
никакого сбора ошибок:

- ни `window.onerror`, ни `unhandledrejection` в `packages/engine/src/`
  (проверено grep'ом);
- единственный приёмник выгрузок — `POST /debug/report`
  (`packages/engine/src/master/lobby.js:326-349`,
  `packages/engine/src/master/DebugReportStore.js`) — регистрируется **только
  вне прода** и нужен отладочному контуру (сценарии, дампы, расхождения
  предсказания), а не ошибкам;
- стек из прода минифицирован: `client-BvkP3FTH.js:84:46108` без source maps
  не прочитать.

Топология прода, которая определяет решения ниже
(`docs/en/deployment.md`):

- **Лобби-мастер и dedicated-сервер — один Docker-образ**; роль выбирает
  `VIMP_DEDICATED_GAME` (`packages/engine/src/master/main.js`). У каждого
  бокса свой домен; мастеров в `SERVERS_MATRIX` может быть несколько.
- Клиент движка (`packages/engine/dist/`) раздаёт **сам бокс** (vite-express,
  `ViteExpress.bind` в `lobby.js` и `dedicated/main.js`); игровые бандлы — по
  `/games/<id>[/<version>]/…` (`master/gameStatic.js`, в dedicated —
  `express.static(distDir)`).
- CSP страницы: `connect-src 'self' wss: data: <authServiceUrl>`
  (`packages/engine/src/config/master.js:148-153`) — браузер не может
  стучаться на чужой домен (мастер ≠ dedicated).
- Dedicated-бокс про мастер ничего не знает. **Все** боксы знают только
  central auth-сервис (`VIMP_AUTH_SERVICE_URL`): у него Postgres, роли
  админов (`requireAdmin`, `packages/auth/src/main.js:161`), его деплой — тот
  же `.github/workflows/deploy.yml`.

## Принятые решения (не пересматривать при исполнении)

1. **Хранилище — Postgres auth-сервиса**, таблица `client_reports`
   (этап 1). Мастер и dedicated БД не получают.
2. **Браузер шлёт на свой же бокс** (same-origin `POST /client-reports`):
   ни CSP, ни CORS, ни Nginx не меняются. Бокс проверяет, режет, считает и
   **пересылает пачками** в auth (этап 2).
3. **Бокс ↔ auth — общий секрет** `VIMP_CLIENT_REPORTS_TOKEN`
   (`Authorization: Bearer …`), GitHub-секрет `CLIENT_REPORTS_TOKEN`,
   раскладывается деплоем в `.env` боксов и `.env.prod` auth-стека.
4. **Отпечаток (fingerprint)** считает бокс: sha256 от
   `[source, kind, code ?? normalizedMessage, rawTopFrame, engineVersion,
   gameId, gameVersion]`. Версии входят в ключ сознательно: исправление
   выходит новой версией, и регрессия в новой версии — **новая строка**, а
   старая строка остаётся `fixed`. Автоматического переоткрытия нет.
5. **`engineVersion` штампует бокс** (из своего `packages/engine/package.json`),
   а не клиент: клиент движка раздаёт тот же бокс, и доверять клиентскому
   полю незачем.
6. **Приватность:** в отчёте нет ника, id игрока и IP. IP бокс использует
   только как ключ лимита и никуда не пишет и не пересылает.
7. **Расшифровка стеков — на боксе** (этап 4): у бокса на диске ровно те
   сборки, что он раздаёт (движок в образе, игры в `VIMP_GAMES_DIR` /
   `node_modules`). Сборки выпускают `sourcemap: 'hidden'`, а бокс в проде
   **никогда не отдаёт `*.map` наружу**. Расшифровывается только новый
   отпечаток — не каждый отчёт.
8. **Плагину — сервис пула `diagnostics`** (этап 3) с API
   `warn(code, details)` / `capture(error)`; сервис опциональный:
   capability `diagnostics` игра в `requires` **не пишет**, на старом движке
   она получает `undefined` и работает как прежде
   (`packages/engine/src/config/clientServices.js`: «незнакомое имя — не
   отказ загрузки, а undefined в парте»).
9. **Защита от спама — слоями, и главный ресурс — НОВЫЕ строки.** Повтор
   известного отпечатка стоит один `UPDATE count`, поэтому ограничивается
   появление новых отпечатков, а повторы считаются всегда:
   - **клиент** (этап 3): дедуп и не больше 50 разных ошибок на сессию;
   - **бокс** (этап 2): лимит запросов по IP, где IPv6 считается подсетью
     **/64** (иначе у одного злоумышленника бесконечный запас адресов);
     **бюджет новых отпечатков на бокс** — 60 в минуту; сверх бюджета и при
     полном буфере новые отбрасываются, известные не вытесняются никогда, а
     число отброшенного уходит в журнал служебной записью
     `source: 'box'`, `code: 'reports.dropped'` — атака видна, а не тиха;
   - **auth** (этап 1): бюджет новых строк **по IP отправителя** (2000 в
     час) и **общий** (10 000 в час), **потолок таблицы** 200 000 строк;
     сверх — обновляются только существующие строки, ответ `200` с
     `throttled`, в журнал процесса — одна строка в час.
   Бюджет auth считается по IP, а не по полю `box`: `box` бокс пишет сам,
   и с утёкшим секретом его можно подменять на каждом запросе.
10. **Один общий секрет на все боксы — принятый риск.** Утечка с любого
    бокса даёт запись в журнал, но не больше бюджетов и потолка из п. 9 (и
    ничего, кроме журнала: секрет не открывает других маршрутов). Секрет на
    каждый бокс (HMAC от общего по домену) и массовый разбор мусора в
    админке (по боксу/комнате/периоду) **отложены** — см. «Вне объёма».

## Архитектура

```
браузер (движок)                бокс (лобби или dedicated)            auth-сервис
────────────────                ─────────────────────────             ───────────
window 'error'          ┐
'securitypolicyviolation'
'unhandledrejection'    ├─► diagnostics ──sendBeacon──► POST /client-reports
Worker хоста (onerror)  │   (дедуп, ≤ 50 ошибок         ├ лимит по IP (IPv6 — /64), Origin, 16 KB
plugin: diagnostics.warn┘    на сессию, пачки ≤ 10)     ├ санитайз, отпечаток
                                                        ├ новый отпечаток: бюджет 60/мин на бокс,
                                                        │  расшифровка стека (source maps с диска)
                                                        │  + строка в docker logs
                                                        └ буфер ──каждые 30 с──► POST /client-reports
                                                          (+ reports.dropped)    Bearer <token>
                                                                                   ├ валидация
                                                                                   ├ бюджет новых строк: по IP, общий,
                                                                                   │  потолок таблицы
                                                                                   └ UPSERT client_reports
лобби, вкладка «Errors» ──► GET/PATCH /admin/client-reports (мастер, adminAuth)
                               └─ прокси Bearer ──► GET/PATCH /admin/client-reports (requireAdmin)
```

## Что попадает в журнал, а что нет

Попадает: неперехваченные исключения и отклонения промисов страницы;
неперехваченные ошибки и отклонения Worker-хоста; нарушения CSP (только в
проде, без расширений браузера); явные `diagnostics.warn` / `capture`
плагинов.

**Не попадает (осознанно):** вызовы `console.error` / `console.warn`;
ошибки, пойманные `try/catch`; сбои загрузки ресурсов и сети (`404`,
`fetch`); ошибки до установки перехватчика (импорт модулей,
`resolveBootConfig`); серверные ошибки dedicated-процесса (они в `docker
logs`); отсечённое лимитами (кроме счётчика `reports.dropped`); standalone
без `reportUrl`.

## Порядок выкладки

1. Сгенерировать секрет: `openssl rand -hex 32` → GitHub, Settings → Secrets
   and variables → Actions → **Secrets** → `CLIENT_REPORTS_TOKEN`.
2. Этапы 1–2 → push в `main`: `deploy.yml` выкатывает auth-стек (если задан
   `AUTH_SERVER_IP`) и все боксы. Миграция `013_client_reports.sql`
   применяется **автоматически** на каждом деплое auth-стека
   (`docs/en/deployment.md`, «Central auth service»: одноразовый контейнер
   `node src/db/migrate.js`, упавшая миграция останавливает деплой). Без
   секрета auth отвечает на приём `503`, боксы копят и логируют — ничего не
   падает.
3. Этапы 3–4 → push в `main` (клиент движка живёт в образе — боксы получают
   его деплоем). `npm run release` нужен для npm-пакета `vimp-engine`
   (SDK, контракт плагинов) — его выпускает разработчик.
4. Этап 5 — когда угодно после этапа 1.
5. Этап 6 — после того, как версия движка с этапами 3–4 опубликована в npm;
   затем релиз `@vimp-games/tanks` (вручную, см. `vimp-tanks/CLAUDE.md`) и
   передеплой dedicated-бокса.

## Вне объёма (осознанно отложено)

- **Секрет на каждый бокс** — `HMAC(CLIENT_REPORTS_TOKEN, domain)`,
  вычисляемый CI для каждого сервера матрицы; auth проверял бы пару «домен +
  секрет», сам писал бы `box` и отзывал бы боксы списком доменов. Нужен, как
  только появятся сторонние операторы боксов: общий секрет им давать нельзя.
- **Массовый разбор в админке** — фильтр по боксу, «Ignore» всего от бокса /
  за период, код комнаты в контексте отчёта (усилитель «хост нарочно роняет
  клиентов своей комнаты» тогда закрывался бы одним действием).
- **Лимит по /64 для остальных лимитеров** движка и auth (сигналинг,
  `limitSubmits`, `byIp` auth-сервиса) — та же дыра IPv6, но вне этой
  задачи. Хелпер из этапа 2 для этого готов; сделать отдельной задачей.

## Общие правила исполнения (из `CLAUDE.md` обоих репозиториев)

- **Никаких коммитов** и правок `version` — всё остаётся в рабочем дереве.
- Каждый этап заканчивается зелёными `npx eslint .` и `npm test` (в vimp —
  из корня; тесты зеркалят `packages/engine/src/` в `tests/`, auth — в
  `tests/auth/`, отдельный vitest-проект `auth`). Запуск без шума:
  `npx vitest run --reporter=dot`.
- **Документация в том же изменении**: `docs/en/<page>.md` канон,
  `docs/ru/<page>.md` — точное зеркало. Таблица «область → страница» — в
  `vimp/CLAUDE.md`. Контракт плагина правится ещё и в `docs/ai/`.
- **Журналы**: `packages/engine/CHANGELOG.md` (npm `vimp-engine`), раздел
  `## [Unreleased]`; подзаголовок задаёт уровень релиза (`### Added` —
  minor). У auth-сервиса журнала нет (пакет приватный). В vimp-tanks —
  `CHANGELOG.md` в корне. Тесты, рефакторинг и `docs/` — не записи.
- Код: ESM, `===`, `let`/`const`, фигурные скобки везде, без двух подряд
  заглавных в camelCase; импорты: Node built-ins → npm → внутренние →
  относительные. Комментарии — по-русски, кратко и про «почему» (как в
  окружающем коде). Новый модуль повторяет ближайший существующий паттерн.
- `packages/engine/src/host/` остаётся Worker-safe (без DOM и Node-глобалов).
  `src/devtools/` не попадает в бандл.
- Файлы с префиксом `_` — черновики, их не трогать.
- **Release impact** (правило `vimp/CLAUDE.md`): правки в путях `files` из
  `packages/engine/package.json` (`src/lib`, `src/config`, `src/host`,
  `src/client`, `src/standalone`, `src/devtools`, `bin`, …) отмечать в отчёте:
  какой артефакт, какой бамп, должен ли следовать vimp-tanks.
  `src/master/` и `src/dedicated/` в npm не публикуются. Удаление строки из
  `packages/engine/contract/surface.json` — повод остановиться и обсудить.

## Термины

- **Бокс** — процесс сервера из образа движка: лобби-мастер
  (`src/master/lobby.js`) или dedicated (`src/dedicated/main.js`).
- **Отчёт (item)** — одна ошибка/предупреждение с счётчиком повторов.
- **Отпечаток** — sha256-hex (64 символа), ключ строки `client_reports`.
- **Сырой верхний кадр** — первый кадр стека в виде `<pathname>:<line>:<col>`
  минифицированного бандла (имя бандла хешированное, значит стабильное в
  пределах сборки).
